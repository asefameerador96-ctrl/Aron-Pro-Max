## How to use this file

1. **Read the row, not the memory.** Before building anything that touches money, units, the day state, sync, scope, geofence, KPIs or printing, find its D-id here (search the topic word) and build to the "Decision" cell. A document or a lens that says something different is wrong; raise an amendment.
2. **Status tells you how far to trust it.** LOCKED-BY-SPEC: build it. DEFAULT: build it and expect it may be amended. MUST-CONFIRM: build the default now, and know that the named sub-milestone cannot exit until the business answers; the answer date is tracked in `docs/14` s4.
3. **Log what you assume.** Every new assumption, deviation or answer gets a row (or an amendment row in the change log) with the date and the reason, before the code that depends on it is merged. A decision raised by a plan document goes in its reserved block (section N); a decision raised by a build session goes to the doc 14 author with the same columns.
4. **Never edit a decision silently.** Status or text changes are made only by the doc 14 author, in the same commit as a change-log row. Rows are never deleted; a superseded decision keeps its row and the change log says what replaced it.
5. **Cite by id.** Code comments, commit messages, tests and gate evidence cite D-ids, F-ids, G-ids and T-ids exactly as written here; `rtm-check` (`docs/20` s8) fails the build when a cited id does not exist.
6. **Questions.** A business answer that arrives (Q, MQ) is recorded as an amendment of the decision that carries the default, with the answer, the date and who gave it; the confirmation schedule in `docs/14` s4 is updated in the same commit.
7. **Guardrails stay outside this file.** No credentials, keys or personal data are recorded here. Apsis credentials found in the dump are data to migrate or rotate (D-119); the Apsis backend and app are never called (D-312).
