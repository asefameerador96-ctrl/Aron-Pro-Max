# Critic: the SRE on launch day (R3, R5)

Date 2026-10-04. Author: SRE critic. Inputs read in full: CLAUDE.md, PROJECT-CONTEXT.md, README.md, docs/01–13 and docs/22, db/schema.sql, db/seed/README.md + sku_catalog.csv header, plan/seed-findings.md, and the seven lenses (data, features, scale, sync, config, security, quality). The two sibling critics (field, analyst) were skimmed for their conclusions and gap lists so this document does not re-raise G-field-15 (support code on blocking screens), G-field-07 (TSO absent at final submit) or G-analyst-02 (as-reported snapshots); where an SRE finding touches theirs it says so.

Scope: two launch days, wave 1 (1,000 SRs) and full fleet (8,500 SRs), played hour by hour from 04:00 to 23:59 Dhaka against lens-scale.md and lens-sync.md. For every incident: how it is detected (signal, time-to-detect), the blast radius, what the lenses already plan (cited), and what is MISSING as `G-sre-NN` with the fix. Then two audits the brief asks for: are the SLOs measurable from the proposed telemetry, and is there a rollback for every change type.

Conventions: gaps `G-sre-NN`; decisions `D-sre-NN`; test gates reuse the **unused slots of the 50-range** (T-0-50..59, T-1-53..59, T-2-55..59, T-4-58..59, T-7-57..59 — lens-scale owns the range and used T-1-51/52, T-2-51..54, T-4-51..57, T-6-51, T-7-51..56); questions continue after lens-quality's Q40. Config keys `cfg.<area>.<name>`; keys introduced here are listed in §5. "Dhaka" = Asia/Dhaka, UTC+6. ASSUMPTION is marked where the spec is silent.

## 0. Verdict (one page)

| # | Conclusion | Consequence |
| --- | --- | --- |
| V1 | **The load model is stale by one document.** lens-scale (13:10) sizes every storm on docs/01's 1.2 lakh successful calls/day; docs/22 (13:24) shows **~350k outlets with positive volume per day** (P-01) and ~2 lines per outlet-day (P-02). Memos are ~3×, `memo_line` ~1.2×, visits ~1.3×; a per-SR day is ~280 rows, not 180, so catch-up is **two** 200-row batches, not one. Capacity still has >2× headroom (D8 Postgres, 5,000 rows/s), but every load-test scenario S1–S9 and the per-SR numbers in the runbook are the wrong shape. | G-sre-05. Re-base before T-4-51 and T-7-51; the architecture does not change. |
| V2 | **The first day of a wave is not the steady-state login storm; it is a one-time storm of a different shape.** Every switched user does a *password* login (Argon2id 64 MiB), a *device bind*, a *full* bundle (no ETag), and an APK download, with no jitter (it is a human tap). On the full-fleet day that is 7,350 new users plus 1,150 wave-1 veterans. 30 concurrent Argon2id verifications per 2 GiB replica is 1.9 GiB of hash memory: the replica OOMs, the readiness probe drops it, and the storm lands on fewer replicas. None of the lenses models this day; lens-security T-7-75 tests 1,000 binds. | G-sre-04 (blocker): a **pre-bind day** (T−1, at the distribution house on Wi-Fi: install, bind, first login, tomorrow's bundle pre-fetched) turns day one into refresh + 304, plus a per-replica password-hash concurrency limiter. |
| V3 | **A DR or PITR failover silently loses data the devices believe is synced.** RPO 15 min (D-scale-5) or a PITR to T−1 h means the server forgets rows it already ACKed; the device marked them `synced` and will never resend them. Reconciliation shows a mismatch nobody can repair except from paper. The outbox already keeps synced rows for 3 days, so the fix is cheap: a **server generation** in every response and a device re-send of the last 24 h of synced rows when it changes. | G-sre-01 (blocker); it is also what makes a PITR "rollback" of the schema or data usable at all (§3.2). |
| V4 | **The one screen the business watches at 17:00 can be wrong on day one by construction.** lens-sync puts `day_submit` in the first priority class of the batch builder *and* requires `pending_rows == 0` before Sales Submit, while D-sync-08 lets a Wi-Fi-only phone submit offline and upload later. If the submit event reaches the server before the rows it closes (a 280-row day is two batches), every offline SR is flagged `submit_count_mismatch` at 17:00 — and lens-scale's pre-agreed rollback trigger is "reconciliation mismatch > 2 % of routes". A false fleet-wide rollback decision on launch day is the worst outcome this document found. | G-sre-02 (blocker): `day_submit` is always the last record of the day's outbox sequence; the server defers the state transition until `server_totals ≥ device_counts` claimed in the event, with a timeout, and shows "submitted (rows arriving)" meanwhile. |
| V5 | **One poison row can stall a device forever.** lens-sync counts only `rejected(retryable)` toward `attempt_count`; transport failures and 5xx never count. If a server bug throws on one row type (a DQ rule, a NULL in a generated column), the whole batch 500s, the device backs off and retries the *same* oldest family every 15 min for the rest of its life; nothing behind it ever uploads. The server must never let one row fail a batch, and the client needs a skip-ahead. | G-sre-03 (blocker). |
| V6 | **Three self-inflicted storms are missing from the plan**: the hourly access-token expiry wave (all tokens issued in the 07:00 storm expire together at 08:00, 09:00 … 17:00 — the last one lands on the check-out wave), the FCM push fan-out (a kill switch wakes 8,500 phones that all `GET /config/delta` within seconds), and bulk admin fixes during the morning (a 1,000-user re-assignment bumps `scope_version` → 1,000 forced re-logins + 1,000 snapshot rebuilds at 07:30). | G-sre-06, G-sre-07, G-sre-22. Jitter is the answer to all three; it costs nothing. |
| V7 | **The edge can lie to the client.** A Front Door WAF false positive (managed SQLi rules on Bangla UTF-8 JSON) returns an HTML 403; lens-sync's client treats 403 as "device unbound — stop sync for this user, show banner". One rule firing on one byte pattern halts sync for every affected device until a human notices. The client must distinguish an API envelope from an edge page, and `/sync/*` bodies must not be inspected by managed rules. | G-sre-10. |
| V8 | **Rollback exists for API, config and (mostly) schema; it does not exist for a bad app build with pending rows, nor for a bad import.** Reinstalling N−1 wipes app-private storage; the pending rows die with it, and a build whose *sync* is broken cannot upload them first. A wave-night delta import that lands wrong has no `undo`. | G-sre-20, G-sre-21: roll-forward "rescue release" policy, additive local schema openable by N−1 for one release, `rollback_import(run_id)`. |
| V9 | Nine SLOs are proposed; **five are only partly measurable** from the telemetry the lenses define (edge/TLS failures never reach the API's counters; "within 3 attempts" needs a header the sync wire contract does not carry; aggregation lag is a gauge, not a distribution; no burn-rate alerts; "vs yesterday" baselines break on the Friday off-day). | G-sre-19; all fixable in Phase 0–1 instrumentation. |

Blockers: G-sre-01, G-sre-02, G-sre-03, G-sre-04. Everything else is major or minor and lands in its natural phase (§9).

| Item | Steady-state morning (lens-scale §1.5) | Wave 1 day one (1,000 SRs + ~120 AMO + ~35 TSO ≈ 1,150 new users) | Full-fleet day one (7,350 new + 1,150 veterans) |

### 2.2 Incident 2b in detail: the full-fleet first morning

Mechanics the plan does not model: Argon2id at m=64 MiB allocates 64 MiB per verification for ~75 ms. NestJS replicas are 1 vCPU / 2 GiB with an HTTP concurrency rule of 30 (lens-scale §2.4). If 30 in-flight requests are password logins, that is 1.9 GiB → the container is OOM-killed, the readiness probe drops it, the storm concentrates on the survivors, and the API falls back to live bundle generation for the users whose snapshots were invalidated by binding (none, if snapshots are per user). Detection is fast (restart count, 5xx), the fix is slow (scale-out of cold replicas under a storm).

### 2.3 Incident 7 in detail: Submit % must be right at 17:00 on day one

The contradiction inside lens-sync: §2.3 priority classes send `day_submit`, `attendance_event`, `day_open` *first*; §2.9 allows Sales Submit only when `pending_rows == 0`; D-sync-08 and §8.8 let a Wi-Fi-only phone submit in the field and upload at home; §3.2 says the server accepts a submit whose counts differ and flags `submit_count_mismatch`. With a 280-row day (two batches) and `day_submit` prioritised, the server sees the submit event in batch 1 while batch 2's rows are still on the phone. Every SR who worked offline is flagged at 17:00; lens-scale's rollback trigger ("reconciliation mismatch > 2 % of routes") fires fleet-wide on a healthy system.

Fix (D-sre-02): (1) the device appends `day_submit` **after** every row of the day in `outbox.seq`, and the batch builder's priority classes apply only to `attendance_event` and `day_open`; `day_submit` is never moved ahead of rows with lower `seq`; (2) the event carries `device_counts` for the route-day (it already does) and the server, on receiving it, **defers** `route_day.state = sales_submitted` until `server_totals ≥ device_counts` for every type, re-evaluating as later batches land (an outbox-worker check, idempotent); (3) until then the state is `submit_pending_rows` (new, device shows "জমা হয়েছে (সার্ভারে পৌঁছেনি)" as lens-sync already proposes); (4) if the rows have not arrived after `cfg.day.submit_settle_timeout_min` (30), the state becomes `sales_submitted` **flagged** `submit_count_mismatch` — the flag now means something; (5) the Daily Tracking and sync-health screens show `submit_pending_rows` distinctly (G-sync-09 asked for this); (6) the rollback trigger reads `submit_count_mismatch` **after settle**, never before. Gate T-1-54.

### 2.4 Incident 6b in detail: poison rows

Server: ingest wraps **each record** in a savepoint (`SAVEPOINT r; … ROLLBACK TO r` on exception), converts the exception to `rejected(retryable=false, reason='server_error', detail=<error class>)`, writes `sync_rejected` with the payload and the stack hash, emits one Sentry event per error class per hour, and returns 200 with the rest accepted. The batch-level transaction still commits. Client (lens-sync §2.7 amendment): a `family_fail_count` increments on every transport/5xx failure *of a batch containing that family*; when any family reaches `cfg.sync.family_skip_after` (5) the batch builder sends all **other** pending families first, then that family alone; a lone family that fails `cfg.sync.row_max_retries` becomes `rejected(retry_exhausted)` and is surfaced (lens-sync §2.9) with "report to supervisor" — the memo exists on paper; money changed hands; the day is not blocked. Gate T-1-53.

### 3.3 Edge responses the client can misread (G-sre-10)

lens-sync §2.6 maps HTTP outcomes to device actions assuming the body is the API's. Front Door (and ACA ingress) can return 403 (WAF), 404 (origin group misroute), 502/503/504 (origin unhealthy), 413 (body size at the edge), all as HTML or empty. The client rule must be: a response is an **API response** only if `content-type` is `application/json` and the body has the envelope (`success` present); anything else is a **transport failure** (backoff, same `batch_uuid`), never a terminal state. Edge 413 must be distinguishable from API 413 (the API's halving rule assumes its own cap). WAF: managed DRS in Detection/Log mode on `/sync/*` and `/media/*` for a full wave on real payloads before Prevention; body inspection excluded for those paths (custom rules — per-device limits live in the API anyway, G-scale-04).
