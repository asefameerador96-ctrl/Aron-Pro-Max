## 0. How to read this file

**Merge rule.** Two source gaps are one register entry when they describe the same screen, rule or behaviour: the shared SR/AMO flows (sale, review, memo, stock, QC, attendance, printer, updater, outlet forms, Astha, tasks, Sales Deposit), the OTP (SR + Web), Team Location and the map decision (AMO + TSO), Submit % (TSO + Web) and the target model (TSO + Web). Related but different defects stay separate and cross-refer. Merged severity is the maximum of the sources.

**Kinds.** `contradiction` (manual and spec/plan disagree, or a spec-of-record rule is wrong), `feature` (a screen, report or endpoint that does not exist in spec or plan), `field` (a field, table, data set or code list missing), `rule` (a missing rule, now stated), `underspecified` (exists but a rule, state or text is missing), `message` (strings), `online-only` (connectivity behaviour). The source deltas' `missing-feature` -> feature; `missing-field` and `new-data` -> field; `missing-rule` -> rule; `missing-message` -> message; the single `new-config` gap (map provider) is filed as feature; config keys are collected in section 2.5, not as a kind.

**Severity.** blocker = cutover parity breaks or a sale/day cannot be reproduced; major = a daily workflow, report, KPI or integrity rule is wrong or undefined; minor = confirm-only, cosmetic or an edge rule.

**Phase** uses `docs/12` (P0 foundations, P1 vertical slice, P2 full SR day, P3 supervisors, P4 web, P5 programs, P6 admin/master data, P7 migration/cutover). Where a decision must land before the phase that builds it, the earlier phase is shown.

**IDs.** `G-man-nnn` are merged ids. Source ids in the deltas (`G-man-sr-nn`, `G-man-amo-nn`, `G-man-tso-nn`, `G-man-web-nn`) are traced in Appendix A. `F-xx-nnn` in 'proposed home' are lens-features ids; new ids continue after the current maximum (F-SR-053, F-AMO-036, F-TSO-020, F-WEB-047, F-ADM-037, F-SYS-046, F-API-038). New ids assigned here: F-SR-054 Sale History, F-SR-055 Outlet points, F-SR-056 SKU target view; F-WEB-048 Astha Web Entry, F-WEB-049 Loyalty report, F-WEB-050 Web Entry, F-WEB-051 web Final Submit, F-WEB-052 web QC, F-WEB-053 DS-RRS, F-WEB-054 AMO Call Report, F-WEB-055 DSS, F-WEB-056 Route-wise Memo.

### 0.2 The 15 most important findings, in plain language

1. **The memo total is wrong in the spec (G-man-002, blocker).** The SR app subtracts a slide (empty-pack) value and a QC settlement amount from the memo total: 360.50 minus 80.00 gives 280.50, and 'মোট QC' sits before 'সর্বমোট'. Neither the schema nor the plan has a column or rule for either, so the printed memo cannot be reproduced and slide and QC have no money model. Add two deduction columns and change the net CHECK.
2. **Web 'Delete Section Data' collides with idempotent sync (G-man-086, blocker).** The TSO web Final Submit page can delete a route's day. docs/03 forbids hard-deleting transactions, and sync assumes a retried upload can never change a number. Make it an audited void and keep the voided client UUIDs as tombstones, so a late phone upload is rejected instead of resurrecting the data.
3. **Quantities are in sticks and the unit differs by screen (G-man-001).** SR and AMO enter sticks with a read-only pack badge; the plan assumed packs. Match prices show per piece on one AMO screen (FB 1 = 2.33) and per dozen on another (FB 1 = 28.00); the web says Lighter in Pcs, the TSO app says Box. This closes the units question for cigarettes and bidi and shows lighter and match need a base unit per category and visible unit labels.
4. **The device OTP works the other way round (G-man-021).** The server creates a 4-digit OTP when a device logs in on a new phone or after a new app version; the TSO only reads it on the web. The spec has the TSO issue it, the plan stores a one-way hash and defaults to 6 digits. Keeping 're-ask after every version' would mean about 8,500 TSO lookups per release and break an offline day, so recommend no re-verify for in-place updates, behind a switch.
5. **Taking a photo silently moves the outlet (G-man-017).** Force Sale (SR) and Manual Override (AMO) overwrite the outlet's stored location the moment the photo is taken, with no approval. That is the spoofing path CLAUDE.md #5 wants closed and docs/05 says to route through verification. Recommend a location-change request plus a provisional device-side location so the SR is not forced to Force Sell daily.
6. **Submit % divides by logged-in routes, not target routes (G-man-066).** The TSO tile divides submitted by logged-in routes, and the web tile and the AMO live tile appear to (the web sample has 0 submitted, so it cannot prove it). The plan flips it to target routes. Parity first, with the plan's figure kept as a renamed secondary number, and a live check on a day with real submits.
7. **Targets do not work the way the schema assumes (G-man-068, G-man-067).** Target rows are variant-level; every monthly target set, not only revisions, needs approval starting with a role called WMO, with start and end dates. The till-date target is a calendar-day pro-rata: the TSO ratios are exactly 26/30 for all four categories and the AMO ones about 25/30, while the plan defaults to working days.
8. **The TSO web portal is a back-office write tool the spec only names (G-man-085, 046, 086, 092, 093, 094, 048, 099).** Seven pages are in neither the spec nor the plan: Web Entry, Astha Web Entry, the web Final Submit page, DSS, DS-RRS, Route-wise Memo and the Loyalty Diamond League report. The TSO also writes QC, Sales Plan, targets, outlet approvals, wholesale flags and Astha gift choices, so 'admin pages' and '37 pages, 13 menus' undercount the work.
9. **Three whole SR screens are missing (G-man-053, 013, 040).** SKU Target and Achievement with ADS, TADS, PADS and RADS; Sale History (online-only in the current app); and the outlet Points screen with expiring points and an expiry date. Slide/DRP exists only as a table name (G-man-004).
10. **QC is money and has six fault types in the app and ten on the web (G-man-003, 089).** The spec has two quantity columns. It needs a fault-type table, a settlement amount, and on the web a Market QC and Warehouse QC entry with Excel and PDF reports.
11. **Outlet requests are cluster-first and the lifecycle differs (G-man-033, 034).** SR and AMO forms pick a Cluster, not a Route. The AMO app can only Verify; Reject and Approve happen on the web, for New, Close and Info requests alike. The spec has route forms and an AMO 'Cancel = reject'.
12. **TSO logout wipes everything, synced or not (G-man-024).** 'Your all app data will removed' with no pending-upload check conflicts with the offline-first and idempotent-sync rules; docs/08 still says keep it. Refuse while anything is unsynced.
13. **There is no text for anything that goes wrong, and no string catalogue (G-man-101, 102).** 251 message entries (about 225 app-owned) must be seeded in Bangla and English, and no manual prints a single error, offline, validation or failure message; offline-first means those must be authored and reviewed with AKTCL.
14. **Final Submit needs a read endpoint and more rules (G-man-070, 071, 087).** The 'already submitted' alert fires at 'Get Sales Data', before Submit, so a preview read is needed; routes with 'SR Not Set' are listed, there is no confirm and no time gate; the web page adds a date picker, a Bangla cut-off banner and a 'call support' override that should become an audited unlock.
15. **'Live' location is not live, and there is no map decision (G-man-058, 059).** The AMO and TSO manuals promise live SR location; the spec stores the last synced fix because of the battery rule. The apps use Google Maps with 3D buildings and no provider, key, cost or offline decision exists.

Only the live app or the sponsor's screenshots can settle: Joint Call items 4 and 5 (G-man-051), the three per-SKU card indicators (G-man-005), the basis of the maximum QC amount (G-man-002), whether a photo is taken on every call (G-man-016), and the printed memo layouts (G-man-014). They are listed with owners in section 5.

### 0.3 What was re-checked in this merge

- **Tallies re-added.** Each delta's coverage table sums to its stated total (SR 381, AMO 327, TSO 144 inventory items plus 77 field/control checks, Web 235), and each delta's gap kinds and severities were re-counted from its own gap index and match its headline (SR 1/15/17, AMO 0/27/22, TSO 0/12/17, Web 1/16/10 blocker/major/minor).
- **Till-date target (G-man-067).** TSO p19: all four till-date/monthly ratios are 0.867 = 26.0/30. AMO p35 digits re-read on the PDF: cigarette about 2,475,000/2,972,900 = 0.833, bidi 85,263/102,800 = 0.829, lighter 0.833, match 0.831 (about 25/30; a Friday-off working-day basis would be 0.808). The AMO inventory's bidi till-date target 82,263 is a misread (printed 16% only fits 85,263), so the 'bidi outlier' that follows from it does not exist.
- **AMO p76 fractional targets (G-man-064).** Nine of the eleven brand targets times 17 are round numbers (Marise 88,235.29 x 17 = 1,500,000). The Maxim - Platinum Series sales read 3,780 on the PDF, not 3,740, which makes its 107.1% consistent; it is not a data glitch.
- **Id collision found.** `delta-sr.md` proposes new feature ids F-SR-051, F-SR-052, F-SR-053, but `plan/lens-features.md` already uses those for stock return, cash deposit and returns/damaged goods. New SR features here start at F-SR-054 (G-man-013, 040, 053 use F-SR-054, 055, 056).
- **Key names unified.** The deltas name the same config differently: `cfg.app.hold_ms` / `hold_to_confirm_ms`, `cfg.i18n.digit_script` / `numeral_system`, `cfg.maps.provider` / `cfg.map.provider`, `cfg.app.reconcile_counters` / `cfg.sync.reconcile_types`, `cfg.print.pairing_pins` / `pin_hint`; section 2.5 uses one name for each.
- **Money unit.** The web SKU list shows prices to three decimals (7.935, 6.945, 6.445), which paisa (`_minor` in `db/schema.sql`) cannot hold; the plan's milli-taka (`_mtk`) is used in the sketches in 2.8.
- **Coverage percentages are upper bounds.** The deltas counted an item COVERED when the spec OR a `plan/lens-*.md` draft covers it. Plan-only items known from the deltas: SR S-08, S-09, S-16, R-016, the device-OTP table, the app-release manifest, per-screen cfg keys; Web password-history tables, outlet kind, gift assignment, route_log view, target revisions, report export log. The spec-of-record figure is therefore lower than shown in section 4.
- **Not done.** No live-app access. PDF spot-checks beyond the deltas' own logs (SR pp 10-11, 23-25, 34-35, 37-38, 45-47, 62-63, 72-73; AMO pp 8-11, 28-29, 34-35, 40-45, 66-68; TSO pp 5-7, 10-11, 13-21; Web pp 2-7, 10-11, 19-20, 22, 24-25, 27-28, 31, 35-37, 40-46) were limited to the two pages above, so other pages rest on the inventories.
