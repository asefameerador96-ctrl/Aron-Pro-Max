# Login credentials: plan (owner directives D-OWNER-CREDENTIALS-01 and -02)

Status: PLAN. Nothing is generated or created until the final Azure account exists. No password, no person's name and no phone
number is ever in this repository.

## What is delivered
Six Excel workbooks, placed in the owner's Drive folder (id 1blHIC8Z1taJnFNdD-WXpmVqPxc6tb61L) after the accounts are created in the
final account.

| Workbook | App | Count (October master data) | Columns |

Each workbook also has an "exceptions" sheet (positions the data could not resolve) and a "read me" sheet (how the first login works).

## Usernames
The owner's rule: the username is mostly the code; names are supplied separately and shown after login.
- SR: the Sales Rep ID of the master data (two letters and digits), lower case. Reps keep the login they know.
- AMO, TSO, DMO, Wing Manager: the code of the zone, territory, division or wing. Codes of different levels are plain numbers and
  can collide (a zone 101 and a territory 101), and usernames are unique across the system, so the proposal is a role prefix:
  `amo-<zone code>`, `tso-<territory code>`, `dmo-<division code>`, `wm-<wing code>`. TO CONFIRM with the owner before generation.
- National User: `national-01` to `national-20`, unless the owner gives names or codes.
- The build's username rule (4 to 32 characters for SR and AMO, mapping gap M13) is checked against every generated username first;
  the rule is relaxed by a migration if a real code needs it, never the code changed.

## Names
The owner supplies the names for AMO, TSO, DMO and Wing Managers (the Apsis table `master_field_forces`, 8,078 rows, very likely
holds them: to be confirmed when the table definitions or the list arrive). A position without a name is created with the position
as its display name ("AMO, <zone>") and listed on the exceptions sheet.

## Passwords and first login
- One random initial password per account, generated by the script from the operating system's secure random source: 10 characters
  from an alphabet without look-alikes (no 0/O, 1/l/I), so it can be read out and typed on a phone.
- The database stores only the password hash. `must_change_password = true` (the schema has it): the first login forces a new
  password, after which the initial one is dead. An account not used within 30 days of creation is disabled until an admin resets it.
- Portal roles (DMO, Wing Manager, National User) additionally enrol their authenticator (TOTP) at first login, as the portal
  already requires for admins. To confirm with the owner: whether DMO, Wing Manager and National User must use TOTP.
- SR phones are also bound to the device by the existing device code flow (the TSO or an admin issues the code): a stolen workbook
  row alone does not open an SR account on another phone.
- The plaintext passwords exist in exactly one place: the workbooks in the owner's Drive folder. The generator writes them straight
  into the workbook files and into nothing else (no log line, no console output, no temporary CSV left behind); the lead's scratch
  copy is deleted after upload and the deletion is stated in the hand-over note.

## Scope each login gets (server-side, from the assignment, never from the client)
- SR: its routes, through effective-dated route assignments (a rep has one to three routes; the seven routes with two reps get a
  primary and a cover per the owner's answer).
- AMO: its zone. TSO: its territory. DMO: its division. Wing Manager: its wing. National User: national, read only.
- SR and AMO have no portal login; TSO has both the app and the portal with the same account (docs/34).

## How it is produced (in the final account)
1. The master data and the Apsis master tables are loaded (D-OWNER-MASTERDATA-01, D-OWNER-APSIS-DUMP-01): geography, houses,
   routes, outlets, field force.
2. A script, run once by the deploy identity, creates the accounts and their scope rows in one transaction per role and writes the
   six workbooks. It is idempotent by username: a second run creates nothing and does NOT regenerate passwords (it reports
   "exists"); a deliberate reset is a separate, audited admin action per user.
3. Reconciliation printed without any secret: accounts created per role against the expected counts, positions without a name,
   usernames that failed the rule, routes without a rep (92,961 outlets sit on such routes: no SR login; listed).
4. The workbooks are uploaded to the Drive folder; the lead verifies the six files are there and tells the owner; nothing else is sent.

## Proof before the final account
The generator is built and tested now against SYNTHETIC data only (a made-up hierarchy of a few zones): counts, uniqueness,
username rule, forced change at first login, idempotent re-run, and "no secret in any log" (a test greps the captured output for
every generated password). It is not run against the real master data in the test account.
