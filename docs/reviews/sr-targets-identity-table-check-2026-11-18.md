# Adversarial check of the proposed identity rule table (lane sr-targets-server), 2026-11-18

Three Opus attackers against the table (scratchpad copy, reproduced in the lane's request doc) and the ingest code at 18fd2ab9b; each claim checked by two refuters. No code existed for the table; this is a design check.

## lines-and-holds
SUMMARY: I checked the proposed rule (/tmp/claude-0/-home-user-Aron-Pro-Max/a5c3c45a-b89c-5768-9d5f-6bc05c04fc63/scratchpad/tkpi/table.md) against the code at 18fd2ab9b, reading only, and it fails at line level. The completeness test ("lines_complete") is defined as stored lines plus "finally-refused memo_line registry rows of the memo's family". That cannot be computed as written. (1) A line's family_uuid is the VISIT uuid, not the memo uuid (CaptureRepository line 179: family = m.visitClientUuid; docs/24 s4.2 lists memo_line with family header "visit"). An edit reuses the old memo's visit (SrSaleKit.beginEdit passes old.visitClientUuid), so refused lines of the old memo count toward the edit's completeness. If "family" is instead read as the memo uuid, the count is always zero and rows 4 and 5 fall back to the earlier bug: a refused line is added forever. (2) A reviewer's discard leaves ingest_registry at 'quarantined' (OpsApi.resolve only updates sync_quarantine), so a discarded line never counts as refused. (3) The server CAN say which line numbers were refused. sync_rejected and sync_quarantine keep the full record (memo_client_uuid and line_no included; see rejectedRow/storable and quarantine), and SalesSubmitDigest already reads them. So honest limit (i) rests on a false premise. Its claim that it is "bounded and self-heals" is also false when the held line is parked qty_invalid for good. (4) The merge rule says nothing about memo counts, so adding an undecided line to a memo the server already counts gives a second brand, outlet or SKU memo count. (5) For a paper twin, the stored lines carry no outlet or route. The twin match uses memo_no and date only, so today's paper sale can land under the wrong outlet or route on the campaign and route figures. Quantities are fine for the SR's own memos: accept_with_fix is refused for every money type (memo, memo_line, ...), the outlet and route cannot be fixed, and phone rows are immutable, so a stored line always equals the phone's line. Only a paper twin's lines can differ, and then S(twin) is the right answer.

### CONFIRMED (2/2): wrong row 4 and 5 (and the lines_complete definition)
lines_complete counts 'finally-refused memo_line registry rows of the memo's family'. ingest_registry has no memo_client_uuid and no line_no; its family_uuid for a memo_line is the envelope family, which the phone sets to the visit uuid. Read literally as family_uuid = memo uuid, the count is always 0, so a header whose only line was refused stays incomplete for ever. Read as the visit, it also counts other memos' lines (see the missing edit case).
SCENARIO: One-line memo M, SKU B, price list 0, 20 packets x 20 = 400 sticks. M is stored; the line is price_invalid, so the registry row is rejected with family_uuid = visit V. If the server counts refused rows WHERE family_uuid = M: stored 0 + refused 0 < line_count 1, so lines_complete=false. Under the phone rule, the line_no is not in S, so the phone adds 400 sticks, SKU memo_count +1, brand volume and memos, Star STD and campaign on every bundle for the rest of the month. Truth 0. This is the same regression the 18fd2ab9b review found.
FIX: Find refused lines by the record content, not the registry family: sync_rejected (retryable=false, stored_at IS NULL, payload->'payload'->>'memo_client_uuid' = m, user_id = caller), joined to registry status 'rejected', plus sync_quarantine discarded and not return_to_device, plus a parked row past parked_until or finalised_at, the rule SalesSubmitDigest already uses. Count distinct line uuids.

### CONFIRMED (1/2): wrong row 6 and 7 when the held line is later DISCARDED
A reviewer's discard updates only sync_quarantine; the line's ingest_registry row stays 'quarantined'. A registry-only count never sees the line as finally refused, so lines_complete stays false and the phone adds the discarded line for good.
SCENARIO: cfg.day.late_sync_after_final_policy = quarantine. M (2 lines) and line 1 upload before the zone-day Final Submit. Line 2 (SKU C, 10 packets = 200 sticks, captured before the lock) arrives in the next batch and is held after_final_submit; the reviewer discards it. Every later bundle: stored 1 + registry-rejected 0 < 2, so incomplete, and the phone adds line 2 (+200 sticks of C, C memo_count +1, brand, Star, campaign). Truth: S = line 1 only.
FIX: Include sync_quarantine 'discarded' (not return_to_device) rows of memo_line records whose payload names the memo, with the newest-row rule of awaitedState, in the refused set.

### CONFIRMED (2/2): wrong row 7 / HONEST LIMIT (i)
The premise 'the registry does not keep the refused line_no' does not matter: sync_rejected.payload and sync_quarantine.payload hold the full record, line_no and memo_client_uuid included, and SalesSubmitDigest already reads them. 'Bounded and self-heals' is false: the held line may never be decided.
SCENARIO: M has 3 lines. L1 SKU A, 10 packets, stored. L2 SKU B, zero price, price_invalid. L3 SKU D, pack_factor no longer the SKU's base_per_pack after a future-dated pack-size change, parked qty_invalid. The phone resends the same immutable payload, which is parked again; nothing on the phone rewrites it. lines_complete stays false all month, and the phone adds L2 (400 sticks of B) and L3 on every bundle. L3 is undecided, so adding it matches the definition. L2 is refused, so the over-count of 400 sticks of B (+1 memo) lasts until month end, not 'until the held one is decided'.
FIX: Return the refused line_nos (or line client_uuids) per memo when the memo is incomplete; the phone then adds only local lines in neither the stored nor the refused set. limit (i) goes away.

### CONFIRMED (2/2): wrong row 7 (merge of undecided lines into a counted memo)
The rule says 'add local lines whose line_no is not among stored_lines', but it does not say that memo counts must not be added again. F already counts the memo once per SKU (any non-voided line), and once per brand and per campaign outlet-SKU pair (sale line), whenever S has such a line.
SCENARIO: M dated d<=T. L1 SKU A (brand X) is stored; L2 SKU E (brand X) is held. F gives brand X 1 memo. The phone adds L2 as a memo contribution, so brand X memos = 2; truth 1. The same applies to campaign memos for an outlet-SKU pair, and to SKU memo_count when S already holds a free or sale line of that SKU.
FIX: State it: for a STORED memo, the phone adds quantity for undecided lines, and adds a memo count for a SKU, brand or outlet pair only when S (live stored lines, kind-aware: any kind for SKU memo_count, sale only for brand and campaign) has none. For today's memos, count over the union S plus undecided lines, once per key.

### CONFIRMED (2/2): wrong row 27, 28, 29 (paper twin)
stored_lines carries (sku, qty_base, line_kind, line_no) but no outlet_id or route_id. The twin is matched on memo_no and date only (SrFigureProbe), with no outlet or route check, unlike matchBackfill. The phone puts S(twin) under its own copy's outlet and route. The answer also does not say it is a twin, so the line_no-based 'add undecided local lines' can mix the phone copy's line numbers with the paper memo's.
SCENARIO: Today the office keys paper memo P, number N, for outlet O2 on route R2 (the SR's cover route, or a mistyped outlet). The phone's copy u has the same number N for outlet O1, route R1. Row 28: the phone adds S(P) to the R1 achievement and the O1 campaign figures, so R1 and O1 are too high by P's lines and R2 and O2 too low until tomorrow. If the copy is also removed locally and P is counted (d<=T): the phone subtracts S(P) from R1, which F(R1) never held, so R1 is too low.
FIX: For a twin match, add memo-level outlet_id and route_id and a twin flag. The phone places S by the answer's outlet and route, never adds local lines to a twin answer, and treats 'counted' as in this figure's route or outlet scope.

### CONFIRMED (2/2): missing case: Edit in the same visit borrows the old memo's refused line
server state: M stored, its zero-price line L2 rejected (registry family_uuid = visit V). Edit E (beginEdit reuses old.visitClientUuid = V) has header stored, E1 stored, E2 not yet stored (next batch, or parked).; phone result: lines_complete(E) = stored 1 + refused-in-family-V 1 (M's L2) >= line_count 2, so true. Today: the phone adds S(E) = E1 only. d<=T: adds nothing.; truth: S(E) + E2 (undecided local line), e.g. +10 packets = 200 sticks of SKU C and C memo_count 1
SCENARIO: Visit V: M with L1 SKU A 20 packets and L2 SKU B priced 0 (refused). The SR edits M at the outlet: E1 SKU A 30 packets, E2 SKU C 10 packets. The batch is cut after E1. Until E2 is stored the phone under-counts SKU C by 200 sticks, brand and Star by the same, and C memo_count by 1; if E2 stays parked, it under-counts for good.

### CONFIRMED (2/2): missing case: Today's memos made on another phone (shared phone, same login)
server state: Memos of today stored from device A; F excludes today.; phone result: Device B has no local copy, so there is no probe and nothing is added.; truth: Today's stored live sales from device A
SCENARIO: The SR sells 5 memos on phone A in the morning, then logs in on shared phone B (Room database per user per device). B shows today's achievement without those 5 memos until tomorrow. This is not line-level, but it is reachable and the table does not cover it.

REFUTED CLAIMS: missing case: Line parked past its TTL (server calls it final); missing case: All lines refused, family read as memo uuid; missing case: Refused-line rows pruned inside the month

The registry has no memo_client_uuid or line_no column, so neither 'the memo's family' nor 'which line_no is refused' comes from the registry alone.

I did not check indexes for a payload->memo_client_uuid lookup on sync_rejected; it may need one (filter by user_id and business_date first).

- Discard leaves ingest_registry 'quarantined' (OpsApi.resolve updates only sync_quarantine; followDiscardedParent follows gift photos only). Any registry-only 'final' test misses discarded lines, and also discarded voids and edits of a held parent.
- Quantities: accept_with_fix is refused (ERR_REQUEST_STATE, 409) for every MONEY_TYPES record (memo, memo_line, memo_discount, qc_line, memo_void, due_collection, ...). A fix of a non-money record (e.g. the parent visit) must keep client_uuid, type, family_uuid, business_date, route_id, acting_for_user_id and outlet_id, and the held lines are released unchanged. Phone rows are never edited after commit, and the qty_invalid resend repeats the same payload. So for the SR's own memos, stored qty_base equals local qty_base for the same line uuid. Only a paper twin can differ, which is why rows 28 and 29 must use S(twin), not L.
- matchBackfill compares lines as sorted sku:qty_base:price:gross only (no line_kind, no line_no). Line numbers of a matched paper memo bear no relation to the phone copy's, which is another reason never to line_no-merge on a twin answer.

For own memos the phone knows outlet and route locally and they cannot change (a fix keeps both), so sku, qty_base, line_kind and line_no are enough. For a twin, add outlet_id, route_id and a twin flag. Phone-made lines are always kind 'sale' (SaleCommitter), so free kinds arise only on paper twins; S carries line_kind, which is enough.
- 'counted' is defined by date only. F is per route (forRoutes, m.route_id) and per outlet for campaigns. Correct for the SR's own memos, whose route and outlet are immutable; wrong for a twin on another route or outlet (see the twin wrong row).
- Privacy: stored lines and refused lines must be filtered to the caller's own memos (memo user_id OR acting_for_user_id) and own uploads (user_id). A twin is restricted to own manual memos. With those filters no line-level answer reveals another user's records. Note that a cover TSO's refused line of an SR memo is uploaded under the TSO's user_id, so it is never visible to the SR, and the SR's memo then stays incomplete. That is safe (no leak), but the SR adds that line.

## removals-and-chains
SUMMARY: I read the rule and its case table in full, the last three sections of the review history, and the code at 18fd2ab9b (IngestService process, quarantine, acceptQuarantined/releaseHeld/settleChild/followDiscardedParent, the waiting sweep, matchBackfill and memoAlias, DuesLedger, DataVoidApi, SrFigureProbe, SrMemoFigures), plus the phone's edit flow (SaleCommitter, SrSaleKit.beginEdit). Nothing was built or run.

Rows 1-31 come out equal to the truth as defined, with one exception: the lines_complete definition (rows 5-7, and 22 when the edit's lines are incomplete) is wrong. It counts refused lines by registry family_uuid, but that is the VISIT uuid, and an edit reuses its memo's visit (SrSaleKit.beginEdit passes old.visitClientUuid). So the old memo's refused lines count toward the edit's line_count. Honest limit (i) is also avoidable: sync_rejected.payload keeps memo_client_uuid and line_no.

The refused-removal rows (17, 18, 23, 26) and row 25 are correct only if REFUSED means "no open item and not stored". The current refusedOf matches ANY discarded quarantine row, and a discarded payload_conflict copy of a record that is still held flips a pending edit to REFUSED.

Storing an edit and superseding the old memo is atomic. Both steps run in one savepoint under the memo:<old> lock; memo_void works the same way. So "edit stored, old not superseded" cannot happen.

Cross-date edits cannot come from the phone. The server does not check the date, but the rule still gives the truth if one arrives.

Gaps not in the table:
- A held or parked edit whose parent was refused or discarded can never be stored, yet it answers UNKNOWN forever. The phone adds it for the rest of the month (chains: the original plus the stuck edit).
- A discarded line never makes lines_complete true, so the phone adds it forever.
- A probe carries one removal uuid, but a memo can have two removals (the first refused). Duplicate probe uuids lose the removal.
- counted=false does not separate "after T" from "before the 1st", so on the 1st the live rule adds last month's memo.
- Today-dated stored own memos the phone does not hold (for example a paper memo keyed today) are never added.

### CONFIRMED (2/2): wrong row 7 (and the lines_complete definition in the ANSWER section; also 5, 6 and 22 when the edit's lines are incomplete)
lines_complete counts 'finally-refused memo_line registry rows of the memo's family', but the registry's family_uuid of a memo_line is the VISIT uuid (docs/24: 'The visit is the family root'; the test saleFamily sends every line with family = visit). An edit reuses the old memo's visit: SrSaleKit.beginEdit starts the flow with old.visitClientUuid, and SaleCommitter keeps outlet and day. So the refused lines of the old memo (and of every earlier link of a chain) count toward the edit's line_count, and an edit whose lines are still held or in flight is reported complete. The registry has no memo_client_uuid column to attribute a line to its memo.
SCENARIO: Memo m (visit v, line_count 2): line 1 SKU A 20 sticks stored; line 2 SKU B 10 sticks at price 0, refused price_invalid (registry rejected, family v). m is complete (1 stored + 1 refused). The SR edits m to E in the same visit v: A 20, and B 10 at the right price, line_count 2. E's header and line A are stored. E's line B is parked qty_invalid after its memo was stored (step 7b) or comes in a later batch. lines_complete(E) = 1 stored + 1 refused row in family v (m's line) = 2 >= 2, so it answers true. Phone, E dated <= T: adds nothing for B. E dated today: adds S(E) = A 20 only. Truth (the row 7 definition): S(E) + B 10, so the phone is 10 sticks of B short on brand, Star and campaign until B is decided. Chain m0 -> m1 -> m2, each with one refused line, and m2 (line_count 2) with no lines stored yet: complete = 0 + 2 >= 2, so it is treated like row 4 and the phone adds 0 for a whole pending sale.
FIX: Attribute refused lines by sync_rejected.payload->>'memo_client_uuid' (final rows, retryable=false), not by registry family. Count each line uuid once, and only when it is not stored. The same rows carry line_no, so the server can also return the refused line numbers, which removes honest limit (i).

### CONFIRMED (2/2): wrong row HONEST LIMITS (i)
The premise 'the registry does not keep the refused line_no' is true of app.ingest_registry, but rejectedRow writes the whole record (payload jsonb, including memo_client_uuid and line_no) to app.sync_rejected for every final reject. The server can compute in the same snapshot which line numbers were refused, so the limit is avoidable, not inherent. The one caveat is retention, which I did not check for sync_rejected; ingest_registry has a 30-day minimum, so a refusal from day 1 can be pruned by day 31 of a 31-day month.
SCENARIO: Memo, 3 lines: line 2 refused price_invalid for good, line 3 held. Proposed rule: the phone adds lines 2 and 3 (line 2 wrongly) until line 3 is decided. With sync_rejected the answer can list line 2 as refused, and the phone adds only line 3.
FIX: Read refused line numbers per memo from sync_rejected (final rows), and include quarantine-discarded lines (see the missing cases). State the retention dependency.

### CONFIRMED (2/2): missing case: A line held and then discarded by a reviewer is never 'finally refused' for lines_complete

CASES CHECKED AND FOUND RIGHT: Edit of a memo the admin data-voided (status still active)

NOTES:
- Atomicity holds for edits. DuesLedger.check takes the advisory lock memo:<old> and requires status = 'active'. DuesLedger.afterStored (the supersede UPDATE and the ledger closure) runs inside process(), in the same record savepoint and transaction as RecordWriter.write. Any non-transient error rolls the whole record back. acceptQuarantined, releaseHeld, matchBackfill (through memoAlias to the paper memo) and the waiting sweep all go through the same process(). A stored edit with an un-superseded old memo cannot happen, and memo_void works the same way. So the rule's 'r = edit memo stored -> old memo GONE' is sound.
- Cross-date edits do not come from the phone. SaleCommitter.checkEdit requires 'an edit stays on the same outlet and day', and commit throws ClockMovedBackException if the date moved. The server does not check the date. If an old or modified client sends one, the rule still gives the truth: old memo counted, subtract S(m) while pending; new memo today, add S(E) once stored; the reverse order also works.
- Rows 14, 20 and 25 are not errors, but should be stated as such: while the removal is pending or HELD (possibly for days, after_final_submit or the device gate), the phone shows the SR's intent (0, L(e)) while the server, dashboards and incentives count the old memo. That is the agreed truth definition (local pending removals applied). In the stuck-child cases above it never converges.
- Rows 17, 18, 23, 25 and 26 are correct as written, provided REFUSED means a final registry reject, or a newest discarded quarantine row with no open item and not stored (see the payload_conflict case). Row 23's discarded edit leaves its lines open in quarantine for good (followDiscardedParent follows gift photos only). That does not affect the figure, because E is REFUSED.
- A void and an edit of one memo from different users cannot happen. crossUserParentAllowed allows other users' parents only for against_memo_client_uuid, task_uuid and request_uuid, so another user's void or edit is held scope_out_of_reach. On one phone, an edit after a void is possible only once the void was refused (missing case 5).
- return_to_device: re-sending the same uuid with the same payload reopens the same row (V0193 ON CONFLICT) and is judged again, so UNKNOWN or STORED is right. Re-sending the same uuid with a changed payload is payload_conflict, which cannot be accepted, so it ends REFUSED after the discard (consistent). If the phone restores m as live on return_to_device, it must stop sending removed_locally for m; the rule should say so.
- Row 13: at 18fd2ab9b I found no single-memo office void. A memo is GONE only through the phone's void or edit or a route-day admin data void (DataVoidApi, which also tombstones memo_void rows but leaves memo status unchanged). Row 30, a twin voided by the office, can only be a route-day data void.
- Privacy: the own filter in SrFigureProbe is user_id = caller OR acting_for_user_id = caller, so stored_lines can be returned for a cover user's memo (an earlier LOW). Removal-uuid lookups (edit memo stored -> accepted) must use the same own filter. refusedOf filters on the uploader only. Inferring 'memo_void accepted' from m being GONE reads nothing about r itself and reveals nothing beyond m.
- The memo uuid lookup filters business_date = ANY(probe dates). docs/24 s3.8 item 3 allows the server to re-date a record, keeping business_date_device, but ingest does not do this at 18fd2ab9b. If it is ever built, a re-dated memo would answer UNKNOWN and be counted twice.
- The ingest_registry retention minimum (30 days) is shorter than a 31-day month, so REFUSED answers and registry-based line refusals can disappear on the last day. sync_rejected retention was not checked.

## twin-scope-privacy-misc
SUMMARY: I checked the proposed rule (table.md) against the code at 18fd2ab9b, read-only. I read SrFigureProbe, SrMemoFigures, BundleService.figures and the loaders' windows, IngestService (acceptQuarantined, releaseHeld, matchBackfill, finalReject and park, memo-number checks, zero-price and pack-size handling), OpsApi discard, DataVoidApi, MemoNumbers, the memo_no_unique index and the memo_line schema. I also read the last three review rounds. Verdict: it fails. One identity answer cannot serve every figure, because the figures differ in scope (route for achievement, KPI and Star; outlet for campaigns) and in window (month-to-date versus Star's whole last month, plus the 1st of the month, prefetch and future dates). The rule's step "not counted means today" adds sales from another month.
