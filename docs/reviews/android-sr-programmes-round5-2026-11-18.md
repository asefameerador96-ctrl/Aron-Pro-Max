The lost-answer rule is built as ruled and works for the case the lead described: rows left in_flight by a timeout or a kill are captured under the sync lock at the bundle request, stored with the snapshot in the same transaction, never added to Astha and never subtracted from points, the line is shown on the Astha and points pages, and one full bundle is asked when they are all answered, at most once per 10 minutes with the stamp persisted. The memo is counted exactly once before and after the refetch. The lane's stated limit ('same-version refetch is ignored') is wrong in the good direction: a same-version bundle is applied again and clears the list.

The server commits family by family, so a 500 or a gateway 502/504 can follow stored memos; those memos are then added again with no line. Rarer than B1c, small fix (treat pending rows with a last_code as sent, add a real-engine test); the lead may demote it.

- Sequence (a) lost answer, bundle, later replay ack, refetch: CORRECT by reading. At the request the in_flight rows are in bundle.uncertain, so they are not added (the server figure holds them once, line shown). After the replay ack refreshIfUncertainResolved asks one full bundle; the new requested_at is after the ack, the list is rebuilt (empty), the memos count as inside the figure. Counted exactly once before and after.
- Sequence (b) attempt never reached the server: rows are uncertain only if a FULL bundle was applied after the failed attempt; the list belongs to the held snapshot. A phone offline all day applies no new bundle, so yesterday's 40 memos keep their real state (in_flight) against the old snapshot and ARE added: no under-report in that case. With a flapping link (upload fails, bundle succeeds) the 40 memos are missing from the page with the line shown, until the next sync run that answers all of them ends DRAINED or RUN_LIMIT and the refetch succeeds. Self-heals; the status file says 'never added' and 'safe side' but does not say in plain words that the page under-reports until then.
- Sequence (c): the lane's stated limit is WRONG, in the good direction. ReferenceRepository.apply ignores only a strictly older version (compare < 0); a same-version bundle is applied again and replaces requested_at and bundle.uncertain (the lane's own test relies on it). fullOfTheDay sends no If-None-Match, so there is no 304. The server version is a per-user sequence over the whole bundle content including programmes (BundleService.snapshotSeq, table app.bundle_snapshot V0032), so it moves when figures move and stays equal otherwise; either way the refetch clears the list. Rows that ended rejected or quarantined count as answered (stillOpen looks only at pending/in_flight), so the line does not stay forever. Correct the status file.
- Cost of the refetch: it is a full unconditional day bundle including every page. For the SR this is small. It also runs for AMO users, who write 'memo' rows and never read bundle.uncertain: an AMO with a memo in flight at the day-start bundle gets a second full download of a large paged bundle (up to about 11,000 outlets) once it is answered. One extra download per such event, rate-limited, but needless: restrict the capture or the refetch to the SR app. TSO: I found no memo or redemption writer, so no effect expected (not fully checked).
- refreshIfUncertainResolved does not check that the held bundle is today's. After midnight with yesterday's bundle held it asks the server for yesterday; the server refuses dates before today (400). Harmless but a wasted request per 10 minutes after sync runs, and the etag is deleted first. Add the same 'held != today' guard as refreshDelta.
- Rate limit: stored in sync_meta (survives process death), stamped before the request so a failed or offline refetch waits 10 minutes; guarded against a clock going backwards. The check and stamp are outside the downloader's lock, so two callers at the same instant could both refetch (once). The sync lock is held only around the head request, not the page downloads.
- bundle.uncertain: replaced or deleted in every full apply (also deleted when the list is empty and after a promoted prefetch), in the same transaction as bundle.requested_at; not touched by a delta or by an ignored older bundle. The database is per user (AronDatabase.fileName(userId)), so another user's list cannot leak. No size cap: about 37 bytes per row, bounded by the unsent queue; the IN query is chunked by 500.

- (demoted 1/3) A memo sent in a batch that the server answered with an HTTP error and the phone released is not seen as 'sent': it is still added on top of a figure that may already hold it: The lead's rule is: a memo is added only if it was never sent in any upload attempt before the bundle request. The lane's test for 'sent' is in_flight or attempts > 0. But attempts counts only definitive row failures (isolate), never a send. A timeout keeps rows in_flight, which is covered. A batch the server answered with a 5xx (or a gateway 502/504) while it carried more than one family is released: rows go back to pending with attempts = 0 and only last_code set. Those rows were sent, the server may hold some or all of them (families commit one by one), yet sentUnanswered() does not list them, so the phone adds them and shows no line for them. The later duplicate ack is after requested_at, so they stay added. This is the same harm as B1c by a rarer path. The fix is small: also treat a pending memo/redemption row with last_code not null as sent (release always sets it; over-including is the safe side), and add a test with a real SyncEngine run. The lead may demote this because it needs a server or gateway error after a commit.
