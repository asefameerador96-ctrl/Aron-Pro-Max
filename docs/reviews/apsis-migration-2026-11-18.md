# Lead review: lane/apsis-migration at 8a637747 (design, tooling, provisional migrations)

Reviewed 2026-11-18 by the lead (Opus pass, two lenses, three refuters per blocking finding). Read from code only: nothing built or run; the dump was never seen.

## design-and-data-correctness verdict=fail
SUMMARY: Read-only review of origin/lane/apsis-migration at 8a637747 (design lens). Nothing was built or run; the 20 lane tests were not executed; the real dump's schema is unknown to everyone, so every scenario about vendor column names, key shapes, code formats and time zone is a likely case, not an observed one. Azure behaviour (failover, parameters) was not checked against a live server.

What is sound: the archive-schema decision is well argued (live memo/visit tables cannot take aggregate rows without invented values); keys are deterministic (UUID v5 of table plus vendor key) and each fact chunk is delete-and-insert in one transaction, so re-runs do not double rows; unmatched outlets, SKUs and routes are kept with their vendor code and counted, not dropped; money goes through exact decimal arithmetic to integer milli-taka with one stated rounding rule; dates become UTC plus Dhaka business date; credential and personal-looking columns are dropped before staging; reports are numbers only; the migrations stay out of db/migrations.

Why it fails: (1) the design never names what the live system starts with at cutover: outstanding dues, loyalty/Astha points, target achievement, stock. The live schema has an opening-balance entry for dues, but the migration does not use it or even ask the owner where those balances come from, and it treats programmes as deferred although the SR programme screens are in scope since 2026-11-12. (2) No report can read the history: dw.v_sales_with_history is promised but not in the migration, nothing reads dw.v_hist_*, scope filtering has no mechanism, the attendance view has no scope column, and the 'sync roles cannot read history' property disappears at the next routine grant refresh because the role map grants api_rw and worker_rw every dw relation. (3) Verification compares staging with archive only, so a chunk whose unlogged staging rows were lost (crash or failover) is verified with zero rows and the reconciliation still says ok. (4) The runbook drops staging before the reconciliation that reads it. (5) A wrong time zone or date column cannot be detected: the hour histogram the design and runbook rely on is not implemented, and date columns silently fall back to created_at. (6) Matching is exact text with no rule for case or leading zeros, facts keyed by vendor ids are not supported, and a 100 percent unmatched load still passes. (7) The name-pattern drop removes non-personal columns (promotion_name, gift_name, any *key*) from the 'full raw' programme archives, and the dump is deleted after sign-off.

Files: docs/status/apsis-migration.md, docs/runbooks/apsis-history-migration.md, tools/apsis-migration/apsis_migration/{runner.py,staging.py,db.py,mysqldump.py}, tools/apsis-migration/sql/*.sql, tools/apsis-migration/provisional-migrations/V0260..V0262, tools/apsis-migration/mapping/columns.json, db/migrations/V0014__database_roles.sql (role map), db/migrations/V0007__field_transactions.sql (due_ledger).

### BLOCKING upheld=3/3: No report can read the history: the union view is promised but not built, and scope for history has no mechanism
WHERE: tools/apsis-migration/provisional-migrations/V0262__apsis_dw_views.sql; docs/status/apsis-migration.md sections 5 and 8 ("V0262: dw.v_hist_* views and dw.v_sales_with_history"); runbook section 4 step 5; db/migrations/V0014__database_roles.sql lines 84 and 88
WHY: V0262 creates four plain views and nothing else. dw.v_sales_with_history, which the design says the monthly-trend, same-month-last-year and outlet-history reports read, does not exist in the diff, and no API, web or report code reads dw.v_hist_*. It is not in the 'NOT done' list, so nobody owns it. Scope: the views expose scope columns but filter nothing; the design says filtering happens 'in the analytics layer', but there is no such reader, so the runbook step 'confirm a TSO sees only their territory through dw.v_hist_*' cannot be carried out. dw.v_hist_attendance has no scope column at all (user_code only), so it cannot be filtered by territory. Also, the claim 'sync roles cannot read history, by privilege' holds only until the next routine grant refresh: the role map has ('api_rw','dw','*','SELECT') and ('worker_rw','dw','*',...), and app.apply_db_role_grants() (called by 64 migrations) grants every dw relation matching the map, including the new v_hist_* views; the lane test passes only because the provisional migrations never call it. The direct GRANT in V0262 is outside the map, which is the project's single source for grants.
SCENARIO: After cutover a DMO opens the monthly report that compares this month with the same month last year, or an outlet's sales history: the months before cutover are blank, because the report reads only live tables. When someone later wires a report to dw.v_hist_sales_line there is no shared scope rule to apply, and the attendance view gives every caller all territories.

### BLOCKING upheld=3/3: A chunk whose staging rows were lost is marked verified with zero rows, and reconciliation still says ok
WHERE: tools/apsis-migration/apsis_migration/runner.py transform_all (metrics_stage vs metrics_hist compare, lines ~297-311), stage_all (skip when _stage is 'staged'); apsis_migration/staging.py ddl (CREATE UNLOGGED TABLE); sql/reconcile.sql sections tables, months, daily_money
WHY: Verification compares the archive only with the staging copy as it is now, never with the row count recorded when the table was staged (apsis_ctl.chunk.rows_in). Staging tables are UNLOGGED: PostgreSQL empties them after a crash, and they are empty on a standby after a failover. The resume logic sees _stage = 'staged' and does not restage. The transform then deletes the chunk's archive rows, inserts nothing, both sides count 0, and the chunk becomes 'verified' with rows_out 0. The reconciliation's 'tables' test is rows_in >= rows_out (true), 'months' needs only state verified, and 'daily_money' compares staging with archive (both empty). The missing rows appear only as a large 'skipped_no_date_or_key' number in a report whose overall flag is ok. More generally, every money and quantity check compares the tool's staging with the tool's archive using the same filters, so it cannot show rows lost before or at staging; there is no check against the vendor's own totals for money.
SCENARIO: During the 12-hour load the PostgreSQL server fails over (the final account's production server is planned with high availability) after sales is staged but before all months are transformed. The operator restarts the same command as the runbook says. The remaining months verify with 0 rows, 'reconciliation ok' is printed, the owner signs, and the dump is deleted with several months of sales history missing.

### BLOCKING upheld=3/3: A wrong time-zone or date-column choice is not detected: the promised hour histogram does not exist and date columns fall back silently to created_at
WHERE: runner.py profile() (no hour-of-day output); docs/status/apsis-migration.md Q4 and runbook section 1 ("the profile's hour histogram"); mapping/columns.json sale_date / summary_date / valid_from / check_in_at / captured_at candidate lists; sql/reconcile.sql daily_money
WHY: The design's only way to find out whether vendor datetimes are UTC or Dhaka local is an hour-of-day histogram in the dry run. The profile code does not produce it, so the owner approves --source-tz with nothing to look at and the default (UTC) stands. The reconciliation cannot catch a wrong choice, because it converts the staging side with the same zone as the load. The route-day comparison with the vendor's summary would shift, but that section is hard-coded ok. Separately, the business-date column is picked as 'first candidate present', and the lists end in created_at: if the vendor's sale-date column has a name not in the list (the list has sales_date, transaction_date, visit_date, but not for example sale_date, order_date or date), the loader uses the row creation time as the business date without any message, because the required column 'sale_date' counts as found.
SCENARIO: The vendor stored Dhaka local time. Loaded as UTC, every sale and visit after 18:00 local moves to the next business date, month-end evening sales move into the next month, and the per-day and per-month history that reports compare against is wrong; reconciliation shows 0 differing days. Or: the date column is named differently, created_at is used, and sales synced a day late land on the wrong day, again with a clean report.

### BLOCKING upheld=3/3: Master matching: exact text only, facts must carry codes, and a total mismatch still passes
WHERE: sql/10_masters_map.sql (g.outlet_code = c.code, no trim or case fold); sql/20_fact_sales.sql and 21_fact_geo.sql joins; mapping/columns.json (outlet_code, sku_code, route_code required in the fact tables; canonical views are one-table projections in runner.build_views); sql/reconcile.sql control section; apsis_map.id_map keyed by code
WHY: Three linked gaps. (a) Codes are compared as exact text. Facts are trimmed, masters are not; nothing handles case (MySQL compares case-insensitively by default, our codes are case-sensitive text) or leading zeros (a code stored as a number in MySQL loses them). The design does not state a normalisation rule for codes at all. (b) The fact tables are assumed to carry outlet, SKU, route and user codes. A normal MySQL schema references masters by numeric id; the design itself writes 'apsis:master_outlets:<id>'. There is no way in the mapping to join a fact's vendor id to the master's code, so the sales step stops with 'missing column' and needs new code during the final-account run. (c) Unmatched rows are kept with their code and counted (good, nothing is dropped), but the count never fails the report: the design says 'no row with outlet_id IS NULL beyond the declared unresolved count', the SQL has no such limit. Unmatched rows have no scope ids and are visible to national roles only. Also outlets in our master with a NULL zone are left out of the lookup by the inner joins and are treated as not ours.
SCENARIO: Vendor outlet codes come as numbers without the leading zeros our October master data has (or in a different letter case). Every sales and geo row is loaded with outlet_id NULL; if route codes differ the same way, all scope ids are NULL. The reconciliation prints ok. Territory and division users see no history at all; only national users do.

### BLOCKING upheld=3/3: The name-based column drop removes non-personal data from the raw archives for good
WHERE: apsis_migration/staging.py PERSONAL and CRED patterns ("(^|_)name($|_)|_name$", "key", "hash", "contact", "address"); sql/25_raw_archive.sql; runbook section 4 step 6 (dump deleted after sign-off)
WHY: The promotion and target tables are archived as 'the full raw row as jsonb' so the programmes can be built from them later. But columns are dropped at staging by name pattern before the jsonb is made: any column ending in _name or containing name, key, hash, contact or address goes, for example promotion_name, gift_name, scheme_name, target_name, or a foreign key called outlet_key or sku_key. The archive is therefore not the full row, and after sign-off the dump is deleted. The dry run lists dropped columns, but the runbook only asks the lead to 'log' unexpected ones; there is no allow-list step for non-personal names.
SCENARIO: The owner asks for the Astha and gift programme history (in scope since 2026-11-12). The raw archive has promotion rows without the promotion or gift name and without any column whose name contains 'key'; the dump has been deleted, so the data must be requested from the vendor again.

LOWS:
- Privacy of logs: db.py raises the last line of psql's error output and runner stores it in apsis_ctl.chunk.error and prints it. For a failed COPY or a bad cast, PostgreSQL's last line is the CONTEXT line or the message with the offending value (for example a code or a date text). The claim 'errors print table, chunk and statement number only' is not true as coded. Names and phones are dropped earlier, so the leak is codes and raw values, into Log Analytics in the final account.
- Personal-data drop is by column name only. A column with personal content under another name (msisdn, cell, bkash, remarks, father, dob, retailer) is staged and, for the four raw tables, stored in jsonb. It stays inside the final database, but the statement 'this tool loads no personal data at all' is stronger than the code.
- Tables without a primary key: rows are keyed by the hash of the whole row, so two real identical rows become one. The collapsed count is not reported anywhere (rows_in is already the distinct count; the profile reports duplicates only when a primary key exists).
- Quantity: one global switch base/pack for all SKUs. With 'pack', a row whose SKU is not in our list is multiplied by 1 and stored as if it were base units, with no flag except sku_id NULL. Fractional quantities are rounded half up silently. No check that amount is close to quantity times price, which would show a wrong unit choice.
- Money: the conversion itself is exact decimal arithmetic, half away from zero, same rule in load and reconciliation. For float columns the dry run only lists them; there is no count of values that needed rounding below a milli-taka, and no comparison to a vendor-side total.
- Disk and duration statements do not match the code: stage_all stages every file completely before any transform, sales staging is kept until reconciliation, and loading is one process, not four in parallel. Peak staging is close to the whole dump as text plus three extra columns, not 4-6 GB. The 250 GB figure probably still covers it, but the estimates should be redone; nothing was measured.
- Each 50,000-row batch starts a new psql process for the COPY and another for the checkpoint (thousands of connections with TLS); DELETE by chunk_key runs without an index on chunk_key, so each month scans everything loaded so far.
- Changing --source-tz or --qty-unit between runs does not redo chunks already verified; the archive can hold a mix. The reconciliation (which uses the latest run's settings) would then fail, so it is visible, but the runbook does not say how to recover.
- History is attributed to today's geography (route to zone to territory as of load); past moves (request R1) are not kept, so last year's figures for a territory follow today's structure. This should be stated to report users.
- apsis_map.user_map is built but not used: facts keep user_code only, no user id, so history cannot be filtered or joined by user; lower() collisions between employee_code and username are resolved arbitrarily.
- A dump file cut off exactly between two INSERT statements parses without error; only the row count against the inventory (runbook section 1) catches it. Keep that check strict.
- dw.v_hist_visit_geo gives exact visit coordinates to web_ro and bi_reader, while the live fact_geo_fix was originally kept from those roles; decide on purpose.
- Load window and the live database: the runbook changes server-wide parameters and plans 12 hours 'outside selling hours'; a night is shorter than 12 hours. It should say plainly that the load runs before any user is live on that server, or on what terms it may run next to live traffic (WAL volume, replica lag with high availability).
- The status file says D-OWNER-FINAL-AZURE-01 is missing; it exists on origin/lane/lead-docs-1022 (DECISIONS.md).
- (demoted, upheld 0/3) Opening balances and carry-over are not named anywhere: dues, loyalty/Astha points, target achievement, stock: The design decides that history is an archive and that live dues, targets and loyalty never read it, but it never says what the live system starts with on cutover day. The live schema has the places for this (app.due_ledger documents an opening-balance entry; app.loyalty_ledger, app.astha_target, app.route_monthly_target exist), yet the design has no line for: outstanding outlet dues at cutover, loyalty/Astha point balances, month-to-date target achievement, stock. It also does not say that the 26-table list has no dues, collection or points table by name, so the source of those balances is an open owner question that is missing from Q1-Q15. The promotion and target tables are treated as deferred, but the owner put the SR programme screens (target and achievement, Astha, outlet points, gift redemption) in scope on 2026-11-12, six days before this lane started, so the 'deferred' basis is out of date. @ docs/status/apsis-migration.md section 5 (only sentence: "anything computing today, dues, targets or loyalty do not include history"); section 3 rows 3, 7, 17, 18 ("deferred ... no behaviour built", R6 "only when the owner un-defers targets"); docs/runbooks/apsis-history-migration.md (no step)

## tooling-migrations-tests verdict=fail
SUMMARY: Read-only review of origin/lane/apsis-migration at 8a637747 (29 files, all under tools/apsis-migration, docs and DECISIONS.md). Nothing was built or run.

What is good: row values never become SQL (COPY with correct escaping, quoted psql variables); numbers stay text until exact numeric rounding, no float in money; each month is deleted and re-inserted in one transaction with deterministic UUID v5 keys, so re-runs do not double; a crash between a write and its checkpoint only re-stages rows that are later de-duplicated; .gz is streamed; fixtures are synthetic; reports and normal logs carry counts only; DECISIONS is append-only; the landing request uses managed identity and no keys.

Verdict fail, six blocking items:
1. The history views sit in schema dw, where the existing grant map gives api_rw SELECT and worker_rw full write on everything; the next migration that calls app.apply_db_role_grants() opens history to the sync roles and makes it writable through the simple views. The lane's own privilege test passes only because V0262 is last.
2. Staging tables are UNLOGGED while checkpoints are logged; after a database restart or failover a resume skips statements or transforms empty months, and the tool still reports 'reconciliation ok'. No check ties staged rows to rows parsed from the dump.
3. The runbook drops the staging schema one step before the reconciliation that reads it.
4. The table name taken from the dump, and the file name, are pasted into SQL unchecked; a crafted name runs arbitrary SQL as the migration role.
5. The job role apsis_migrator and its rights are described only in prose; no migration or runbook step grants them, and 'masters untouched' is proven only by tests run as the database owner.
6. A zero date in a promotion or target table aborts the raw-archive step on every run.

At landing the lead must also renumber the three migrations, bump the dw view contract, give the v_hist views is_effective and data_origin and dictionary comments, and add the views to the grant map exceptions. The design document claims several things the code does not do (time-zone histogram, deleted flag, parallel load, v_sales_with_history).

### BLOCKING upheld=3/3: History views become readable (and writable) by the sync roles at the next migration that re-applies grants
WHERE: tools/apsis-migration/provisional-migrations/V0262__apsis_dw_views.sql (views in schema dw) against db/migrations/V0014__database_roles.sql (app.db_role_grant, app.apply_db_role_grants) on the integration branch
WHY: The grant map has ('api_rw','dw','*','SELECT') and ('worker_rw','dw','*','SELECT, INSERT, UPDATE, DELETE') with no exceptions. app.apply_db_role_grants() revokes and re-grants on every table and view in app and dw, and almost every later migration calls it (V0188, V0191, V0192, V0193 ...). V0262 puts the history views in dw, adds no except_tables entry, and does not call the function, so the lane's test (api_rw/worker_rw/jobs_rw have no SELECT on dw.v_hist_sales_line) only passes because V0262 is the last migration in the test. dw.v_hist_sales_line, v_hist_visit_geo and v_hist_attendance are simple single-table views, so they are auto-updatable: worker_rw's INSERT/UPDATE/DELETE on the view reaches apsis_hist through the view owner's rights. Separately, the existing map keeps fact_geo_fix and fact_attendance away from web_ro and bi_reader as 'PII facts', while V0262 grants the history equivalents (coordinates; user code with check-in times) to both.
SCENARIO: V0262 lands; the next train migration creates a table and calls app.apply_db_role_grants(). api_rw can now SELECT all history through dw.v_hist_*, and worker_rw (and jobs_rw, which is a member of worker_rw) can DELETE or UPDATE archive rows through dw.v_hist_sales_line. The stated rule 'no grants to the runtime roles, the sync engine cannot read history, by privilege' is silently gone, and no test notices because the lane test never calls apply_db_role_grants() after V0262.
