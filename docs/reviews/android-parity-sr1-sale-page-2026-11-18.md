- Flaky SppConnectorTest.aHangingConnectIsClosedAtTheTimeoutAndTheNextMethodIsTried. I could not see the failure text, so this is from reading the code, not a proven cause. The test mixes two clocks. The 300 ms attempt timeout runs on runTest virtual time, which skips ahead as soon as the test thread is idle. The hanging `connect()` runs on a real pool thread, and `TestIo` decides inline versus thread with a shared `@Volatile onThread` that every `create()` overwrites (the INSECURE create sets it back to false). So the virtual timeout can fire before the pool thread has even entered `connect()`, or while it is blocked, and which one happens depends on the machine. It also asserts a wall-clock `ms < 5_000` on the same run. Smallest robust fix without loosening any assertion: give FakeSocket an `entered` CountDownLatch counted down at the start of the hanging `connect()`. Run the call as `val job = async { connector.connect(...) }`, then `runCurrent()`, then `entered.await(5, SECONDS)` (a real wait for the thread to be blocked), then `advanceTimeBy(301)`, then `job.await()`. That fixes the order every run, so the timeout always lands on a really blocked connect and `close()` is what unblocks it. Make the dispatch choice per socket instead of the shared flag, or reset `onThread` only after the hung attempt has finished, and drop or widen the wall-clock bound. The same shared-flag pattern is in `cancellingTheCallerClosesTheSocketAtOnce`, which has a real 200 ms `withTimeoutOrNull`.
