### BLOCKING upheld=3/3: B1 only half closed: upload and bundle request are still not single-flight, so a batch acknowledged while a bundle request is in flight is counted twice
WHERE: android/core-sync/.../BundleDownloader.kt fetch() (requestedAt = iso(clock.nowMs()) before api.bundle; own instance Mutex `lock`) vs android/core-sync/.../SyncEngine.kt run() (separate per-user Mutex lockOf(userId)); callers outside the sync worker: app-sr SrDay.downloadBundle (day start), SrDay.launchDeltaRefresh, SessionModule ConnectivityFlush.pullIfStale, push/PushPull.kt. Contract: contract/slices/schemas/ProgrammesSection.yaml ACHIEVEMENT RULE on origin/claude/wonderful-thompson-k6ejnf. Server: backend/sync/.../BundleService.kt (programmes read in one REPEATABLE READ snapshot late in the build, built on request). DECISIONS.md D-LEAD-CONTRACT-115-01 and D-LOY-API-14 both say this is open for the Android lane.
WHY: The contract's phone rule has two parts: (a) add the memos not acknowledged when the request was SENT, and (b) 'the phone never uploads records while a bundle request is in flight (single-flight sync), and if an acknowledgement arrives during the request it discards the section's achievement and refetches'. Round 3 does (a) only. The server's figure holds every memo COMMITTED when it reads the programmes snapshot (status active, sale kind, business month), which is after the request was sent. The sync engine and the bundle downloader take different locks, and the day-start download, the foreground delta (which becomes a full bundle on 410) and the reconnect pull run outside the sync worker. So a batch can be committed on the server before the snapshot and acknowledged on the phone after requested_at: it is inside the server figure AND 'acked after the request' -> added again. Nothing in the lane detects an ack that arrived during the request. The status file says 'B1 done' and does not mention this gap.
SCENARIO: SR sold 40 memos offline yesterday evening (same month) and did not sync. Morning, phone gets signal, SR opens the app: day start sends the bundle request (requested_at = 08:00:00.000) and at the same moment the connectivity flush / sync worker uploads the 40 memos. Server commits the batch at 08:00:00.300, reads the programmes snapshot at 08:00:00.600 (figure includes the 40), phone handles the ack at 08:00:00.900 (acked_at > requested_at). Bundle is applied. Astha page: the 40 memos are added on top of a figure that already holds them: STD, value and memo count of those outlets doubled. It stays so until the next full bundle (after the next synced sale forces delta -> 410 -> full; all day if the SR stays offline). Same race mid-day whenever a sync upload overlaps a foreground or reconnect bundle fetch. Fix direction: take the per-user sync lock around the bundle request (or record that an ack landed between requested_at and apply and then drop the phone's additions / refetch).

### BLOCKING upheld=3/3: A memo edited twice before the next bundle: the original stays in the server figure and the second edit is added on top (counted twice)
WHERE: android/feature-programmes/src/main/kotlin/com/aktcl/aron/feature/programmes/AsthaLocal.kt delta(): `addedSupersedes = add.mapNotNull { it.supersedes }` then `out = live.filter { it.uuid in addedSupersedes && insideServerFigure(...) }` (one step only, the chain is not followed). Edit of an edit is allowed: core-database CaptureRepository.kt ~l.188 only refuses a target that another memo already supersedes; SrSaleKit.kt l.330 treats the edit memo as live/editable.
WHY: The take-back only looks at the memo the counted memo supersedes directly. With a chain M <- E1 <- E2, where M is inside the server figure (acked at or before requested_at) and E1 is not (still local, or acked after the request), the code adds E2, looks at E1 for the take-back, finds it is not in the server figure, and takes nothing out. M is never removed although the server figure holds it. No test covers a chain.
SCENARIO: 10:00 memo M (10 packets) sold, synced, full bundle refreshed: figure holds M. SR goes offline. 10:30 edits M to 12 packets (E1, pending). 10:40 edits again to 8 packets (E2 supersedes E1, pending). Astha page for that outlet: server 10 + E2 8 = 18 packets, value and memo count likewise (memo count 2); the right figure is 8 and 1. It stays wrong until E1/E2 are synced and a new full bundle is applied. Same result when E1 was acked after the request and E2 is pending. Fix: walk the supersedes chain down to the first memo inside the server figure and take that one out.

Needs a wrong wall clock and the bundle request being the first server answer after boot; the business date would be wrong too in the bad case. Not blocking, but the comparison trusts one clock across boots.
