## bundle-correctness-and-scope verdict=pass
SUMMARY: Read-only review of git diff 038e3121..4cdece42 (nothing built or run). No blocking defect found.

What I checked and found correct:
(1) Quarter rows: the quarter is AsthaQuarter.of(date, cfg.astha.quarter_start_month), the same function the gift assignments and the gift_choice ingest use, and the phone lane's label formula matches it. Current month is queried first with the whole bound, then the other months with what remains (limit remaining+1); a month that overflows is cut and named, later months with any row are named too; rows are emitted in month order. Achieved figures for each month are all active, non-voided, non-superseded sale memos with a business date in that month at the snapshot, so closed months and late memos are right. The size test still asserts the docs/04 budget, including at the 1,000-row cap.
(2) tier_code comes from programme_enrolment valid at the bundle's business date, same table and date rule as GiftChoiceRecords; the exclusion constraint guarantees one enrolment per outlet and programme at a date, so adding tier_code to the GROUP BY cannot double a row; null when the enrolment names none; only outlets of the caller's own bundle.
(3) user.geography is read on the server from the user's home zone (else first route's zone), inner joins on NOT NULL parents, name/code NOT NULL, name_bn nullable in DTO and contract; null when no zone.
(4) Inactive-brand names: LEFT JOIN on the product node primary key, members put only when the brand is not active; absent otherwise.
(5) Digest/ETag: the content digest is over the whole serialised Bundle minus meta, and the delta fingerprint 'rest' includes both 'user' and 'programmes', so tier, new targets, truncated months and geography renames force a refetch. No wall-clock value was added; astha_as_of is the newest memo ingest among sent outlets over the quarter (Dhaka start of the quarter when none), so it moves only when a memo of the quarter arrives.
(6) Worker prebuild and prefetch go through the same BundleService.bundle path, so they carry the same members.
(7) Old phones: every new member is optional or nullable with defaults (BundleUser.geography default null in backend and shared WireDtos; new section members are extra keys); Android WireJson and the bundle reference readers on the integration branch set ignoreUnknownKeys = true, and no integration-branch Android code parses astha_targets, so a 1.19/1.20 app is unaffected.

Not verified: tests were not run; the 300 KB / 32 KB figures were not measured; query plans at fleet size were not measured; the full contract/openapi.yaml was only spot-checked against the slices (version 1.22.0, new schemas, no new required members on existing schemas); how the phone lane uses astha_truncated_months (it currently reads only astha_truncated) was not reviewed in depth.

LOWS:
- Quarter offline view is thin at realistic size. The one bound of 1,000 rows fills the current month first. The size test's own realistic SR (120 outlets x 7 rows) uses 840 rows for the current month, so the other two months of the quarter get only 160 rows and are always named in astha_truncated_months. The quarter and month chips therefore work fully offline only for small routes (about 47 outlets at 7 rows a month). This follows the lead ruling (one bound, budget unchanged) and is never silent, but the phone lane must really read the named months online; say so in the status doc. (BundleProgrammes.section, backend/sync/.../BundleProgrammes.kt)
- ProgrammesBundleSizeTest asserts the docs/04 budget (300 KB raw / 32 KB gzip) for the current-month-only case and for the capped 1,000-row case, but not for a realistic three-month quarter. The cap case covers the worst row count, so the budget holds by construction; a quarter-shaped realistic case would make that explicit.
- Past-month rows can be missing without the month being named. asthaTargets filters on route_id = today's routes and on outlets enrolled at the bundle's business date. An outlet whose enrolment ended earlier in the quarter, or whose earlier-month target row still carries its old route (outlet moved route and no re-upload), sends no row for that past month, while the contract says 'a month not named here is complete'. Edge case; the online read (listAsthaTargets) has the same route filter.
- When the current month alone overflows the bound, the two other month queries still run their full memo aggregation only to return one row (limit 1) to learn the month has rows. Wasteful per bundle build for an over-bound user; a cheap EXISTS on astha_target would do. Indexes used are fine otherwise (memo (outlet_id, business_date), astha_target (month, route_id, ...), product_node primary key).
- Bundle build now runs three month queries plus the quarter-wide as_of read instead of one month: about three times the memo read for the Astha part per SR bundle. Read on the primary inside the REPEATABLE READ snapshot. Looks acceptable at pilot size; not measured at fleet size.
- Quarter start month: the bundle uses the SCOPED config value (cfg.astha.quarter_start_month through the user's chain), GiftChoiceRecords uses the GLOBAL value. If someone sets a scoped override, the bundle's quarter months and gift_assignments quarter differ from what the gift_choice ingest calls the open quarter. Existing before this push, but the quarter rows now also depend on it. The phone lane computes labels with a default start month of 1 and the same formula as AsthaQuarter.of (label year = year of the quarter's first month).
- user.geography for a user with no home zone uses the first route of the day (ordered by route id, so stable within a day). A user with routes in two zones and no home zone may see a different chain on different days, and each change forces a full bundle refetch (user is in the delta 'rest'). A TSO or other user with no home zone and no route that day gets null. Only the user's own or own-route zone chain is read; no other names leak.
- tier_code: the bundle sends it only where the loyalty entry exists (programme scope applied per outlet); GiftChoiceRecords does not apply that per-outlet programme scope. The phone is therefore at most stricter than the server (it offers fewer gifts, never one the server refuses for tier). Null tier: phone offers only untiered gifts, server accepts those. Consistent.
- astha_truncated changed meaning slightly for a pre-1.22 reader: true can now mean only another month of the quarter was cut while the current month is whole. No Android code on the integration branch reads astha_targets or astha_truncated yet, so no shipped phone is affected.
