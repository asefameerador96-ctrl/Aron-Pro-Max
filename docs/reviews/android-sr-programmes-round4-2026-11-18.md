### BLOCKING upheld=3/3: B1b is closed for overlapping requests, but not for a lost or late acknowledgement: a batch the server stored before the snapshot whose answer never reached the phone is still counted twice

Contract rule: contract/slices/schemas/ProgrammesSection.yaml l.15-23.
WHY: The lock only orders what the PHONE sees: an upload call that ended and a bundle request. It cannot order what the SERVER did. When the upload answer is lost (timeout on weak signal, app killed mid-upload), the server may have committed the batch, the sync run ends with the rows still in_flight and the lock is released. The waiting bundle request then goes out: the server figure holds those memos, the phone still sees them as not acknowledged and adds them. When the batch is replayed later the ack time is after requested_at, so they stay added. This is the same outcome the lead held blocking in round 3 (committed before the snapshot, acked after requested_at), reached by a path the lock does not cover. The contract's second half ('if an acknowledgement arrives ... discards the achievement and refetches') was not built; the lane chose the lock instead of detection. No test covers a timed-out batch followed by a bundle. Honest limit: the contract rule itself is worded around 'acknowledgement sent', so part of the fix may belong to the contract or server (the lead may demote); the loyalty balance errs on the safe side in the same case (subtracted twice, understated).
SCENARIO: Morning, weak signal. The SR has 40 unsent memos of this month from last evening. Sync worker uploads the batch; the server commits it at 08:00:20 but the answer is lost and the phone times out at 08:00:45 (rows stay in_flight, run ends, lock free). The day-start download was waiting for the lock: requested_at = 08:00:45, the server snapshot already holds the 40 memos, bundle applied. Astha page: 40 memos in the server figure plus the same 40 added as 'still on the phone': STD, value and memo count doubled. At 08:02 the retry is answered (duplicate/accepted), acked_at 08:02 > requested_at, still added. No programme figure changed on the server since the snapshot, so the after-sync delta gets no 410 and no new full bundle: it stays doubled until another sale is synced and a full bundle is fetched. Fix direction: when a batch that was already sent once before the held requested_at is acknowledged (a replayed persisted batch, or ack status duplicate), drop the phone's additions for those memos or force one full bundle refetch; add a test with a timed-out batch followed by a bundle.
