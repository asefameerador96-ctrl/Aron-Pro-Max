# Lead review: SR QC two-step rebuild (bd03a20e..fa03bcab)

Reviewed 2026-11-18 by the lead (Opus lens, three refuters per blocking finding). Read from code only: nothing built, run or walked on a device.

## verdict=fail
SUMMARY: Read-only review of bd03a20e..fa03bcab (QC two-step, SR). Money and quantity maths are unchanged: qcMax is an exact copy of the one-scroll formula, totals and settlement use the same integer expressions, the confirm calls the same onDone, AMO keeps its screen (twoStep default false, only the SR host turns it on), strings are in both languages, goldens are add-only, and the slice does not collide with train 118's gate code (one hand merge on SaleRoute's last line from an earlier slice). Two defects stop it: (1) on a locked QC the new step-2 বাতিল calls onQty without the locked guard; SaleDraftOps.setQc throws when QC is completed and the view model does not catch it, so the app crashes when a rep looks at a submitted QC and taps Cancel; (2) the claimed kill-and-relaunch survival is only true for QcScreen in isolation: in the real route the stage is not saved and unsubmitted QC is dropped on restart, and the saved `selected`/`opened` can come back later, opening step 2 unasked and letting Cancel write stale quantities back (read from code, not run). Both are small fixes in the composable. Tests drive real composables but with lambdas, so neither defect is visible to them. Nothing was built or executed here.

### BLOCKING upheld=3/3: বাতিল on step 2 of a LOCKED QC writes to the draft and crashes the app
WHERE: android/feature-sale/src/main/kotlin/com/aktcl/aron/feature/sale/ui/SaleExtraScreens.kt, QcTwoStepScreen, the step-2 AronSecondaryButton(qc_cancel) lambda (calls onQty for all six fault codes with no `if (!locked)` guard); reached through SaleRoute.kt onQty -> SaleViewModel.setQc -> SaleFlow.setQc -> SaleDraftOps.setQc `check(!d.qcCompleted)`
WHY: Every other write on the page is guarded by `if (!locked)` (the quantity boxes) or hidden (Delete), exactly as on the one-scroll screen. The new Cancel is not. SaleDraftOps.setQc throws IllegalStateException("QC is locked once completed") when qcCompleted is true, and SaleViewModel.setQc runs it in a bare viewModelScope.launch with no handler, so the exception is uncaught and the process dies. The locked page is reachable: after QC is submitted the Review still shows the QC button (onQc is only null for an edit), step 1 tiles stay tappable when locked, and the locked step-2 golden (srp1b_qc_step2_locked) shows সংরক্ষণ and বাতিল as the two ways out. QcTwoStepTest's locked test never taps Cancel, and its onQty is a no-op lambda, so it cannot see this.
SCENARIO: SR sells, opens Product QC, enters faults, taps QC জমা দিন -> হ্যাঁ (QC now locked). Back on Review the rep taps প্রোডাক্ট QC again to look at what was entered, taps a pack tile, then taps বাতিল to leave the page. Six vm.setQc calls run, the first throws inside the coroutine, the app crashes in the middle of a call with an unsaved sale. Fix: in the Cancel lambda do nothing but `selected = null` when locked (or hide বাতিল's restore when locked). Note: the step-1 বাতিল has the same pre-existing fault through vm.restoreQc -> replaceQc check(!qcCompleted) (also on the AMO screen, not introduced here); worth fixing in the same pass.

### BLOCKING upheld=3/3: "Survives kill and relaunch on step 2" is not true in the real route, and the saved step-2 state can come back stale and write old quantities
WHERE: SaleExtraScreens.kt QcTwoStepScreen (`selected` and `opened` are rememberSaveable) versus SaleRoute.kt (`var stage by remember`, `qcBefore` by remember, not saveable) and SaleFlow.start -> SaleDraftOps.sanitizeQc (QC that was never submitted is dropped on every start)
WHY: The slice's proof (theOpenSkuSurvivesAKillAndRelaunch) restores QcScreen alone. In production, after a process death SaleRoute starts again at SaleStage.Entry and SaleFlow.start drops all unsubmitted QC rows, so the rep is NOT returned to step 2 and the typed values are gone (that part is the existing, intended rule; D-PAR-SR1-23 says the opposite: "survive a kill and relaunch; the quantities themselves live in the sale draft as before"). Worse, the two rememberSaveable values were written to the saved instance state while step 2 was open, and the call site is the same after relaunch, so when the rep next opens QC the restored `selected` and `opened` are consumed: the screen opens straight on the old SKU's step 2 with an `opened` string that describes a draft that no longer exists.
SCENARIO: Rep enters 5 damaged on SKU A, সংরক্ষণ, taps SKU A again (opened = "damaged_crushed=5;..."), the phone kills the app in the background (2 GB phone). Relaunch from recents: sale is on the entry list, the draft's QC is empty (sanitizeQc). Rep goes Review -> প্রোডাক্ট QC: instead of step 1 the page opens on SKU A's entry with all boxes empty; the rep taps বাতিল to get out, and the lambda writes damaged_crushed=5 back into the draft, a quantity and settlement the rep did not enter in this session. I read this from the code (Compose keeps restored values until the same key composes); it was not run on a device or in a route-level test. Fix: reset selected/opened when the QC stage is entered (key them on something SaleRoute owns, or hoist them), and correct the DECISIONS text; a route-level restoration test (SaleRoute, not QcScreen) would prove either way.

# Review of the QC-locked sale crash fix (e017b2d7..c48337db), 2026-11-18. Opus lens. Read from code only.

## verdict=pass
SUMMARY: Read-only review of git diff e017b2d7..c48337db (origin/lane/android-parity-sr-1 is at c48337db). No blocking defect found; lows listed.

(1) Handler. The 11 guarded launches are start, setQuantity, setSlide, setQc, setPaid, confirmZeroSale, startQcOnly, cancelQcOnly, restoreQc, completeQc, beginEdit(withEdit). The commit is NOT one of them: Review's Print goes vm.onPrintTapped -> SaveAndPrint -> SaleCommitStep -> flow.commit in viewModelScopeForDialogs(), with its own handling (ReviewNotCommittable, ui.refusal, refusalText, SaveAndPrintDialogs), all untouched. A failed save therefore cannot be turned into the small banner. CancellationException never reaches a CoroutineExceptionHandler, and the try/catch in editLocked wraps only the non-suspending change lambda. Other exception types are rethrown from the handler. The one place where a real error is now hidden is start() (low 1).

(2) editLocked. Nothing is written on a refusal (the catch returns before review, store.save and the state publish), the draft object is the same, only notice is set. setQuantity and setSlide are single-step changes; DRP reward packs are only read to cap the quantity. The only multi-step caller is withEdit (catalog give-back before the refusal), on a state I could not reach (lows 3, 4).

(3) Forced Review. Derived from draft.qcCompleted, only Entry and Slide are remapped; Credit and QC (read-only when locked) still open and return to Review; Save/Print, the SR 'no sale' button and the host Back handlers are outside the route and unchanged. QC-only sale ends on Review anyway. Edit drafts cannot be locked (QC is not offered on an edit, the edit gate refuses a memo with QC). AMO uses the same SaleRoute and gets the same behaviour (Review instead of the entry list after a locked QC, plus the banner); no screenshot test composes SaleRoute.

(4) QcDropped. Set only when the loaded draft had QC rows, was not submitted and sanitizeQc removed them; kept across a second start of the same visit; cleared by the next accepted change (editLocked publishes a fresh state); a new process shows it on its first start because the drop happens then.

(5) Money path. SaleCommitter, SaleReview*, SaleDraftOps, SaleSaveAndPrint, PrinterUi: zero diff. In SaleFlow the commit, review and stock code are unchanged; only start (notice), editLocked and noteRefusal changed.

(6) Tests. QcLockedFlowTest: additions only (+6), real SaleFlow, asserts draft equality. SrSaleLockedRouteTest: real SaleRoute, real SaleViewModel, StateRestorationTester, asserts draft equality and the notice; its test (b) covers the deleted SrQcRouteRestoreTest's property. SrQcRouteRestoreTest and QcLockedFlowTest are not on integration 4d310d8c0 (lane's own). No other test file is touched. Gap: the view-model guard itself is untested (low 2).

Files: android/feature-sale/src/main/kotlin/com/aktcl/aron/feature/sale/domain/SaleFlow.kt, .../ui/SaleViewModel.kt, .../ui/SaleRoute.kt, android/app-sr/src/main/kotlin/com/aktcl/aron/sr/SrSaleKit.kt (beginEdit), android/app-amo/src/main/kotlin/com/aktcl/aron/amo/AmoSaleKit.kt (beginEdit).

LOWS:
- The net is broad for start(): flow.start does file and Room reads, and any IllegalStateException or IllegalArgumentException there (check(visit.canSell), Room's own ISEs such as a closed database or a missing migration, a serialization error) used to crash and now becomes the banner 'That change was not accepted. Nothing was changed.' over an empty entry list with no draft. The rep cannot sell, gets misleading words, and no crash report is produced. Suggest keeping the guard off start(), or narrowing it to a dedicated draft-refusal exception type.
- The guard is not exercised by any test. In SrSaleLockedRouteTest the locked quantity and slide changes are refused inside SaleFlow.editLocked, so no exception ever reaches the CoroutineExceptionHandler; QcLockedFlowTest calls noteRefusal() directly. Neither 'ISE/IAE becomes a notice' nor 'any other exception still crashes' (the handler rethrows, which should reach the thread's uncaught handler) is proven at view-model level.
- SrSaleKit.beginEdit and AmoSaleKit.beginEdit call flow.start / flow.setQuantity / flow.withEdit directly, not through the view model. If the stored draft of that visit were a QC-locked sale draft, the seeding used to throw and now is refused silently line by line, withEdit is refused too, and the edit host then shows Review of the locked non-edit draft with the edited memo's stock given back in the catalog. I could not build a reachable path to that state: the draft is cleared at commit, a landed draft still throws 'sale already committed' as before, and the edit gate refuses a memo with QC. A Save there would also be refused by SaleCommitter ('a fix is only for an edit') and go to the normal save-failed dialog, so no wrong memo is written. Worth an explicit check in beginEdit that draft.edit is set after withEdit.
- SaleFlow.withEdit updates the catalog (give-back) and givenBackFor before editLocked; with the silent refusal on a locked draft that partial change now stays in the state instead of ending in a crash. Same unreachable case as above; the commit transaction re-checks stock, so it is display only.
- SaleFlow.setQuantity returns the requested quantity (5 in the test) when the change was refused, while its KDoc says it returns the quantity actually set. No caller uses the return value today (the view model and both beginEdit ignore it); return the draft's quantity or 0 on a refusal, or fix the KDoc.
- On a locked sale the Review's Slide button (only present when a SKU has a DRP offer; offers are deferred) sets stage = Slide, which is mapped back to Review: the button does nothing and says nothing. Hide it when the draft is locked.
- editLocked turns ANY IllegalStateException from the change on a locked draft into 'Locked', including ones that are not the lock (confirmZeroSale's 'a zero sale has no lines'). Harmless today because Entry is no longer shown on a locked draft, but the notice could name the wrong reason.
- noteRefusal() reads and writes ui.value outside the flow's mutex. Everything runs on the main thread today (viewModelScope and LaunchedEffect), so I see no lost update, but it is not protected by construction.
- A Locked notice can never be cleared on a locked sale (no change is accepted any more), so the banner stays above Review, Credit and QC until the save. Acceptable, just noting it; the QC screen also shows its own qc_locked line, so the text can appear twice there.
- Bangla qc_dropped_notice ends 'আবার QC খুলে দিন', which reads as 'open QC again (for someone)' and not 'open QC again to enter it'; 'আবার QC খুলে লিখুন' is closer to the English. sale_change_refused Bangla is fine. Both keys are present in values and values-bn, and qc_locked already existed in both.
- Not verified: nothing was built or run here, so compile, the new tests passing, the 'tests bite' claims in DECISIONS, and 'AMO/TSO goldens unchanged' are read from code only. No screenshot or golden test composes SaleRoute (only SrSaleLockedRouteTest does) and the banner shows only when notice is non-null, so I see no reason for a golden to change. Not walked on a device.
