### BLOCKING upheld=3/3: The API console query silently drops the API's own database ERROR lines, so the new section can show "no errors" while the API is failing
WHERE: infra/scripts/diagnose.sh line 152 (the exclusion `where not(line matches regex ...statement|parameters|bind|password|secret|token...)`), applied to the RAW console line before line 154 projects formattedMessage
WHY: The API logs one JSON object per line (backend/app/src/main/resources/logback.xml, logback JsonEncoder) and the stack trace is a field of that same object. The exclusion runs on the whole raw line, so it also matches class names inside the stack trace and words in the message, although only level + logger + formattedMessage is ever printed. Http.kt line 175 logs "statement timeout request_id=..." (the word statement is in the message itself) and line 178 logs "unhandled error request_id=..." with the exception; any exception that passed through Jdbi (package org.jdbi.v3.core.statement) or the PostgreSQL driver (PgStatement / PgPreparedStatement) has "statement" in its stack. A database login failure carries "password authentication failed". All of these are dropped with no trace and no count of dropped lines. This is the safe direction for secrets, but it defeats the stated purpose of the change (read the API's ERROR lines).
SCENARIO: A request hits a SQL error in dev. The API logs ERROR aron.error "unhandled error request_id=..." with a stack that contains org.jdbi.v3.core.statement.Query. The operator dispatches ops-diagnose for that window. Line 152 drops the row because the raw JSON contains "statement"; the API section prints only start-up lines, and the operator concludes the API logged no error. Same for every statement-timeout line. Fix: apply the exclusion to the projected text (the 200 characters that are actually printed), not to the raw line, and print how many lines the exclusion dropped.

LOWS:
- Redaction runs AFTER truncation (KQL substring 200/240/300, then cut, then redact). I ran the sed block on synthetic lines: an e-mail cut before its top-level domain prints its local part and partial domain; a long token cut to under 40 characters prints whole; a phone number cut short prints its first digits. key=value, JWT and Bearer still match after a cut. Fix: fetch the longer line, redact, then cut in the shell.
- Phone pattern gaps (tested): dashed (01712-345678), spaced (+880 1712 345678, 017 1234 5678), 10 digits without the leading zero, a number glued to a preceding letter (no word boundary), and Bangla digits are all printed unchanged. Only the plain 01XXXXXXXXX, 8801XXXXXXXXX and +8801XXXXXXXXX forms are caught.
- Names are only partly covered, yet the script comment and D-OPS-DIAGNOSE-API-01 say names are redacted. `name=First Second Third` keeps everything after the first word; `outlet_name=...` likewise; a name or username in free text (`user x.y logged in`) is not touched. Only the JSON "name":"..." form is fully redacted. The wording should say so.
- Not caught at all (tested): otp=..., OTP followed by digits, cookie / Set-Cookie values, pin=..., IP addresses, device UUIDs, memo numbers that embed a username, usernames in a path or query string. The lens list names otp and cookie; neither is in redact() nor in the KQL exclusion. Today's API log statements that I read (107 info/warn/error calls) log ids, pseudonyms and exception class names only, and the request line uses the route template with hashed user and device, so I found no current line that would leak these; the net is simply thinner than described.
- The comment says request lines are not kept, but the include filter (line 151) runs on the raw JSON line with very broad words (config, application, worker, schema, started). Request lines for /config/delta, /config/public and /admin/config/* contain "config" in the route and are INFO lines from aron.request, so they pass. They carry no personal data (route template, hashed user/device), but with newest-first and a cap of 150 a busy window can push the start-up lines and older errors out of the output. The thread name is also in the raw line, so any line logged from a thread named ...-worker-N would pass too (not verified which thread names the API uses). Fix: match the include words on logger + message, and exclude logger aron.request.
- Only the new output goes through redact(). The existing sections are unchanged and unprotected: the migrate job console (line 91, every line of the job, 400 characters, no filter), the job/worker system log (line 99), the PostgreSQL log (line 114) and the worker console (line 135). Pre-existing, not introduced here, but the same public job log.
- api_app is put into the KQL string unvalidated (`where app == '$API_APP'`), like the existing job_prefix, worker_app, since and until. No shell injection (passed through env and quoted arguments). A quote in the input can change the query and remove the filters; only someone with write access can dispatch, and the output still passes redact(). Validate all five inputs against a fixed pattern (for example ^[a-z0-9-]{1,60}$ and an ISO timestamp pattern) in the workflow or at the top of the script.
- redact() has no behaviour test: infra/tests/check_infra.py only checks that the marker strings exist and that the three new az query lines contain `| redact`. A small test that pipes sample lines through the function would have caught the gaps above.
- redact() is line-based; a value split across two output lines (a multi-line field, if az tsv does not escape newlines) would escape the JSON and key=value patterns. Container Apps console rows are one line each, so this is unlikely.
- The pre-flight query prints the first 300 characters of the RAW JSON line (not formattedMessage), unlike the API console query; contents are ids, zone codes and counts by design of MigrationPreflight, so no data, just noisier.
- Over-redaction costs some diagnostic value: any run of 40+ letters/digits/slashes (long file paths, long class paths without dots) becomes [long-token], and `key:`/`name:` anywhere blanks the next word.

### BLOCKING upheld=3/3: The held-back filter almost certainly never fires: az prints the flag as "True", the script compares with "true"
WHERE: infra/scripts/diagnose.sh line 198 (awk: NF >= 3 && $2 == "true"), fed by the KQL column `dropped` on lines 194-197
WHY: The API console query marks secret-word lines with a boolean column `dropped` and the shell is meant to hold those rows back and count them. The az log-analytics command turns every cell into text with Python str() (azext_loganalytics/custom.py: `item[column_names[index]] = str(value)`), and the tsv writer (knack output.py, _TsvOutput._dump_obj) also uses str(). A boolean therefore arrives as `True` / `False` with a capital letter. The awk test is for lowercase `true`, so no row is ever held back, every flagged row is printed, and the count line always says 0. I could not run az here (not allowed, not installed); I read the az source and ran the same awk program on made-up rows: a row flagged `True` was printed and not counted. The only residual doubt is whether the Log Analytics API returns a JSON boolean for a bool column, which is its normal behaviour. No test covers this path. Fix: compare case-insensitively (tolower($2) == "true"), or project a string from KQL (iff(..., 'held', 'shown')), or filter and count in KQL; add a test that feeds the awk step sample rows.
SCENARIO: The API container fails to start and the JVM prints a plain (non-JSON) line holding a secret in free text, for example "... the password is <value>" or a library line "otp_code=<digits>". The KQL marks it dropped = true. az prints `True`. awk does not match, so the line goes to the public job log; the redaction net does not catch these forms (see lows). The log then ends with "(0 line(s) held back ...)", which tells the lead the exclusion found nothing.

### BLOCKING upheld=3/3: A line cut in the middle of a non-ASCII character kills the output filter; everything after it is lost and the step stays green
WHERE: infra/scripts/diagnose.sh line 41 (show: redact | cut -c1-N), line 63 (exec > >(redact)), line 21 (perl -CSDA); also line 110 (awk substr on server log files, byte-based with mawk on Ubuntu)
WHY: GNU cut 9.4 (the version on ubuntu-24.04 and here) cuts by bytes, also in a UTF-8 locale. When the cut lands inside a multi-byte character (any Bangla letter, a long dash, a curly quote, an arrow), the half character reaches the second, script-wide redact. Perl with -CSDA stops with "Malformed UTF-8 character (fatal)". After that the script writes into a closed pipe and is killed; in the workflow the pipeline's status is that of tee, so the step is green and the step summary is the truncated file. I reproduced this in redaction mode only: a made-up line with a dash, cut with `--redact 34`, then piped with two following lines through `--redact`: the first line printed, the cut line and both later lines were lost, exit codes 0 0. The lane's own boundary test only uses ASCII. Fix: cut by characters inside perl (substr after decoding) or make the filter tolerant of bad bytes so it can never die; add a test with a Bangla line cut mid-character followed by more lines.
SCENARIO: The migrate job fails on a data guard and the exception text in the raw console line holds a Bangla outlet name ("Key (name)=(...)"), which is exactly when the lead runs this workflow.
