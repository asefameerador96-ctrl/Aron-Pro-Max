### BLOCKING upheld=3/3: The API console query silently drops the API's own database ERROR lines, so the new section can show "no errors" while the API is failing
WHERE: infra/scripts/diagnose.sh line 152 (the exclusion `where not(line matches regex ...statement|parameters|bind|password|secret|token...)`), applied to the RAW console line before line 154 projects formattedMessage
WHY: The API logs one JSON object per line (backend/app/src/main/resources/logback.xml, logback JsonEncoder) and the stack trace is a field of that same object. The exclusion runs on the whole raw line, so it also matches class names inside the stack trace and words in the message, although only level + logger + formattedMessage is ever printed. Http.kt line 175 logs "statement timeout request_id=..." (the word statement is in the message itself) and line 178 logs "unhandled error request_id=..." with the exception; any exception that passed through Jdbi (package org.jdbi.v3.core.statement) or the PostgreSQL driver (PgStatement / PgPreparedStatement) has "statement" in its stack. A database login failure carries "password authentication failed". All of these are dropped with no trace and no count of dropped lines. This is the safe direction for secrets, but it defeats the stated purpose of the change (read the API's ERROR lines).
SCENARIO: A request hits a SQL error in dev. The API logs ERROR aron.error "unhandled error request_id=..." with a stack that contains org.jdbi.v3.core.statement.Query. The operator dispatches ops-diagnose for that window. Line 152 drops the row because the raw JSON contains "statement"; the API section prints only start-up lines, and the operator concludes the API logged no error. Same for every statement-timeout line. Fix: apply the exclusion to the projected text (the 200 characters that are actually printed), not to the raw line, and print how many lines the exclusion dropped.

LOWS:
- Redaction runs AFTER truncation (KQL substring 200/240/300, then cut, then redact). I ran the sed block on synthetic lines: an e-mail cut before its top-level domain prints its local part and partial domain; a long token cut to under 40 characters prints whole; a phone number cut short prints its first digits. key=value, JWT and Bearer still match after a cut. Fix: fetch the longer line, redact, then cut in the shell.
- Phone pattern gaps (tested): dashed (01712-345678), spaced (+880 1712 345678, 017 1234 5678), 10 digits without the leading zero, a number glued to a preceding letter (no word boundary), and Bangla digits are all printed unchanged. Only the plain 01XXXXXXXXX, 8801XXXXXXXXX and +8801XXXXXXXXX forms are caught.
- Names are only partly covered, yet the script comment and D-OPS-DIAGNOSE-API-01 say names are redacted. `name=First Second Third` keeps everything after the first word; `outlet_name=...` likewise; a name or username in free text (`user x.y logged in`) is not touched. Only the JSON "name":"..." form is fully redacted. The wording should say so.
- Not caught at all (tested): otp=..., OTP followed by digits, cookie / Set-Cookie values, pin=..., IP addresses, device UUIDs, memo numbers that embed a username, usernames in a path or query string. The lens list names otp and cookie; neither is in redact() nor in the KQL exclusion. Today's API log statements that I read (107 info/warn/error calls) log ids, pseudonyms and exception class names only, and the request line uses the route template with hashed user and device, so I found no current line that would leak these; the net is simply thinner than described.
- The comment says request lines are not kept, but the include filter (line 151) runs on the raw JSON line with very broad words (config, application, worker, schema, started). Request lines for /config/delta, /config/public and /admin/config/* contain "config" in the route and are INFO lines from aron.request, so they pass. They carry no personal data (route template, hashed user/device), but with newest-first and a cap of 150 a busy window can push the start-up lines and older errors out of the output. The thread name is also in the raw line, so any line logged from a thread named ...-worker-N would pass too (not verified which thread names the API uses). Fix: match the include words on logger + message, and exclude logger aron.request.
