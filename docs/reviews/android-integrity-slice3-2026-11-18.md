# Lead review: android-integrity 49e6abc6..0f69f3b9 (enrolment, signals upload, lab grant part 1)

Reviewed 2026-11-18 by the lead (Opus pass, two lenses, each blocking finding checked by three refuters; fewer than 2 of 3 upheld counts as a low). Read from code only: nothing built, run or walked on a device.

## lab-grant-and-enrolment verdict=pass
SUMMARY: I found nothing blocking in the security of the lab grant (part 1) or in enrolment (slice 3A); the lows above are things to settle before or in part 2.

**Key material.** I searched every added text line for PEM markers, PRIVATE, EC KEY, .pem, .jks, .p8 and long base64 strings: nothing. The only key in the app is the resource aron_lab_grant_public_key (android/core-system/src/main/res/values/lab_grant.xml:5). It is empty, and no debug or test variant overrides it. Both test classes (LabGrantTest, LabExemptionServiceTest) generate P-256 keys at run time and never store them. tools/make-lab-grant-key.sh writes the private key to a mode-600 file, refuses to overwrite one, and prints only the public key.

**Token and verification.**
- Format: base64url(payload).base64url(DER ECDSA P-256/SHA-256 signature).
- Payload: v=1, d = device uuid (from app.device.device_uuid), iat, exp.
- The phone (LabGrant.kt:96-109) reads no header and fixes the algorithm in code, so 'alg none' or key confusion is not possible.
- It accepts only v==1, a d equal to this phone's DeviceIdentity uuid, and an exp still in the future.
- With no key, an empty key or a bad key, the verifier is not configured and accepts nothing; a test covers this.

**Storage on the phone.**
- The signed token is kept in noBackupFilesDir and re-verified on every isActive.
- isActive also needs the LabExemptionStore record, which enforces the 7-day cap and the clock-back and reboot guards.
- So a hand-written record, a token signed by another key, or files copied from another device all fail; tests cover each.
- Backups are off in all three manifests.
- Under the grant, the controller (IntegrityGateController.kt:59-61) lifts only the Developer-options block, and only when the build has no build exemption.
- The onset is still recorded with exempt=lab and uploaded as integrity_events, which carry codes only, so the server sees an exempt phone.
- The spoofing refusals are in core-geo and do not read the grant.
- The old unauthenticated labExemptionHonoured switch stays false.

**Expiry and clock rollback.** Bounded today: setting the clock back voids the store, and only accept() can recreate it. accept() is not wired yet, and part 2 must not feed it from a cached token (first low).

**Revocation.** Not wired. Until it is, no grant can reach a phone (fails closed). Once wired, the offline window is min(exp, 7 days).

**Server.**
- LabGrantSigner and LabExemptionService refuse to grant or sign without a key.
- Grants are capped at 1..14 days and the note at 300 characters; V0202's CHECK enforces the same limits again.
- No token is given for a revoked or replaced device, or once the row has expired.
- V0202 only creates a new table and applies the role grant map, so it is safe on existing data and has no guard that can RAISE.

**Enrolment (3A).** Only the demand for the self-reported device_owner boolean was removed. All key-attestation checks for production tokens are unchanged, so a rooted or emulated phone gains nothing. The test change only inverts the device-owner case, as the owner directive requires; the boot, root and hardware-key negatives remain. Both portal forms now start with no lockdown level and refuse to submit until one is chosen. The server already rejected any level other than dev or prod (DeviceService.kt:65).

**What I could not check.**
- Nothing was run: no Gradle tests and no device.
- Part 2 does not exist yet: the admin endpoint and its permission and audit, reading ARON_LAB_GRANT_KEY in Settings/Main, the bundle field and the accept/revoke calls.
- I did not look in depth at the signals upload, the geo_fix.signals migration or the slice-2 lows beyond the integrity_events schema, because they are outside this lens.
- Reviewed with git show and git diff on 49e6abc6..0f69f3b9; HEAD was not moved. Fetching the branch into origin/lane/android-integrity failed with a ref-lock error, so I fetched into FETCH_HEAD and confirmed that 0f69f3b9 exists. The remote branch has moved on to 4cc364f2, which I did not review.

LOWS:
- Clock rollback can revive the grant once part 2 is built (android/core-system/src/main/kotlin/com/aktcl/aron/core/system/integrity/LabGrant.kt:128-135). Today the bound holds: LabExemptionStore (LabExemption.kt:44-56) clears the record when the wall clock moves back past its high-water mark or the issue time, or when one boot has held it too long, and VerifiedLabExemption.isActive needs that record and a verified token, so an expiry is final. But accept() only checks exp against the phone's own clock, then calls store.grant(exp), which writes a new high-water mark at the rolled-back time. Part 2 will feed accept() from the bundle load. If it ever replays a token cached on the phone (an offline bundle), a rep could set the clock back and re-run the load to bring the grant back again and again. Requirements for part 2: call accept() only with a token from a fresh, authenticated server response, never from a cached bundle; or have accept() refuse an iat older than the stored high-water mark.
- Revocation is not wired yet (docs/runbooks/lab-exemption.md:11): there is no admin PUT/DELETE, no bundle field and no call to acceptLabGrant/revokeLabGrant. So nothing reaches a phone, which fails closed. Once part 2 ships, a withdrawn grant stays live on an offline phone until min(signed exp, 7 days from the last accept), because LabExemptionStore caps it locally (LabExemption.kt:26-31). Write that offline window into the runbook.
- The signed payload is {v,d,iat,exp} with no purpose, issuer or environment claim (LabExemptions.kt:22; LabGrant.kt:106). No alg or kid header is read, so algorithm and key confusion are not possible. But if the test account and the final account use the same ARON_LAB_GRANT_KEY / public key resource, an admin on the test server could sign a grant that a production phone accepts. Use one key per environment (say so in the runbook), or add an 'aud'/'env' claim and check it.
- LabGrantVerifier loads any EC public key from the resource with no curve check (LabGrant.kt:90-92). The resource is fixed at build time, so a rep cannot exploit it. Still, check that params.curve is P-256 (secp256r1) at load and fail closed otherwise, so a wrong key pasted by mistake is caught.
- Signature encoding: SHA256withECDSA verifies DER on both sides (LabExemptions.kt:25; LabGrant.kt:103), so the signer and verifier agree. There is no test for a raw r||s signature or one with trailing bytes, and the KDoc does not say that only DER is accepted. Add one negative test.
- The device binding is to the client-generated device_uuid in app-private storage (core-session DeviceIdentity.kt). It is not a hardware-attested ID. Without root a rep cannot copy a grant: allowBackup=false and fullBackupContent=false in all three manifests, the token sits in noBackupFilesDir, and LabGrantTest covers copied files. With root he can clone the uuid and the token. The runbook already states this limit honestly, so no action is needed. Optionally, once part 2 exists, bind the grant to the enrolment key thumbprint as well.
- IntegrityGates.deviceUuid is set in the DeviceRuntime init block (DeviceRuntime.kt:151). If the gate is checked before DeviceRuntime is built, the uuid is null and the grant verifies for no one, so a lab phone is blocked (fail closed). That is safe but could confuse the first gate check after a cold start. Document the ordering, or set the uuid in Application.onCreate.
- LabExemptionService.grant/revoke do no permission check (LabExemptions.kt:32,46). That is acceptable while no endpoint exists. When the route is built it must require Super Admin or the mdm module write grant on the server and write an audit row (the runbook lists this). Also the private key is not yet read from ARON_LAB_GRANT_KEY anywhere in Settings/Main, so 'absent = endpoint refuses' cannot be checked yet; the signer itself refuses with no key (LabExemptions.kt:23,33).
- Enrolment: req.device_owner was a boolean the phone reported about itself and was never attested. Removing the demand (DeviceService.kt:168-171) therefore drops no cryptographic check. Production tokens still require: a trusted root, with roots configured; an attestation challenge equal to SHA-256 of the token; the attested package and signer; a known release certificate; a locked device with verified boot state 0; and a hardware-backed key (DeviceService.kt:172-183). A rooted phone (unlocked bootloader) or an emulator (software key, untrusted root) is refused as before. One existing detail: the hardware-key check can be switched off with cfg.device.key_attestation_required=false. This delta did not change that, but the portal hint now says production 'demands' a hardware key, so the hint is untrue if an admin flips that flag.

## signals-upload verdict=fail
SUMMARY: Lens: the signals upload and the slice-2 lows, delta 49e6abc6..0f69f3b9 (lane commits c30f8b0e7 and 8046c41de, plus the merge 1ce3a19c4, a DECISIONS-only conflict with both sides kept). The contract is additive and old phones are accepted. Signals are mapped at enqueue and queued payloads and signatures never change. V0201 is metadata-only. Soft signals only feed post-hoc risk rows. Each slice-2 low is fixed with a test that would fail without the fix. One blocking finding: the server stores integrity_events unchecked, and RiskSignalEvaluator casts flag elements without a check. One malformed report from a tampered phone therefore aborts risk evaluation for every user on today and yesterday. Lows: a clean checked fix is sent as absent, which the contract defines as unknown; a 10-minute facts cache defeats the refusal's 'open again' step; shared-phone misattribution and a device subject id that differs from the existing device rows; events dated by the report instead of the event; no ingest test for events. Nothing was run on a device or a database.

### BLOCKING upheld=3/3: One malformed integrity_events entry stops the server's risk evaluation for every user, for today and yesterday
WHERE: backend/masterdata/src/main/kotlin/com/aktcl/aron/backend/masterdata/RiskSignals.kt:211 (`.map { (it as JsonPrimitive).content }`), with backend/sync/src/main/kotlin/com/aktcl/aron/backend/sync/RecordWriter.kt:88-90 (device_status stored whole) and IngestService.kt:1829-1860 (shapeError checks only member names, and only for nested objects, so the contents of the integrity_events array are never checked)
WHY: The server never checks the contents of integrity_events against the contract (additionalProperties false, the flags enum, maxItems 50/3). The report goes into device_status_report.report as it arrived. RiskSignalEvaluator.integrityEvents then casts every flags element to JsonPrimitive without a check. Any flags element that is an object or an array throws ClassCastException. That aborts the whole evaluateDay transaction for every user on that business date. RiskSignalJob runs today and then yesterday inside one runCatching, so yesterday is skipped too. Reps tampering with their phones is the stated threat (CLAUDE.md constraint 5, D-OWNER-MDM-02), and a tampered phone can send this. A future phone whose contract changes the element shape can too.
SCENARIO: A rep on a rooted or repackaged app sends one signed device_status record whose report holds `integrity_events: [{"at":"2027-01-03T04:00:00Z","flags":[{"x":1}],"exempt":"none"}]`. Ingest accepts it, because the shape check sees only known member names. Every 15 minutes evaluateDay(today) throws, is logged and rolled back, and yesterday's date is never reached. GEO_MOCK, GEO_TELEPORT, GEO_ZERO_JITTER, route-single-point, mismatch and phone-signal hits stop appearing for the whole fleet on two business dates. The fix: use `as? JsonPrimitive` (mapNotNull) and keep only known flags and exempt codes in the evaluator. Better still, also check the integrity_events elements at ingest (array, at most 50; at, flags and exempt are strings; flags at most 3). Add a test that inserts a malformed report and still gets the other users' hits.

LOWS:
- Clean fixes look the same as old phones: VisitPorts.kt:58 and BreadcrumbWiring.kt:46 store signals_json only when the list is non-empty, so a 1.19 phone that checked and found nothing sends no `signals` member. The server then stores NULL, which V0201's comment and the GeoFix description define as 'unknown, not clean'. The comment's 'empty array = checked and found nothing' is never sent. The phone should send [] for a checked fix (new captures only), or the contract and comment should be reworded.
- FixManager.kt:197: when spoof.check throws, the result falls back to SpoofResult.NONE. The fix is then treated and stored as clean for the soft codes and for mock_app_selected/test_provider. The platform mock flag still applies through loc.isMock. Send no signals member (unknown) instead of clean on that path.
- The refusal's next step does not take effect for up to 10 minutes. AndroidSpoofProbes caches mockAppSelected and fakeGpsAppInstalled for 10 minutes (AndroidSpoofProbes.kt:42-46), and invalidate() (line 49) is never called. A rep who follows out_blocked_mock ('uninstall... open the outlet again') is refused again until the cache expires or the process restarts. Suggest invalidate() on a hard refusal or when an outlet is re-opened, plus a test.
- SpoofChecker.prepare (PreviousFixStore.kt:66) runs inside FixManager's lock with no timeout, so a hanging AppOps or PackageManager binder call holds the fix indefinitely (it used to hang on the caller's thread instead). check() still calls probes.facts() on the caller's thread when prepare failed or the TTL ran out in between, so a small ANR window remains. It is never 'clean by default', because the read happens synchronously.
- Shared phones: PhoneSignalRules groups by phone and sets user_id = the first fix's or event's user (RiskSignals.kt:139-146, 155). On a phone shared by two reps on the same day, rep B's codes are counted in a row attributed to rep A, which drives portal scope and the reviewer's view. Group by (phone, user) or note it in the evidence.
- Subject id differs from the existing device rows: the existing DEVICE_INTEGRITY_FAIL rows use subject_id = device UUID (DeviceService.kt:322-331, IngestService.kt:1323-1330), while PhoneSignalRules uses device_id::text (the bigint) or 'user-<id>'. Nothing gets overwritten, but one phone can now have two DEVICE_INTEGRITY_FAIL rows per day under two id formats. Also, store() overwrites score and evidence without the status='open' guard that the other writers use. That is harmless today only because the keys never collide.
- Gate events are dated by the report, not by the event: integrity events are counted on the device_status_report's business_date, not their own `at`. Events reported days later, or a re-send across Dhaka midnight after a kill, land on the wrong date, or on two dates, and dedup by (phone, at, flags) works only within one date.
- Phone strings reach the evidence unfiltered: the evidence 'flags' keys and the unknown fix codes stored in geo_fix.signals are free strings from the phone, bounded only by the body limit. maxItems 16, uniqueItems and the enum are not enforced on the server. Storing unknown codes is right for extensibility, but filter or bound their length before they go into risk_signal.evidence.
- IntegrityEventLog (CAP 200, takeLast) together with ack(count): if the log is full and the gate records an event between pending() and ack(n), the oldest line is dropped and ack(n) then removes one event that was never sent. This needs 200 or more pending events; the fix is to ack by identity instead of by count.
- There is no ingest test for integrity events: RiskSignalsTest covers fromIntegrityEvents only as a unit. The SQL that reads device_status_report.report->'integrity_events' never runs through a real device_status ingest. Add one that goes from ingest to the risk table.
- RecordMapping.SPOOF_CODES (RecordMapping.kt:48-51) is a hand-written copy of the SpoofCode wires; they match today, but no test ties them, so a new SpoofCode would be silently dropped from uploads.
- Checked and fine: contract additive (both members optional; the server tolerates unknown codes because PayloadShapes checks only member names, and signals was added to all 12 fix-bearing shapes plus integrity_events to device_status); old phones accepted (BatchAcceptanceTest through real ingest); payload built at enqueue, sig set only `WHERE sig IS NULL`, the resync/digest paths only reset state, so a queued payload is never rewritten; V0201 is one nullable column with no default (no rewrite), lock_timeout and comments, no data guard; soft signals only feed the post-hoc risk_signal table, never ingest verdicts, and nothing re-evaluates stored verdicts; codes only, no coordinates or package names in signals or events; acknowledgement after recordDeviceStatus, at most 50 per report, the server dedups by (phone, at, flags); strings in values/ and values-bn/ (out_blocked_mock and edit_denied_mock give a next step in both languages, with tests); previous-fix prefs cleared with commit() at logout on both LogoutFlow paths, via ShellLogout for every role (tests stricter, not loosened); the FLAG_SECURE reference count is shared with SecureScreen, with a Robolectric test at API 30; memo edit returns EditDenied.MockLocation in SR and AMO; integrity gate first in every CaptureRepository record method; the DECISIONS merge resolution keeps both sides (D-AINT-01..09 plus the lead entries); the AmoManualContractTest pin is a version bump matching openapi 1.19.0, not a loosening; the DeviceEnrolmentTest change follows the directive (non-owner now Created; root, boot and key failures still refused).
