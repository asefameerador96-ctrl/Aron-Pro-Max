# Lead review: android-gates-2 ten follow-ups (29e8d86f3..6a86c275)

Reviewed 2026-11-18 by the lead (Opus lenses, three refuters per blocking finding). Read from code only: nothing built, run or walked on a device.

## gates2-attendance-and-close verdict=pass
SUMMARY: Read from code only at 6a86c275 against 29e8d86f3 (nothing built or run). No blocking defect found in items 1, 2, 5, 6, 10.

Item 1 (closed_by). There is one mapping, RecordMapping.attendance, and the payload is built when the outbox row is inserted, inside the check-out transaction, never at upload. closed_by = phone is set only when the caller's own mark list holds a DAY_CLOSED mark for the same business date as the event (CaptureRepository.recordCheckOut). It reads the parameter, not the phone_mark table, so a stale mark from an earlier failed attempt cannot turn a rep close into a phone close (and a failed attempt rolls its mark back anyway). Paths: rep check-out (SR and AMO AttendanceFlow -> commitAttendance with no marks) sends no closed_by; the phone's close of a forgotten day (closeForgottenDays, the only caller, reached from start, resume, the midnight/04:00 timer, end of a call and Try again) always passes the mark of that date, so it always sends phone; there is no background or worker close path; TSO uses recordAttendance and never sends closed_by. The mark is inserted after the outbox row but in the same transaction, so both commit or neither. Rows queued before this change keep their stored payload, hash and signature. Check-ins and rep check-outs encode no closed_by (default null, same as before). The rep's check-out now takes its meta at the press, before the fix read: press 23:59:45, fix 00:00:10 gives business date D and capture time 23:59:45 on D. The server on this branch (IngestService date window, checkout_too_early, V0202 once-per-day indexes, checkoutWithoutSubmit) has no rule that compares the fix time or the day_submit's capture time with the check-out's capture time, so it is accepted as a rep check-out of D. A fix that comes back not-ok is still stored with the press stamp; a readFix that throws writes nothing (as before). One narrow race remains (first low).

Item 2. AutoDaySubmits.build passes the date being closed to stockSlipPrinted; SR and AMO read stockOn(that date). Correct.

Item 5. Counter key is day_close_fail:<kind>:<date> in sync_meta (existing DAO methods, no schema change). It is raised only on an exception (a cancellation is rethrown, a refusal is not counted), deleted on success, and lockedOut() deletes any counter whose day is no longer in openAttendanceDates or whose call is no longer the open one, before showing anything, so a rep whose close succeeded (by any path) is not trapped. The code is 'E-CLOSE-DAY/' or 'E-CLOSE-CALL/' plus the exception class name only. Try again runs resumeDaySafely: same resumeLock, fixLock.tryLock and the in-transaction 'no check_out yet' check, button disabled while running, so no double close. The four strings exist in English and Bangla.

Item 6. The guard runs first inside the check-out transaction and uses exactly the lookup restoreOpenVisit uses (callToRestoreAcross plus the route-day refusal), so it refuses only for a call the next resume would restore: a closed call (has a visit_close) and a call the restore skips (blocked, Final Submit or Sales Submit closed route-day) do not refuse. The phone's close passes no guard. The refusal rolls back everything and shows the same 'open call' words.

Item 10. ACKED with last_code = attendance_duplicate is produced only by the AckRules branch 'row payload says closed_by=phone AND server answered rejected/attendance_duplicate'; accepted and duplicate answers write a null code. The server digest counts only registry accepted/voided, and a rejected row is in neither, so the counts now match. A rep's duplicate goes to REJECTED (never in the digest, as before); a phone close resent by uuid is answered duplicate and stays counted on both sides. After a restore, resendAckedSince still re-sends the row, so a lost server copy is healed. The filter is as narrow as stated.

Rules: Room version is still 10, no file under core-database/schemas changed, no entity or DAO signature that affects the schema changed; backend, shared DTOs and contract are untouched by the diff.

Could not verify: that the new tests pass or that the mutation proofs were run (no SDK here); FakeIngestServer's fidelity to the real server; how Compose hit-testing and Back behave under the lock-out overlay on a device; real FixManager timing at midnight; the Bangla wording beyond reading it.

LOWS:
- Item 1, midnight race still open in a narrow case. A rep presses check-out at 23:59:45 and the midnight timer runs resumeDay at 00:00:00. forgottenDays() (SrDay.kt / AmoDay.kt) does not know a rep check-out is in flight (openWorkNow is null), so the phone also starts a close of day D. Fix reads are serialised in FixManager (one mutex), so the rep's read normally ends first and the rep's commit wins. But when the phone's own read returns at once (location off, permission denied, or a very fast fix) the phone's commit can land first: one record only, sent as closed_by=phone with a capture time on D+1, the rep's press gets AttendanceResult.Failed, and the server reads the day as 'no check-out'. Never two records (recordCheckOut checks 'no check_out yet' inside the transaction). The phone's failed-close counter is not left behind in the opposite order (stillOpen deletes it). Suggest: forgottenDays() returns nothing while attendance.state.busy.
- Item 1, display only: after a rep check-out the screen shows nowIso() (after the fix read) as the check-out time, while the stored and uploaded capture time is the press time. A restore shows the stored one. Up to about 30 s apart.
- Item 1, by design but worth saying: the TSO check-out (recordAttendance) and any check-out not passed a DAY_CLOSED mark now never carry closed_by, also when captured on a later Dhaka date than the business date. SR and AMO block a rep press after midnight (pastDay), so this only changes the TSO edge.
- Item 5: the lock-out screen is drawn as a second child of a Box over the app. Touches are stopped by its full-size scroll column (read from code, not seen on a device), but system Back and TalkBack focus can still reach the screens underneath. Device walk item.
- Item 5: the counter rises on every resume attempt (start effect and ON_RESUME both run at launch), so three transient failures within seconds raise the screen. Not a trap: Try again or the next resume clears it on the first success, and a counter whose day or call is no longer open is deleted before it is shown.
- Item 5: while the lock-out screen is up the rep cannot reach the sync sheet or log out; background sync still runs. This is the lead's approved design.
- Item 10: a phone close that was answered attendance_duplicate by an app version before this change is ACKED with last_code = null, so it is still counted by the phone's digest until its date leaves the 7-day window (the old bounded behaviour for those rows only).
- Item 10: the acked phone close now keeps last_code and message_key, so it appears in the support bundle's outbox code list (state acked, code attendance_duplicate). No screen shows it as a refusal (those read rejected/quarantined states).
- Item 6: the AMO guard treats a failing dayRefusal read as 'call open' (runCatching ... getOrNull() == null), the same as restoreOpenVisit would restore it; a database read error at that moment refuses the check-out with the 'open call' words instead of a plain failure. Next press tries again.

## gates2-sale-races-and-tests verdict=pass
SUMMARY: Lens B on origin/lane/android-gates-2 at 6a86c275 against 29e8d86f3: pass, no blocking defect. Everything is from reading code; nothing was built or run.

- **Item 3 (SaleFlow.commit):** correct. The lookup is by the draft's own memo UUID, inside the flow lock, after the in-memory answer and before the closed-call refusal. It can only return this draft's memo, clears the draft, sets `committed`, and writes nothing. The print model is loaded from Room by memo UUID (SaleCommitStep, then MemoPrintSource), so a replay prints the stored memo.
- **Item 4 (resumeDaySafely):** SR and AMO both use `catching`, which rethrows cancellation and catches the rest; SrApp uses it at its four sites and in Try again. The four AMO sites still use `runCatching` and do swallow cancellation, but I found no hang or leak from it. The caught failure is not logged or counted (low).
- **Item 7 (audit saves under closeLock):** no deadlock found. The order stays resumeLock, closeLock, flow lock, Room. No save is called with closeLock already held, nothing inside a Room transaction takes closeLock (the item 6 guard only reads), and all locks are suspending, so the main thread is not blocked. The fix covers the Save-first order only; the close-first order is not guarded for a same-day rep close, and the KDoc overclaims (low).
- **Item 9 (race tests):** SrSaveCloseRaceTest and AmoSaveCloseRaceTest do run two coroutines on the real kit and real Room with the executor held. They check that the first holds closeLock, that the second waits and has not reached the database, and they assert the end state in both orders for the phone end and the rep close. The hold is released in a finally. They are not sleep-free (a 300 ms delay and a wall-clock poll guard), which is safe for passing runs but not strictly deterministic.
- **Mutation proofs, spot-checked by reading (four):** each named test would fail — commit lock removed (the `closeLock.isLocked` check or `waiting() == 1`), the Room lookup removed (SaleFlowTest gets CallClosed), resumeDaySafely not catching (SrMidnightRestoreTest throws), audit lock removed (the Save completes inside the 300 ms).
- **Item 8 (wording):** all six new keys are in both values and values-bn, the Bangla reads correctly, and both call sites that used the check-in text for an earlier open call now use the new key.
- **Hygiene:** no test file deleted, no @Ignore or assume added. The two older check-out tests only swap `visitSession.close()` for the real close with assertions unchanged. DECISIONS.md is append-only (3 lines added, none removed). Only android/, docs/ and DECISIONS.md changed; no schema or migration file was touched. The handover does not actually list device-walk-only items (low).

LOWS:
- Item 7, close-first order is not guarded for audit records. AmoRecordWriter's KDoc says that when the close lands first 'the write is refused by the closed-call guards', but I found no such guard: CaptureRepository.recordAmo and recordSurveyResponse check the check-in and the route-day only, never the visit's close. For the phone's 04:00 end the waiting Save is refused in practice (the session is empty, so the record takes today's date, which has no check-in). For the rep's own same-day close (leave the call, then Save lands a moment later) the record is still written on a call closed as abandoned, with route 0. Narrow (two taps within the close's run time) and no worse than before the lane, but the comment overclaims. D-AGATE-23's own wording is accurate (it only claims the Save-first order).
- Item 7 tests: only saveAssessment of the four wrapped saves is tested, with a private Mutex. No test covers the production wiring in AmoDay (`callLock = closeLock`), so removing that one line would leave every test green. There is no real audit-Save against closeVisit race on the kit, and no end-state assertion for either order.
- Item 9, the race tests are not sleep-free or clock-free: a `delay(10)` poll with a System.nanoTime 10 s guard, and a fixed `delay(300)` before the 'second one waits' assertions. The same `delay(300)` is in the audit lock test. This is safe in the passing direction (correct code cannot fail on timing). Two residual risks: on a very slow machine a broken lock could slip past the 300 ms window, and `assertEquals(1, exec.waiting())` would fail falsely if any background Room command of the fixture reached the held executor in that window. I could not rule the second out by reading.
- Item 4: resumeDaySafely drops the failure without a log or counter. The lock-out counter only counts a failed close write (closeForgottenDays' commit, abandonStaleCall's close). A persistent read failure earlier in the resume (restoreOpenVisit throwing, or forgottenDays, which turns a read error into 'no forgotten day') is retried silently for ever and never reaches the lock-out screen. refreshCloseLockout also sets the lock-out to null when its own read fails, which hides the screen. All of these need a broken database; no realistic trigger found.
- Item 4, AMO sites (MainActivity.kt lines 195, 211, 219, 229): `runCatching { d.resumeDay() }` does swallow CancellationException. I found no hang or leak from it: each is the last suspending call of its coroutine, and the only code that runs after a cancel is `boundaryTick++` at line 219, a harmless state write. It is still the wrong pattern; AmoDay.resumeDaySafely now exists and the four sites should use it.
- Item 4, SR: the Try again handler and the ON_RESUME, boundary and call-end sites call `day.reload()` right after resumeDaySafely with no catch. A Room read failure there would still crash the app, in the same class of failure item 4 set out to stop. This was there before the lane.
- `catching` rethrows every CancellationException, including one Room throws when the database is closed (the lane's own gotcha note). In SrApp's boundary effect that would end the effect before `boundary++`, so the midnight timer is not re-armed until the next key change. It only happens with the database closing (sign-out), where the tree is rebuilt anyway.
- Item 5 (seen in passing, not my lens): DayCloseFailedScreen is laid over the app in a Box, and AronScreen is a plain Column with a background that does not consume touches. Taps on empty parts of the lock-out screen, and the system Back, likely reach the hidden screen underneath, and TalkBack would read both layers. Nothing unsafe can be written (the write layer refuses), but it needs a device walk.
- Handover: docs/status/android-gates-2.md says what is left is 'the device walks named in D-AGATE-24', but D-AGATE-24 names none, and nothing else in the lane's docs lists device-walk-only items. Candidates: the lock-out screen (look, Bangla, touch-through, Try again), the two new dialog texts, and a check-out pressed just before midnight.
- Item 3: if a Save landed unheard and the rep then changed the draft in the same flow before retrying, commit now answers with the stored memo and clears the draft without saying the later changes were not saved. Only reachable without leaving the sale screen, and it matches what `start` already does.
- Hygiene: one old assertion was removed with the deleted function (SrMidnightRestoreTest: 'a check-out captured on its own date is the rep's, not marked'). Per D-AGATE-22 its replacement is in CheckOutSubmitTest, which is outside my lens and which I did not read line by line.
- Could not verify: nothing was built or run here. The race-test run time is an estimate from reading (8 tests, each at least 300 ms plus fixture set-up, so a few seconds plus Robolectric start). The mutation proofs were not re-run; the status file records a CI result for pushes 1 and 2 only, none for push 3 (6a86c275).
