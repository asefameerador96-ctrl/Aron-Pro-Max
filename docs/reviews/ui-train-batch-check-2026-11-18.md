## sr-qc-fix-round verdict=pass
SUMMARY: Read-only check of the QC two-step fix round (commits 2c621a5fea and e017b2d740 on top of 960556efec; the merge of 29e8d86f3 skipped). Both earlier blockers are closed by the code as read. B1: step-2 Cancel writes nothing when locked, and SaleFlow.setQc, cancelQcOnly and restoreQc now return the draft unchanged on a submitted QC, so no QC path (SR step 1, SR step 2, AMO one-scroll) can throw into the view model's coroutine; no caller relies on the write. B2: selected/opened are plain remember, so after an activity recreation or a process death QC opens on step 1 and Cancel has nothing old to write back; the restart also re-runs SaleFlow.start, which drops unsubmitted QC, so the screen and the draft agree. The shared qcMax is word for word the old formula, no AMO/TSO golden changed, totals and settlement are untouched, the new strings are in both languages, and no pre-existing test was weakened in this round. No blocking defect found. Main things to know: (1) a pre-existing crash of the same kind remains outside this diff: after QC is submitted, a rotation/relaunch puts the route back on the Entry list where a quantity change throws 'sale is locked after QC' in a bare launch; (2) a rotation during QC silently drops all typed QC (existing restart rule; the SR activity is not orientation-locked); (3) the DECISIONS wording about the discard confirm and one KDoc line overstate what the code does; (4) the route-level restore test is a weak proof (it may pass on the old code too). Nothing was built or run here.

LOWS:
- PRE-EXISTING, not from this lane, but the same crash class as B1 and worth a fix in the next pass: the Entry and Slide screens do not know about the QC lock. SaleDraftOps.setQuantity and setSlide still throw "sale is locked after QC", and SaleViewModel.setQuantity / setSlide run them in a bare viewModelScope.launch (SaleFlow.setQuantity and setSlide have no guard). Inside one composition Review never goes back to Entry, but SaleRoute's stage is plain remember and the SR MainActivity has no orientation lock or configChanges in the manifest, so: rep submits QC (locked, kept across restarts), then rotates the phone / the app is killed and relaunched / the rep leaves the sale and comes back before Save -> the route is on the Entry list with a locked draft -> a quantity change throws in the coroutine -> the app crashes. Read from code only, not run. The same code is on integration 29e8d86f3.
- Rotation (or any activity recreation) while in QC: SrSaleHosts runs LaunchedEffect(v.visitUuid) { vm.start(...) } again on every fresh composition, so SaleFlow.start's sanitizeQc drops all unsubmitted QC, and the route returns to the Entry list. Nothing stale is written and nothing half-restored is left (safe for money), but the rep silently loses every QC value typed, including SKUs already closed with Save on step 2, with no message. This is the existing rule, not new in this fix; with plain remember the step-2 page is also gone, which is consistent with it. Worth telling the owner or locking the orientation.
- The DECISIONS text (D-PAR-SR1-25) says a discard confirm appears 'when a page has unsaved typing and Back/Cancel is pressed'. The code asks only on step-1 Cancel, and only when the draft has QC rows and is not locked. Step-2 Cancel restores the page's opening values with no question; step-2 Back and the top-bar back act as Save; system Back on step 1 leaves the Sale screen with no question (the QC rows stay in the draft until the next start drops them). None of this writes wrong numbers; the wording overstates.
- The 'discard' on step 1 is one atomic write (restoreQc(qcBefore) under the flow lock), so it cannot leave half-restored rows. The step-2 Cancel is six separate setQc writes in order under the same lock; values come from the draft itself and setQc does not clamp, so no value can be lost; a kill in the middle is covered by the restart rule (unsubmitted QC dropped).
- The KDoc above QcTwoStepScreen still says 'The open SKU and the values to restore survive a kill and relaunch (rememberSaveable)'. The code beside it is now plain remember; the comment is stale.
- SrQcRouteRestoreTest drives the real SaleHost/SaleRoute in SrFrame and recreates the activity, but (a) the content is set again by hand after recreate() and the test tolerates the start-call 'Yes' box being there or not, so it does not show that the saved instance state was really restored into the new composition; (b) after the recreation vm.start runs again and the stage is Entry anyway. I could not confirm the test would have gone red on the old rememberSaveable code. The product fix itself is plain from the code (remember is not saved), so this is a weak proof, not a defect. It also does not cover process death (only recreation); process death is covered by reading: stage Entry, start drops QC, nothing saved in the screen.
- Making SaleFlow.setQc / cancelQcOnly / restoreQc return the draft unchanged on a locked QC hides no caller: the only callers in main code are SaleRoute's QC lambdas (onQty, onClearSku, onCancel), shared by SR and AMO, and all of them are read-only once locked. SaleDraftOps is untouched and its own test (SaleReviewTest.afterQcCompletesTheSaleIsLocked) still asserts the throw. The ignored call still saves and republishes the same draft; harmless.
- B1 paths checked by reading: SR step-1 Cancel (locked: no confirm, onCancel -> restoreQc ignored, back to Review); SR step-2 Cancel (guarded by !locked, only closes the page); step-2 Delete hidden when locked; typing guarded by !locked and the field disabled; AMO one-scroll Cancel -> restoreQc/cancelQcOnly ignored; +/- and field guarded. A setQc that races the lock (queued after completeQc) is now ignored instead of crashing.

No AMO or TSO PNG differs between 29e8d86f3 and e017b2d7 (only srp1* files changed). Totals and settlement expressions are unchanged; the fix adds only the 'no QC entered' line, the unit in the quantity header and the step-2 title.

The new QcTwoStepTest cases use a state-held real draft with SaleDraftOps.setQc (which throws when locked), so a write on a locked page would fail the test. theOpenSkuSurvivesAKillAndRelaunch is the lane's own (QcTwoStepTest.kt does not exist on 29e8d86f3) and the new assertion (2 cards, 0 fields after restoration) is right for plain remember. The only pre-existing test file changed in the whole lane is SppConnectorTest (commit 960556efec, outside this lens): timing/dispatcher set-up changed, one assertion added, none removed as far as I read.
