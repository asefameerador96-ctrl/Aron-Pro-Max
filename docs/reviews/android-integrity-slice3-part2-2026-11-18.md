## lab-grant-server verdict=pass
SUMMARY: Read-only code review of origin/lane/android-integrity 0f69f3b904..90e795e228, server lens. Nothing was built or run (no SDK, no database here), so every statement below is from reading the code and tests, not from a green test run.

No blocking finding.

What I checked and found correct:
- Admin PUT/DELETE /v1/admin/devices/{id}/lab-exemption: ADMIN and SUPERADMIN only (SUPPORT, TSO, DMO, WM, AMO, ANALYST get 403); ADMIN is additionally judged by the 'mdm' module write grant through the existing path map (/v1/admin/devices/** -> mdm, PUT/DELETE need 'w'). Reach is taken from the server-side Reach of the token; a phone outside reach, unknown, or revoked/replaced answers 404 (not 403, so existence is not leaked). 409 when no signing key, and nothing is recorded. Days 1..14 and note <= 300 are checked in the API, the service and the table CHECK.
- Audit row is written inside the same transaction as the grant upsert / the delete (callback on the same handle); it holds days, expiry and note, never the token. The token is not in any DTO, response or log line. Settings.labGrantKey is a Secret, redacted in toString, absent by default, blank treated as absent; the signer refuses non-P-256 keys.
- The grant is signed once in grantRow and stored in grant_token; BundleService.labGrant only reads the stored token for the device id in the caller's signed token (claim did), only while unexpired. A different device, another user, a token without a device, and the worker prebuild cannot receive device A's grant; the delta never carries config values, and the page cache only serves paged row sections. The bundle digest (ETag / snapshot seq) includes the grant, so a new grant changes the version; the delta fingerprint's 'rest' includes it, so grant, withdrawal and expiry all answer the delta with 410 'fetch the full bundle'; bundles without a grant keep their old hash.
- Migrations: V0202 at the tip is byte-identical to the blob at the base commit 0f69f3b904 (restored after fc140a4a had edited it); V0203 only adds a plain nullable text column with a comment, forward-only, no rewrite. Table-level role grants from V0202's apply_db_role_grants() cover the new column (no column-level grant applies to this table).
- B1 fix (afecc7e1): IntegrityEventReader never throws on stored JSON, skips and counts bad elements (warn log with count only), keeps only known flag codes, treats unknown 'exempt' as not blocked; each source runs in a savepoint so one failing query or store does not abort the others; per-user and per-route rule failures are isolated; today and yesterday are evaluated independently. Ingest now refuses malformed integrity_events / signals as schema_invalid (PhoneEvidenceShape), with caps that match the phone (50 events per report, phone takes 50).
- Signals lows: one risk row per rep on a shared phone with the rep's own user_id, events dated by their own Dhaka date and counted once across re-sent reports; phone-side ack is by identity.
- Tests: LabExemptionServiceTest, BundleLabGrantTest, RiskSignalsTest additions, PhoneEvidenceShapeTest, SettingsTest and the extended BatchAcceptanceTest assert real behaviour (signature verification with the public key, DB row counts, audit rows, HTTP statuses, digest equality/inequality, 410 on delta). The one renamed test (BatchAcceptanceTest) was widened, not loosened; I saw no skipped or disabled test in the server diff. The old masterdata LabExemptionServiceTest was moved to analytics with more cases.

Could not verify: that the tests actually pass; that the contract conformance suite accepts the new config value and routes; whether the dev database already applied V0201 to V0203 (matters for the planned renumber); whether the signing secret is set on the dev server; the Android side (verification of audience/device/expiry on the phone, handling of an unknown config key) was outside this lens. Relevant files: /tmp/claude-0/-home-user-Aron-Pro-Max/a5c3c45a-b89c-5768-9d5f-6bc05c04fc63/scratchpad/wt-verify/backend/analytics/src/main/kotlin/com/aktcl/aron/backend/analytics/devices/LabExemptions.kt, .../devices/DeviceService.kt, .../devices/DeviceApi.kt, backend/sync/src/main/kotlin/com/aktcl/aron/backend/sync/BundleService.kt, .../sync/BundleDelta.kt, .../sync/PhoneEvidenceShape.kt, backend/masterdata/src/main/kotlin/com/aktcl/aron/backend/masterdata/RiskSignals.kt, db/migrations/V0202__device_lab_exemption.sql, db/migrations/V0203__device_lab_exemption_token.sql.

LOWS:
- DB runtime roles: neither V0202 nor V0203 adds a DELETE row for api_rw on app.device_lab_exemption to app.db_role_grant (api_rw gets SELECT, INSERT and UPDATE by wildcard, DELETE only per listed table). Today the runtime-role switch is OFF in infra/params (stage and prod say 'OFF until api_rw has the DELETE grants'), so nothing breaks now; once it is switched on, DELETE /v1/admin/devices/{id}/lab-exemption would fail with permission denied and a grant could not be withdrawn. Add the grant row (and list it in docs/requests/db-runtime-roles-gaps.md) before that switch.
- ARON_LAB_GRANT_KEY is read by Settings but is not wired anywhere in infra/ or .github/ in this range, so on a deployed server the PUT answers 409 until someone adds the secret. Also, a key that is set but unreadable (not PKCS#8 base64, or not P-256) silently counts as 'not configured' with no log line (not even a key-free one), and an empty/odd public API URL gives the same 409 with the message 'the server has no signing key', which points operators at the wrong cause.
- DeviceService.grantLabExemption maps every IllegalArgumentException from grantRow (including one thrown by the signer or the audit callback) to 404 'no such device'. The inputs are validated before, so this is only a misleading answer in an unexpected failure, not a wrong grant.
- After the write, grant and revoke answer with getDevice(), which reads db.readJdbi. With a read replica (final account) the response can show the old state for a moment. Same pattern as the existing changeState route; no replica exists at pilot size.
- The revoke audit row carries no 'before' (who granted it, until when), so the audit log alone does not say what was withdrawn; the grant row has those facts. The grant audit is fine (days, expiry, note, no token).
- Withdrawal reaches a phone only with its next FULL bundle (a delta answers 410 and the phone then refetches). An SR phone that fetches its bundle once a day keeps a revoked grant until then or until expiry. The code comments and runbook say this honestly; worth keeping in the owner-facing wording.
- RiskSignals shared phone: disambiguate() switches the subject id from '<device uuid>' to '<device uuid>#<user id>' only once a second rep has the same code on that phone that date. If rep A was evaluated alone at 10:00 and rep B shows up at 14:00, the 10:00 row for A (plain uuid) stays next to the new 'uuid#A' row: a duplicate signal for A that day, and a reviewer status set on the old row does not carry over.
- RiskSignals fromIntegrityEvents de-duplicates on (phone, at, flags) BEFORE grouping by user, so two reps reporting an event with the identical millisecond and flags on one shared phone would count for only the first. Also the identity uses the timestamp string, so the same instant written two ways (with and without .000) would count twice. Both are edge cases.
- Events are now dated by the phone's own 'at' (Dhaka date), and the job only evaluates today and yesterday. An onset whose report arrives two or more days late, or whose 'at' comes from a wrong phone clock, is stored in the status report but never becomes a risk row. The 7-day read window only helps if someone re-runs evaluateDay for the old date. Malformed elements are skipped with a count in a warn log (no data), which is an acceptable trace.
- GeoFix.signals is capped at 16 codes at ingest and the phone can produce 15 today; a record with more is refused schema_invalid (this hits the visit/memo that carries the fix). SpoofCodesTieTest ties the upload list to the enum but nothing fails the build if the enum grows past 16.
- The integrity-events query reads every status report of an 8-day window (that has events) for each of two dates every 15 minutes. Fine at pilot size; needs a look before fleet size.
- V0201 to V0203 are still called 'provisional, renumbered at landing' in their comments and in docs/status. Renumbering is only safe if no database outside lane CI has applied them; if the dev database has, the renumber must not happen (forward-only rule).

## lab-grant-phone verdict=pass
SUMMARY: Android lens, read-only code review of 0f69f3b904..90e795e228 (nothing built or run). I found no blocking defect.

What I tried to break and how it held:
- Replay from another device: the token's device uuid must equal this phone's uuid exactly; copied files do not verify. Holds.
- Another environment: the audience must equal the API host of this build (set from apiClient.origin in Application.onCreate before IntegrityGates.install in all three apps; a test pins the order). Holds.
- Old, cached, prefetch or delta bundle: the grant is taken only in BundleDownloader.fetch after a day bundle returned APPLIED; prefetch promotion, 304, OLDER_IGNORED, failed and delta paths never call it. Holds.
- Expired grant plus clock set back: accept() needs server_time within 15 minutes of the phone clock and judges expiry on server time; a large step back clears the store and the persistent iat/wall marks stop an older token or a rolled-back clock from bringing it back. Holds, except the impractical under-5-minute creep after a reboot (low).
- Signature: P-256 key check on load, SHA256withECDSA, any parse or verify error gives null; empty or wrong key means not configured, so nothing is accepted or honoured. The committed key resource is empty.
- Revocation: only an applied full day bundle without the value revokes; offline it lasts until expiry (at most 7 days locally, 14 on the server). Bounded, noted as a low.
- Mock location under a grant: the geo spoof checks do not read the gate or the grant at all, so a mock app is still refused.
- Normal phones: the grant files and the device uuid are read only when a developer flag is on; no network and no sensor was added to the sale path. An applied day bundle adds one small file write.
- Signals lows: probe cache is dropped after a mock-app or test-provider refusal; null vs [] is carried through to the record; event ack is now by identity and round-trips.

Not verified: no build or test run (no Android SDK); strict-DER behaviour of the phone's crypto provider (relies on the unit test and the platform); the server's 410-on-delta route after a grant or revoke and the admin permission on the grant endpoints (server lens); whether app TLS settings stop a user-installed CA from replaying a bundle; whether every app token carries a deviceId; gate coverage of activities beyond the existing source-scan test.

LOWS:
- Clock set FORWARD traps a lab phone: VerifiedLabExemption.touchWall() raises the persistent 'wall' mark to whatever the phone clock shows (also on normal phones, on every applied day bundle without a grant). If a tester moves the clock forward (a common business-date test) and back again, accept() refuses every later grant (now < marks.wall - 5 min) until the real time passes that mark or the app data is cleared. Fail-closed, but the runbook should say so, or the mark should be capped against server_time when a fresh bundle arrives. File: android/core-system/src/main/kotlin/com/aktcl/aron/core/system/integrity/LabGrant.kt.
- Clock creep after a reboot: LabExemptionStore.isActive only voids on a step back of more than 5 minutes, and the monotonic 'held too long' check applies only inside the boot in which the grant was stored. A holder of a real grant who reboots and then keeps nudging the clock back by under 5 minutes can hold the wall clock still and stretch the grant past its expiry. Needs a manual clock change every few minutes and makes every record timestamp wrong (visible on the server), so impractical, but it is not 'cannot be extended'. A re-anchor of elapsed/boot on each successful read after reboot would close it. File: .../integrity/LabExemption.kt.
- Offline bound is real but long: a withdrawn grant stays honoured on a phone that never loads a full day bundle until min(token exp, 7 days after the last accept); the server allows up to 14 days and each fresh bundle re-arms the 7-day local cap. This is an honest limit, and docs/runbooks/lab-exemption.md should state it in those words (revoke is not immediate for an offline phone).
- Freshness window is measured after the whole download: server_time is stamped when the bundle head is built, but labGrant() runs after all pages are fetched and applied. An AMO/TSO bundle on a slow link that takes over 15 minutes means the grant is silently not accepted (fail-closed; the next full bundle fixes it).
- False withdrawals are possible by design (fail-closed): any applied full day bundle without the value revokes. That includes a token signed in for a session whose principal has no deviceId (BundleService.labGrant returns nothing), so a lab phone that signs in before it is bound/enrolled loses its grant. Worth one line in the runbook.
- As committed, android/core-system/src/main/res/values/lab_grant.xml holds an EMPTY public key, so no release build in this range can honour any lab grant; the lab exemption of rule 17 only starts working after the owner runs tools/make-lab-grant-key.sh and the key is committed. Correct fail-closed default, but the status note should say plainly that the ADB device walks on release builds are not yet possible.
- Comment drift: IntegrityGates.LAB_GRANT_KEY says 'contract 1.19.0' while the server constant says 1.20.0; IntegrityGateController still carries the dead labExemptionHonoured=false parameter and its outdated comment.
- FixManager: when the spoof check throws, signals is now null (unknown) and hardSpoof is false, so only the platform loc.isMock flag refuses the action in that case. Acceptable (unknown is sent as unknown, server re-checks), but a thrown check is not surfaced anywhere on the phone.
