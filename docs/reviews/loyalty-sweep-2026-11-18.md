# Lead review: Loyalty follow-up round, waiting-child sweep (aa619a558..55ca113f)

Reviewed 2026-11-18 by the lead (Opus pass, two lenses, each blocking finding checked by three refuters; fewer than 2 of 3 upheld counts as a low). Read from code only (the reviewers could not start a database).

## sweep-correctness verdict=fail
SUMMARY: Lane lane/portal-loyalty-api-c at 55ca113f, delta aa619a558..55ca113f: fail, with two blocking findings.

1. Wrong waiver. IngestService.sweepOne releases a waiting child by calling acceptQuarantined on the child itself. That makes release = the item's code, which is the FIRST parent's code, and it applies even to a child from another uploader or device. The reviewer's accept deliberately gave such a child no override. So the job waives checks no human waived: the owner check on the later parent, visit kind, reach, and the device gate and signature. Concrete case: a TSO collection whose visit turns out to be another user's is stored and told accepted.

2. No audit row. An automatic release writes nothing to audit_log. Every reviewer accept (OpsApi.resolve) writes a hash-chained audit row, and other jobs use via="job". The closed, mutable sync_quarantine row with the system resolver and note is not a tamper-evident record.

What holds up: the job's lifecycle and wiring (API role only, stopped on shutdown, no overlapping passes, config read every pass, env switch), one transaction per item, the advisory lock plus SKIP LOCKED at database level against a reviewer or a second replica, idempotent resends, scope on waiting_count, the additive contract, migration V0207 (plain insert, nothing that can raise, shipped migrations untouched), and the SchemaV1aTest key registration, which follows the established pattern and is not a loosening.

Lows: head-of-line starvation under the batch cap, silent permanent waiting when the child's own check fails, the marker being a detail-text prefix, shutdown always taking the 20 s grace, and stale "worker" wording.

Not checked: the tests were not run, because a local PostgreSQL could not be started in this sandbox.

### BLOCKING upheld=3/3: The sweep waives the first parent's hold code for a child from another uploader, which the reviewer's accept never waived
WHERE: backend/sync/src/main/kotlin/com/aktcl/aron/backend/sync/IngestService.kt:628 (sweepOne calls acceptQuarantined(id, ...) on the child itself). See also :410-424: ctxOf(item) computes `same` = child vs itself, which is always true, so release = item.code, and item.code is the FIRST parent's code (markWaiting keeps it).
WHY: In the reviewer's accept (:419-422) a child from another uploader or device runs with release = null. The comment there says "a child of another uploader gets no override of its own checks". When the sweep later releases that same child, acceptQuarantined treats the child as the reviewed item, so ctx.release = the parent's code. The waiter only ever reached step 9 (parent missing), so every check after it never ran in the reviewer's pass. With a scope code, the sweep now waives those checks: the owner check for the later parent field (:1379), the visit-kind policy (:1397) and the step-5 reach re-check on the business date (:1199). With a device code, it waives the TSO device's gate and the record signature at sweep time. This is a job accepting what only a human may accept.
SCENARIO: 1. An SR memo M is quarantined with scope_out_of_reach.
2. A TSO's due_collection against M (parents = against_memo_client_uuid, then visit_client_uuid V; TypeRules.kt:32) is held as "parent M is quarantined (scope_out_of_reach)".
3. The reviewer accepts M. The collection re-runs with release = null: the TSO's reach passes, and the cross-user rule on against_memo passes. V is not stored yet, so the outcome is parent_missing and the collection is marked waiting.
4. V later syncs, and it is another user's visit (or the TSO's reach changed meanwhile).
5. The sweep finds V STORED (awaitedState does not check the owner) and runs acceptQuarantined(collection) with release = SCOPE_OUT_OF_REACH. scopeAccepted is true, so "visit_client_uuid V belongs to another user" (:1380) is skipped. The money collection is stored and the phone is told accepted, with no human decision.
6. Under the reviewer path, the same record would have gone back into review.

Fix: give acceptQuarantined an override parameter. The sweep passes the first parent's code only when the child's user and device match the accepted parent's item (its uuid is in the detail), and passes null otherwise.

### BLOCKING upheld=2/3: An automatic release writes no audit_log row, while the reviewer's accept and other jobs do
WHERE: backend/sync/src/main/kotlin/com/aktcl/aron/backend/sync/IngestService.kt:621-636 (sweepOne, STORED branch); compare backend/analytics/src/main/kotlin/com/aktcl/aron/backend/analytics/OpsApi.kt:368-376.
WHY: Every reviewer resolve writes an AuditLog.write row for entity 'quarantine' (before status open, after accepted, reason). That row is hash-chained, the database refuses UPDATE and DELETE on it, and AuditLog.verify checks it. AuditLog explicitly supports an actorless via = "job" row (AuditLog.kt:25-27), and jobs use it: ConfigService.kt:404 for a scheduled config apply, AutoFinalSubmitJob via "job". The sweep only closes the sync_quarantine row (closeItem), and that row is mutable: closeItem is a plain UPDATE, and quarantine()'s re-open path rewrites resolved_* columns. That is not a tamper-evident record. The release stores money and points records and tells the phone "accepted", and only a mutable row records it.
SCENARIO: 1. The sweep releases a waiting due_collection or gift_photo. It is stored, and the phone's feed says accepted.
2. app.audit_log has no row for it, so audit_verify and the audit screen show nothing.
3. Every reviewer-released sibling of the same family is covered by the reviewer's audit row; this release is not.

Fix: in the same transaction, write AuditLog.write(h, null, "quarantine", id, "accept", before {status: open, code, client_uuid}, after {status: accepted, by: waiting_sweep, awaited: uuid, first_parent: uuid}, note, null, via = "job").

LOWS:
- Starvation: sweepWaiting takes `ORDER BY id LIMIT batch` with no last-checked column (IngestService.kt:588-590). Items that can never be released stay open and keep their place at the head: those hinted as refused (left until a reviewer discards them), those whose parent never syncs, and those whose parent is stored but whose own later check fails (ERR_REQUEST_STATE, rolled back each pass). Once at least `batch` (200) of these pile up, newer releasable items are never examined. Nothing is lost and nothing is finalised wrongly, but releases stop until a reviewer acts. The warning log reports how many were skipped but does not fix it. Suggest a keyset cursor across passes, or ordering by a last-checked time.
- An item whose awaited parent is stored but whose own post-parent check fails stays `waiting = true` and `waits_for_refused = false` forever, and the queue does not say why (sweepOne :630-632 swallows ERR_REQUEST_STATE silently). The reviewer is misled that it is only waiting.
- The `waiting` marker is a prefix in the free-text detail column, not a typed column (QuarantineWaiting.kt). Today every quarantine detail is built by the server: field names, validated uuids, codes. No phone-controlled or reviewer-written string can start with the prefix (reviewer text goes to resolution_note). It is fragile if a future handler puts payload text at the start of a detail.
- awaitedState treats any accepted or voided registry row, or any row in the parent table, as STORED without checking owner or type (:553-555). The release itself re-checks owner and type, except where the override above waives them; the first blocking finding covers that case.
- Shutdown: ScheduledThreadPoolExecutor keeps executing delayed tasks after shutdown() by default. The next pass is always pending, so stop() normally waits the full 20 s grace before shutdownNow (WaitingChildSweepJob.kt:85-90). That is a slow stop, but correct: tick() returns null once stopped.
- Stale wording: the contract descriptions (QuarantineItem.waiting, waits_for_refused) and Wiring.ingestService's KDoc say "the worker" releases or builds the sweep. It runs in the API process with the API role.
- SchemaV1aTest: the three keys are appended to the `ruled` set with a decision reference, the same way earlier lanes registered their keys (exact-equality assertion). This is registration, not a loosening. The AmoManualContractTest version pin bump to 1.21.0 is the standard pattern. The contract change is additive: waiting_count is not required, and all three new item members are optional.
- Checked and OK. Wiring: the job is built in production and started only by Main's API role; it is stopped on ApplicationStopped before the pools close, and tests start nothing. Config: read every pass, the env switch is honoured, and the AtomicBoolean prevents overlapping passes. Connections: one transaction per item, borrowed per item, a failure counts one item and the pass continues. Locking: the per-uuid advisory lock, then the row FOR UPDATE SKIP LOCKED, are database-level. The two-sweeper test uses separate connections from a shared pool, so it really exercises the database locks. There is no lock-order cycle with the reviewer's resolve (row FOR UPDATE, then the advisory lock inside release). closeItem's `status='open'` guard prevents a double close. Resends: duplicate via the registry; nothing is doubled. waiting_count uses the same reach predicate as the list. matchBackfill: its children now wait as required.
- Could not check: I could not run the lane's sweep tests. A local PostgreSQL 16 would not start (the scratchpad path is not reachable by the postgres user under the sandbox), so no gradle run. Not verified at runtime: Jdbi 3.55's reuse of the thread's handle for the nested inTransaction inside sweepOne, which the savepoints depend on. acceptQuarantined's KDoc documents this reuse. Not inspected: how each record handler's checkEarly or late checks use IngestRecord.release (the extent of the waiver beyond the core checks).

### BLOCKING upheld=2/3: Automatic release by the sweep writes no audit_log row, but every reviewer accept does; the only record is a closed sync_quarantine row, which can be edited and is not chained
WHERE: backend/sync/src/main/kotlin/com/aktcl/aron/backend/sync/IngestService.kt:628 (sweepOne calls acceptQuarantined directly); compare backend/analytics/src/main/kotlin/com/aktcl/aron/backend/analytics/OpsApi.kt:368-375 (resolve writes AuditLog.write(entity 'quarantine', action accept, before/after, reason)); DECISIONS D-LOY-API-29 says 'no audit_log row is written by the sweep'
WHY: acceptQuarantined writes no audit row of its own. In the reviewer path the caller (OpsService.resolve) writes it. The sweep skips OpsService, so a record released into the money and points tables (due_collection, gift_photo, redemption) leaves no audit_log entry. app.audit_verify (V0010:319) checks only the hash-chained audit_log. app.sync_quarantine is plain UPDATE-able by api_rw, so the 'aron.system' resolver plus the note is neither append-only nor tamper-evident. The project already has a pattern for job actions: AuditWriter/AuditLog.write(..., via = 'job') in ConfigService.kt:404 (scheduled cfg apply), AutoFinalSubmitJob.kt:119 and MigrationPreflight.kt:160. The brief's own rule applies: reviewer accepts write audit_log and the job does not.
SCENARIO: A waiting due_collection of 1,000 milli-taka (BackfillMatchTest new case) or a gift photo is released at 03:00 by the sweep. Later someone with api_rw access edits resolved_by_user_id or resolution_note on that sync_quarantine row, or the row's history is questioned. audit_log has no entry for entity 'quarantine' / that id, audit_verify reports the chain intact, and nothing tamper-evident shows that an automatic actor accepted a held money record. Fix: in sweepOne, after a successful acceptQuarantined and inside the same transaction, write AuditLog.write(h, null, 'quarantine', id, 'accept', before {status open, code, client_uuid}, after {status accepted, action 'sweep_release', awaited uuid}, note, null, via = 'job'), and add a test that asserts the row.

LOWS:
- Review-queue scope is fine: waiting_count (OpsApi.kt:324-327) uses the same reach predicate as the item list (route_id in dim_geo for reach.zoneIds; national sees everything, including items with no route). It ignores the status, code, zone, date and cursor filters, as the contract says. The endpoint is still limited to QUARANTINE_READERS = ADMIN, SUPERADMIN, SUPPORT (OpsApi.kt:385). So Brand User, Wing Manager, DMO and TSO get 403 as before, and SR and AMO have no portal login. Per-module admin grants are not checked on this route, but that is unchanged and outside this delta. waits_for_uuid exposes nothing new: the same uuid is already in the item's payload and detail, which the caller could already read.
- Cost of the count query: there is no index for `detail LIKE 'waits for another parent:%'`. The partial index sync_quarantine_open (business_date, code) WHERE status='open' (V0008:128) bounds the scan to open rows, but every queue page load and every sweep pass (two queries per minute per replica) filters all open rows on detail. This is fine at pilot size. At fleet size, consider a partial index or a column for the waiting marker.
- waits_for_refused is only a hint. It is set when markWaiting runs or on a later sweep pass, and it is never cleared. If a refused parent is later stored, the sweep still releases the item, because awaitedState is checked fresh and only the REFUSED branch reads the hint. Between those two points the flag is stale. The contract text 'never released by the worker' is stronger than the code; reword it to 'not released while the parent stays refused'.
- markWaiting fallback (IngestService.kt:522): when the parent_missing detail does not match `<field> <uuid>`, the item is marked waiting with no awaited uuid. waits_for_uuid is then null and sweepOne returns 0 every pass. The item is never auto-released, though not lost (a reviewer can still accept it). The free-form o.detail is also copied into the item detail, so the 'field names and uuids only' claim depends on every handler's detail being clean. Consider marking waiting only when an awaited uuid was parsed.
- matchBackfill waiting children (IngestService.kt:786): in matchBackfill they ran with no override. The sweep releases them through acceptQuarantined with release = item.code = memo_no_duplicate. I checked that this waives nothing real: MEMO_NO_DUPLICATE is used only by the manual-entry batch check (lines 330/349) and by RecordWriter mapping the DB unique constraint (RecordWriter.kt:149), which no override can bypass. No handler check returns it; the only handlers that read rec.released are the gift handlers, for REACH and their own codes. So a real duplicate memo on the child cannot be waived. Still, it is a different override from the match path. A comment or a test pinning this would help.
- twoSweepersOnTheSameItemReleaseItOnce (GiftPhotoRecordsTest.kt:782) asserts released >= 1. The code allows exactly 1 (the second release gets ERR_REQUEST_STATE and returns 0), so assert == 1. The other assertions (closed once, stored once) do hold.
- Tests that are missing: no non-national caller (a SUPPORT or ADMIN with zone reach) checks that waiting_count and the items stay inside reach; no case where a waiting child also has its own hold code; no audit assertion for the sweep.
- Hygiene: the Wiring.ingestService KDoc (Wiring.kt:204) still says 'the worker builds the same one'. Slices, INDEX.md and web/src/contract/openapi.d.ts match the yaml. AmoManualContractTest was updated with the version history (a registration, not a loosening).
