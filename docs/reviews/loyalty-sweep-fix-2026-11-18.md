## waiver-and-release verdict=fail
SUMMARY: Head 8a90f1b41ed1 of lane/portal-loyalty-api-c, read from code only (nothing built or run).

Both earlier blocking findings are fixed as the lead ruled. The sweep now calls releaseHeld directly with the override stored on the child at wait time (null for another uploader or device and for matched-backfill children), runs every later check, turns a child's own failure into an ordinary held item, keeps waiting on parent_missing, and writes a hash-chained job audit row in the same transaction. Order is least-recently-checked first. Locking and idempotency hold for two sweepers, retries and a crash.

One new blocking defect: the typed waiting marker is never cleared when an item is closed, and quarantine() re-opens the same row on a resend after return_to_device without clearing it. A returned waiting child that is held again for a fresh reason (late after Final Submit, too old, or the same code as its stale waiver) is then auto-released by the sweep, because reviewed = true skips the late and too-old checks. That stores a money record no reviewer accepted.

Not verified: the tests were not run; Jdbi savepoint behaviour, the real deadlock behaviour under load, the migration on a database with train-115 waiting rows, and each record handler's own use of the override were not exercised. ### BLOCKING upheld=3/3: The waiting marker survives a close and a re-open, so the sweep auto-releases a freshly held record that no reviewer accepted
WHERE: backend/sync/src/main/kotlin/com/aktcl/aron/backend/sync/IngestService.kt: quarantine() ON CONFLICT ... DO UPDATE (about line 1975-1990) re-opens the same row without clearing waiting_since / awaited_uuid / accepted_parent_uuid / waiting_release_code; closeItem (about 927) and backend/analytics/.../OpsApi.kt resolve (about line 361, discard and return_to_device UPDATE) do not clear them either. Only markWaiting and clearWaiting ever write these columns. Read by sweepWaiting/sweepOne (about 623-697), which select on status='open' AND waiting_since IS NOT NULL.
WHY: A reviewer can return a waiting item to the device (OpsApi allows return_to_device on any open item). The row becomes discarded but keeps its typed marker. When the phone sends the record again it is judged from scratch (process(): 'quarantined' + returnedWithoutOpenItem). If it is held again, quarantine() re-opens the SAME row (conflict on client_uuid + payload hash): status back to open, new code and detail, the old marker still set. The sweep now treats this ordinary fresh hold as a waiting item. Once the old awaited parent is stored it calls releaseHeld with reviewed = true and the stale waiting_release_code. reviewed = true alone skips the too-old business-date check (line ~1194) and the late-after-Final-Submit hold (line ~1449), and the stale code waives a fresh hold of the same code for a same-uploader child. So the job stores a record whose current hold no human ever judged, after the reviewer's last decision was 'return', not 'accept'. This breaks the ruling 'never more than the reviewer's accept' and the audit row then records a job accept of a hold the reviewer never saw. The queue also shows the re-opened item as waiting with a wrong waits_for_uuid.
SCENARIO: 1. SR memo M is held (scope_out_of_reach). A due_collection C against M is held with it. 2. Reviewer accepts M; C's visit V is not synced, so C is marked waiting (typed columns set). 3. Reviewer returns C to the device (return_to_device). Row is discarded, marker columns stay. 4. V syncs. Days later, after the route day got its Final Submit (or past the back-date window), the phone resends C. It is processed fresh and held for review as late (day-lock hold or business_date_out_of_window). quarantine() re-opens the same row; waiting_since is still set. 5. Within one sweep interval (60 s) sweepOne finds it, sees V stored, runs releaseHeld with reviewed = true: the late / too-old check is skipped, the money collection is stored, the item is closed by aron.system and the phone is told accepted. No reviewer accepted the late row. Same path for a same-uploader child re-held under the code equal to its stale waiting_release_code (for example a device hold). Fix: clear the six marker columns when an item is closed (OpsApi discard/return, closeItem) and in quarantine()'s DO UPDATE; add a test (return a waiting item, resend held again, tick: not released, not shown as waiting).

LOWS:
- B1 from the last review is fixed as ruled: the sweep passes the stored waiting_release_code (written at markWaiting from ctxOf(child).release, i.e. the parent's code only for same user and device, null otherwise; matchBackfill children get null). Grandchildren released with the item get the override only if they match the item's user and device, which is never more than the reviewer's pass gave. Old-form rows are backfilled with a null code.
- B2 is fixed: AuditLog.write(via='job', actor null) runs on the same handle and transaction as the release, only when the item was stored; the test checks the row and audit_verify.
- A poison item keeps the head of the queue: when sweepOne throws (the transaction rolls back) or returns early (aron.system missing, heldItem null), waiting_checked_at is not updated, so the item stays first (NULLS FIRST or oldest). If at least 'batch' such items exist, releasable items are again never reached. Stamp waiting_checked_at in a separate small transaction on failure.
- Own-hold branch: if the fresh hold is 'parent X is quarantined (code)' (another parent is itself in review), the item's detail becomes 'a check of its own held it ...: parent X is quarantined (...)'. heldChildren matches only details that START with 'parent X is quarantined (', so accepting X later will not release this child; it needs its own accept. Not lost, but orphaned from its parent.
- When the awaited parent is stored but the release still ends parent_missing (a third parent, or a registry 'voided' parent that the parent step does not take), the item keeps waiting with the old awaited_uuid. Every pass runs a full release and rolls it back, and the queue shows a parent that is already stored.
- The sweep still reads the awaited FIELD name from the free-text detail (QuarantineWaiting.field); only the uuid is typed. If the detail lacks it, the parent-table check is skipped and only the registry is consulted. Store the field in a column too.
- The stored waiver has no age limit: a same-uploader child keeps the parent's scope or device override until the awaited parent arrives, however long that is and whatever changed for the user or device since. This matches the lead's ruling ('what the accept carried at that time') but is worth a written note.
- V0207 backfill: deterministic and safe (WHERE guards both regexes, casts only matching text, nullable columns, no waiver). Old-form rows that do not match (awaited parent not named) stay ordinary held items whose detail still says 'waits for another parent'; the queue shows them as not waiting. awaited_refused is not backfilled but is refreshed at the first pass. No test exercises the backfill.
- Test realism: theSweepGivesATsoCollectionNoWaiver... builds the TSO child by SQL UPDATE of user_id/device_id/code/detail on a row uploaded by the SR, not by a real TSO upload. It does exercise the null-override path and the own-hold outcome. The two-sweeper assertion was tightened from >= 1 to == 1. No test is disabled or loosened; SchemaV1aTest only registers the three keys.
- Missing tests: return_to_device or discard of a waiting item followed by a resend; a reviewer's accept racing the sweep on the same item; a non-national reviewer's waiting_count.
- Concurrency read from code only: sweep takes the uuid advisory lock, then the row FOR UPDATE SKIP LOCKED with status re-checked; one transaction per item; closeItem guards status='open'; a second sweeper, a retry or a crash cannot double a record (the registry makes the second attempt a duplicate). Child rows inside heldChildren are locked with a blocking FOR UPDATE; a deadlock with a reviewer would be detected by PostgreSQL and counted as one failed item, retried next pass.
- Scope: the sweep has no caller scope; each record runs as its own uploader with that user's reach on the business date, so it cannot store across territories what the uploader could not. waiting_count uses the list's reach predicate.

### BLOCKING upheld=3/3: A waiting item that is returned to the device and held again keeps its typed waiting marker and stored waiver, so the sweep can release a fresh hold that no reviewer accepted
WHERE: backend/sync/src/main/kotlin/com/aktcl/aron/backend/sync/IngestService.kt: quarantine() re-open upsert (about :1975-1987, ON CONFLICT (client_uuid, payload_sha256) DO UPDATE sets code, detail, status='open' and clears the resolved_* columns but not waiting_since, awaited_uuid, accepted_parent_uuid, waiting_release_code, awaited_refused, waiting_checked_at); closeItem (:927) and backend/analytics/.../OpsApi.kt:362 (discard / return_to_device UPDATE) also leave the six columns set; sweepWaiting/sweepOne (:625, :647-672) select only on status='open' AND waiting_since IS NOT NULL and pass waiting_release_code as the override. Columns from db/migrations/V0207__cfg_waiting_sweep_keys.sql.
WHY: This is a regression of this fix round. At 55ca113f the marker was a prefix of the detail text, and the re-open upsert overwrites detail, so a re-opened item was never waiting. Now the marker is six columns that nothing clears when an item is closed or re-opened. OpsService.resolve allows return_to_device on any open item, waiting ones included. The sync path (IngestService :1171-1178, returnedWithoutOpenItem) then judges the phone's resend again, and if it is held again quarantine() re-opens THE SAME row (same client_uuid and payload hash). That row is now open with a new code and detail from a fresh hold, but still has waiting_since and the old waiting_release_code. The queue shows it as waiting (toDto, waiting_count) and the sweep treats it as waiting. When the old awaited parent is stored the sweep calls releaseHeld with the stale override. If the fresh hold has the same code as the stored waiver, the check is waived and the record is stored and the phone told accepted, with an audit row saying the job released it. The reviewer's last decision on that item was 'return to device', not accept, so this is more than 'exactly what the reviewer's accept carried for that child at that time': the wait that waiver belonged to ended when the reviewer closed the item.
SCENARIO: 1. An SR's memo M is held scope_out_of_reach. The same SR's due_collection C (same device; parents M then visit V) is held as 'parent M is quarantined (scope_out_of_reach)'. 2. The reviewer accepts M. C re-runs with the waiver, V is not stored, so C is marked waiting with waiting_release_code = scope_out_of_reach. 3. The reviewer resolves C with return_to_device. The row becomes discarded; the six waiting columns stay. 4. V syncs and is stored (or is accepted by a reviewer). The phone sends C again with the same payload. It is judged again with no override; its own reach check on the business date fails (the same reach problem M had), so quarantine() re-opens the same row: status open, code scope_out_of_reach, new detail, waiting_since and waiting_release_code unchanged. 5. Next pass: sweepOne finds the row, awaitedState(V) = STORED, releaseHeld(override = scope_out_of_reach) waives C's own reach check, the money collection is stored, the item is closed by aron.system and the phone is told accepted. No reviewer accepted this hold. Milder variant with a null waiver: the re-opened item is shown and counted as waiting with a stale waits_for_uuid; if the old awaited parent is never stored it stays labelled waiting forever although it is an ordinary held item. Fix: set the six columns to NULL/false in the re-open upsert (and, to be safe, in closeItem and the OpsApi discard/return UPDATE), and add a test: waiting item, return_to_device, resend held again, tick() releases nothing and the queue says waiting=false.

LOWS:
- Audit row content is good but does not record the waiver: after = {status accepted, action sweep_release, by waiting_sweep, awaited, first_parent}. Adding the carried override (waiting_release_code or null) would let the tamper-evident row show whether a check was waived; today that is only in the mutable item row, and closeItem does not keep it readable either.
- Children of the waiting child that are released in the same releaseHeld call are closed by aron.system with 'released with parent <uuid>' and get no audit row of their own (same as the reviewer path, where one row covers the family). Acceptable, but say so in D-LOY-API-30.
- A waiting item whose release throws a non-ApiProblem, non-transient exception every time (a handler bug, a constraint error) rolls back whole, so waiting_checked_at is never stamped and it keeps the head of the order. One such item costs one slot per pass; a batch-full of them would starve the rest. The pass itself continues (failure isolation holds). Consider stamping waiting_checked_at in a separate small transaction on failure.
- The failure log line gives only the exception class name (good for privacy, thin for diagnosis); if the first listing query fails (database down) pass() logs a full stack trace every interval.
- Every pass writes one UPDATE (waiting_checked_at, non-HOT because the column is in the partial index) per examined waiting item, on every replica, every minute, even when nothing changed. Fine at pilot size (a handful of items, one connection at a time, two cheap queries when nothing waits); at fleet size with many long waits it is steady WAL churn. There is no pass-level lock, so N replicas each examine every item; correctness is kept by the per-uuid advisory lock (blocking) plus the row FOR UPDATE SKIP LOCKED and the status='open' guards.
- When the stored awaited parent is there but the release still answers parent_missing for ANOTHER parent, the item keeps waiting with the old awaited_uuid: the queue shows the wrong awaited parent and the sweep re-runs a full release attempt (rolled back) every pass.

PostgreSQL would break this as a deadlock and one side retries/fails. The same pattern already exists between two reviewers (pre-existing), the sweep only makes it more frequent. Not verified at runtime.
