# Lead review: android-sr-programmes round 2 (dfabe13e..ebcc0ee8): gating, AsthaLocal, fix round, slice 5

Reviewed 2026-11-18 by the lead (Opus lens with three refuters per blocking finding; Sonnet UI check). Read from code only: nothing built, run or walked on a device.

## programmes-gate-and-numbers verdict=fail
SUMMARY: Read-only review of origin/lane/android-sr-programmes at ebcc0ee8 against dfabe13e and the integration merge 29e8d86f3. Nothing was built or run.

What holds: the check-in gate is correctly in place for every programme write (inside the transaction, both record types, refused after check-out, replay cannot write, both write screens in the gated list, no write reachable from an ungated screen). The merge kept train 118 exactly (only additions on top of 29e8d86f3 in SrApp.kt and CaptureRepository.kt). Room stays at 10 with no schema change; no contract or backend change. The Dhaka date fix and the single balance function are done. The gift_choice payload matches the server.

Two blocking defects:
1. Low 6 (AsthaLocal) uses astha_as_of as the cut-off. The contract says that field is display only. Because the phone's ack time is always later than the server's receipt time of the same memo, the last synced batch is counted twice on the Astha page after the next bundle refresh (a whole day's sales doubled for an SR who syncs once in the evening). The lane's own test encodes the wrong rule.
2. The new CONFLICT comparison includes balance_before_points, so the one real replay case (same basket after a kill, balance already reduced by the first save) is judged a conflict, the screen says nothing was deducted, and the next confirm writes a second redemption. Narrow window, but it breaks the idempotence the fixed uuid was there for.

Lows cover: zero-sale memos in the memo count, route rows taking memos of any route or outlet (and a server route-row figure that looks always zero), the tier taken from a localized label and from a different source than the server's, an uncaught re-read after save, clock-skew limits of the balance display, and wording of the gift state.

### BLOCKING upheld=3/3: Astha (low 6): memos already inside the server figure are added a second time, because the cut-off is astha_as_of instead of the bundle request
WHERE: android/feature-programmes/src/main/kotlin/com/aktcl/aron/feature/programmes/AsthaLocal.kt (delta: 'acked and ackedAt > astha_as_of counts'; insideServerFigure) ; test AsthaLocalTest.aMemoAckedAfterTheServerFigureIsStillAdded encodes it. Server side: backend/sync/.../BundleProgrammes.kt contentAsOf (astha_as_of = max(received_at, status_changed_at) of the month's memos at the sent outlets); phone ack time: android/core-sync/.../SyncEngine.kt line ~409 (now = phone trusted clock when the ack response is handled).
WHY: The contract (ProgrammesSection, ACHIEVEMENT RULE) says astha_as_of is display only and never part of the rule; the rule is 'add the memos NOT acknowledged when the phone SENT the bundle request'. AsthaLocal compares the phone's ack time with astha_as_of. astha_as_of is the server receipt time of the newest memo, and the phone always handles the ack AFTER the server stored the memo, so for the newest uploaded batch ackedAt > astha_as_of is the normal case, not the exception. Those memos are in the server figure AND are added again by the phone. The same wrong test makes an edit go wrong too (the old memo is judged 'not inside the server figure', so it is not taken out while the edit is added).
SCENARIO: SR sells 40 memos offline, syncs in the evening: all 40 are acked in one batch at 18:00:02 (phone clock), server received_at 18:00:01. The bundle is then refreshed: the server figures include the 40 memos and astha_as_of = 18:00:01. On the Astha page the phone finds 40 acked memos with ackedAt 18:00:02 > astha_as_of and adds them again: the outlet rows show the day's STD, value and memo count doubled. It stays doubled (also next morning, same month) until a later memo is synced and a newer bundle arrives, and then that later batch is the one doubled. Fix direction: decide by the bundle, not by astha_as_of: count a memo when it is still local, or acked after the bundle on the phone was built/requested (KEY_BUNDLE_SERVER_TIME, the same source LocalRedeemed already uses), and fix the test.

### BLOCKING upheld=3/3: Fix round: the same basket replayed after a kill is judged CONFLICT (balance_before_points is in the comparison), the screen says 'Nothing was deducted', and the next confirm makes a second redemption
WHERE: android/app-sr/src/main/kotlin/com/aktcl/aron/sr/ProgrammeStore.kt signature()/sameContent() (only confirmed_at is removed from the parent); android/app-sr/.../ProgrammeHosts.kt RedemptionHost (CONFLICT -> new uuid); string pg_redeem_conflict; Basket.plan puts the shown balance into balance_before_points.
WHY: The fixed uuid exists for exactly one case: the save was committed but the screen came back with the old uuid and the old basket (state saved while the save was running, process killed later). In that case the reloaded balance already has the first redemption subtracted, so the replay's balance_before_points differs from the stored one although the basket is identical. The comparison says 'different', the host mints a new uuid, and the text tells the SR nothing was deducted and to confirm again. Before the fix round this case ended harmlessly as 'saved'. Now it ends in a duplicate redemption (double debit of the outlet's points on the server). The window is narrow (app sent to background or screen off during the few milliseconds of the save, then process death), but it is the kill-and-relaunch case the definition of done names, and the message shown is untrue.
SCENARIO: Outlet balance 110, basket 50 points. SR taps Confirm and the phone screen goes off as the save commits (instance state saved with the old uuid and basket); Android later kills the process. On return the basket is still shown, balance now 60. SR confirms: recordProgramme returns false (uuid held), signature differs (balance_before_points 110 vs 60) -> CONFLICT, text 'Nothing was deducted. Confirm again'. SR confirms again with the new uuid: a second redemption of 50 is written and synced. Fix: leave balance_before_points (an informational figure) out of the comparison, as confirmed_at is; add a test for the same basket with a changed balance.

## programmes-slice5-ui verdict=fail
SUMMARY: Slice 5 is mostly sound. The gift list comes from the stored bundle with no network call. Locked, on-this-phone and refused states are shown. A refused choice can be redone with a new record. A double tap is one record (busy flag plus a fixed uuid, and a store that answers ALREADY_SAVED or CONFLICT). The chosen state survives kill and relaunch because it lives in Room (amo_record plus the outbox), so clearing app files loses nothing. The strings are in resources in both languages, with a font-2.0 layout and goldens added without touching any amo_ or tso_ file. Three blocking points: (1) the refusal text never shows the server's reason, only 'choose again'; (2) the pack category (match or lighter) is read from product-node codes that the seed data does not set, so on real data every brand falls back to 'packets'; (3) the lane's match-dozen assumption (pack_factor 12) is wrong, because the data model sets match pack_factor to 1 with the dozen as base unit. I could not build or run anything, and I could not see live data (only db/seed and the server code), so I did not confirm whether production product nodes have codes, whether the server's quarter label matches quarterOf, or how the screens look on a device.

### BLOCKING upheld=3/3: Pack unit rule never fires on real data: category is read from a product-node code that the seed does not set
WHERE: android/feature-programmes/.../AsthaModel.kt brandCategories() and packLine(); data in db/seed/02_products.sql (nodes inserted with level, parent_id, name, sort only; BundleService.kt sends product_node.code, nullable)
WHY: packLine() finds the category from the code of the category node ('match', 'lighter'). In the seed the category, segment and brand nodes have no code. Only SKUs carry category_code. The lane's test uses a hand-made tree with codes, so it passes while real data would give an empty map. Every brand then falls into the fallback and is shown as packets.
SCENARIO: A match brand on a seeded database: by_pack has pack_factor 1 and achieved 36 (dozens). The row reads '1 per pack: 36 packets' where the field counts 36 dozens. A lighter brand reads 'N packets, 25 per pack' where it should say boxes. The unknown-category fallback to packets is NOT safe for match and lighter: it prints the wrong unit word with a number that looks plausible. The bundle already has products.skus[].category_code and variant_id, so the category can come from the SKU. If production data has the codes set, this is invisible; I could not see the live database.

### BLOCKING upheld=3/3: Match-dozen rule is built on a pack_factor that does not hold
WHERE: AsthaModel.packLine(), strings pg_pack_dozens and pg_pack_dozens_loose, AsthaModelTest (AsthaPack(12, 36_000))
WHY: The lane assumed pack_factor equals pieces per dozen (12). The data model says otherwise. docs/34 s4.2: matches have base_per_pack 1, the dozen is the base unit. db/seed: match SKUs are 'dozen', 1. BundleProgrammes.kt sends by_pack.pack_factor = s.base_per_pack, and std_achieved is in base units (dozens for matches).
SCENARIO: Real match data gives pack_factor 1, std_achieved 36000 milli. The code shows 36 dozens (the number is right by luck) with the label '1 per dozen', which is nonsense. Any fractional dozen (e.g. 36.5) goes to the 'loose' branch and prints '0.5 pieces', but 0.5 is half a dozen (6 pieces). The test encodes factor 12 and expects 3 dozens from 36000, which is the opposite of what the server sends, so it proves the wrong model. Lighters (factor 25, base piece) and cigarettes (20 or 10, base stick) are correct. Bidi falls to packets with sticks, which is right.
