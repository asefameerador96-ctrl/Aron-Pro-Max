## record-layer-vs-server verdict=pass
SUMMARY: Read-only review of the slice-4 record layer at dfabe13e against the server at 39db6c734 (the lane's merge base is exactly that commit; nothing was built or run, no live server was called).

What matches the server, field by field:
- redemption, redemption_line and gift_choice payloads: member names, required sets, integer types and ranges are the same as contract/openapi.yaml (RedemptionPayload, RedemptionLinePayload, GiftChoicePayload) and the generated PayloadShapes. Optional visit_client_uuid and fix are left out, which the server allows. Points are integers, cash_mtk is integer milli-taka = cash_points x rate (cash is always 0 for now). Memo money is untouched.
- Envelope: built by the existing RecordMapping.amoRecord/outbox path (business date from the trusted Dhaka clock, route_id of the outlet's route, family = redemption uuid, parent rank 0, lines rank 1; server accepts rank 0..3).
- Signature: the server marks redemption as signedHeader; the phone's SyncEngine.SIGNED_TYPES already lists redemption and signs it with the same generic ProofStrings.record scheme as memo. No change was needed.
- Parents and order: the server parks a line whose redemption is not stored (parent_missing, retryable); the phone writes parent and lines in one outbox insert with rank order. The Final Submit lock lists (phone and server) already contain redemption and redemption_line, and recordProgramme names the type to the guard.
- Idempotence: one Room transaction for the amo_record rows and the outbox rows, keyed on the parent uuid; a replay returns false and writes nothing; the uuid is rememberSaveable and renewed only after a save; a busy flag stops a second tap. A partly written family is not possible. Server side upserts by client_uuid and the ledger posts once per client_uuid.
- balance_before_points = 0 when negative: informational only on the server (stored, never read).
- amo_record sharing: every existing reader filters by record type or by a visit's family uuid, LocalPurge treats the table generically, and the gates lane's 9->10 backfill touches only distribution_check_line and call_assessment_answer rows. No reader misreads the new rows. The gates lane's Send-again guard covers a redemption line through its generic family rule (rank >= 1, parent = family uuid), even though amoParent does not know the type.
- Existing record types: the diff adds one function and one constant to CaptureRepository and one new file; RecordMapping and every existing builder are unchanged, so existing payload bytes are unchanged. No Room schema change.
- The 9 tests in ProgrammeRecordsTest are real: they run CaptureRepository over an in-memory Room database and assert rows, outbox counts, family and rank, replay, all-or-nothing, totals, the quarter pattern and unknown members.

The one blocking point is merge order: the check-in gate lives on origin/lane/android-gates as a separate per-write call and per-screen list, and this lane's new write path and screen are in none of them, so the owner's rule would be bypassed after a clean merge.

Could not verify: a build or test run (no Android SDK here); real acceptance on the dev API (the lane itself marks screens 6 and 7 'server path not verified'); behaviour of the generic server insert on a foreign-key or CHECK failure (for example a programme_id the server no longer has); the claim that the gate is already on the integration branch (the head I fetched is still 39db6c734 without it; I compared against origin/lane/android-gates bc38c0ad instead). The fetch could not update the local ref for the lane branch (ref lock), but commit dfabe13e was present and was used by hash.

LOWS:
- ProgrammeStore.saveProgramme returns true whenever recordProgramme does not throw, including when it returned false because the redemption uuid is already stored, and it never compares the contents. In the normal replay (same basket) that is right. But if the app is restored with the old saved uuid after the first save was committed (process death or state save in the few milliseconds between the DB commit and 'uuid = newUuid()'), and the SR then changes the basket or the outlet and confirms, the new basket is dropped silently while the screen says 'saved on this phone'. Narrow window; suggest treating 'already stored with a different payload' as a failure or minting a new uuid.
- balance_before_points goes out as 0 when the phone's balance is negative. I found no server code that reads it (not in IngestService, LoyaltyLedgerJob, BundleProgrammes; only the DDL column with CHECK >= 0 and the shape list). The debit uses points_total only and the balance is recomputed from the ledger. So the server does not act on it; it is only a stored, signed figure that understates the overdraw. The contract minimum 0 forces this; the lane has already raised the question. A contract change (allow negative) would be the honest fix later.
- Each record of one basket gets its own meta() call, so the redemption and its lines carry slightly different captured_at, and confirmed_at comes from a third call. A basket confirmed exactly at Dhaka midnight could put the lines on the next business date than their redemption. Suggest building one CaptureMeta per basket and reusing it.
- A refused save (Sales Submit already done for the route-day, Final Submit lock, points_total above 100000 for a very large basket, cash rate config above 100000) shows only the generic 'could not save' text; the reason is swallowed by runCatching in saveProgramme.
- onConfirm calls metaProvider.meta, Basket.plan and store.redemptions() outside any catch; the screen's coroutine has try/finally only, so an exception there would crash the app rather than show the failed text.
- LocalRedeemed.points compares confirmed_at (phone clock, ISO text) with the bundle's server_time as strings. A redemption confirmed before the bundle was built but acknowledged after it is counted in neither figure until the next bundle, so the shown balance can be too high for a while (display only; the server balance is right). Also relies on both timestamps having the same text format.
- ProgrammePayloads.problem does not check redemption_line.points_total against the contract maximum 1,000,000; harmless today because the parent's points_total limit of 100,000 bounds every line.
- The server does not check points_total = cash_points + sum of lines for a redemption (MemoChecks.recordMismatch has no redemption case, though the contract text says arithmetic_mismatch). The phone checks it before writing, so phone records add up; noted as a server gap, not a lane defect.
- ProgrammePayloads header comment says contract 1.17.0 and the server-needs doc says 1.18.1; the branch is on 1.19.0. The three schemas are the same in 1.19.0.
- (demoted, upheld 0/3) Redemption bypasses the check-in gate once the gates lane is on the integration branch (clean merge, no test fails): The check-in gate is not inside the open-route-day guard that recordProgramme reuses. On the gates lane it is a separate call, requireCheckedIn(businessDate), added by hand to every operational write (visit, memo, due, recordAmo, skip, content view, request...), plus a screen list SR_CHECKIN_GATED and a tile list HomeTiles.OPERATIONAL = {STOCK, SALE}. recordProgramme is a new function, LOYALTY_REDEEM a new screen and the Loyalty tile is not in OPERATIONAL, so git merges both lanes with no conflict and none of the three gate layers covers redemption. The lane's status file already says the redemption entry must sit behind the gate when it lands, but nothing in code or tests enforces it. Note: at the integration head I fetched (39db6c734) the gate is not there yet, so on the lane's own base there is nothing to call; this becomes a defect at the moment both are on the integration branch. @ android/core-database/src/main/kotlin/com/aktcl/aron/core/database/repo/CaptureRepository.kt recordProgramme (lane dfabe13e); android/app-sr/src/main/kotlin/com/aktcl/aron/sr/SrApp.kt (LOYALTY_REDEEM); compared with origin/lane/android-gates bc38c0ad (CaptureRepository.requireCheckedIn, SR_CHECKIN_GATED, HomeTiles.OPERATIONAL)

## screens-1-3 verdict=fail
SUMMARY: Read-only review of slices 1 to 3 at dfabe13e. The structure is sound: reads are offline from stored sections, numbers are integer thousandths and milli-taka, strings and month names are in resources, and the Gift tile is hidden. I found two real defects. The Astha 'Data as of' date uses the UTC date, which is wrong for part of the Dhaka day (the tests use 10:00Z, so they miss it). The outlet points page also shows the bundle balance without subtracting this phone's own pending redemptions, so it disagrees with the redemption screen. I could not run builds, tests, the HardcodedStringScanTest or the goldens, and I did not open the golden images. I did not read core-rules Percent/Formats or AronChoiceChip. I read only slice 4's host and model code, as needed for the points-page finding, and did not review slice 4 itself.

### BLOCKING upheld=3/3: Astha 'Data as of' date is the UTC date, not the Dhaka date
WHERE: android/feature-programmes/.../AsthaScreens.kt (TargetBody, the pg_as_of line: Formats.digits(it.take(10), locale)) and AsthaModel.asOf
WHY: astha_as_of is a contract Timestamp (RFC 3339 in UTC, 'Z'), and the contract says it falls back to the Dhaka start of the month. The screen shows the first 10 characters of the UTC text. Between 18:00 and 24:00 UTC (00:00 to 06:00 Dhaka) that is the previous Dhaka date. The tests only use 10:00Z, so they cannot catch it.
SCENARIO: Bundle built with no memos yet this month: astha_as_of = 2026-10-31T18:00:00.000Z, which is 2026-11-01 00:00 in Dhaka. The page says 'Data as of 2026-10-31' on the first of the month. A memo ingested at 2026-11-17T19:30Z (Dhaka 01:30 on the 18th) shows the 17th. Fix: convert the instant to Asia/Dhaka before taking the date, and add a test with an evening-UTC instant.

### BLOCKING upheld=3/3: Outlet points page ignores this phone's own redemptions, so it shows a stale balance
WHERE: android/app-sr/.../ProgrammeHosts.kt OutletPointsHost (uses the raw LoyaltyModel.parse balance) versus RedemptionHost (subtracts LocalRedeemed.points)
WHY: The contract's loyalty rule is that the phone subtracts redemptions it has not yet had acknowledged. The lane's own status table row 5 says the points page is 'as of previous day plus local redemptions'. Only the redemption screen does the subtraction. The points page shows the bundle balance unchanged, and the overdrawn flag is the bundle's too.
SCENARIO: Offline, an SR redeems gifts worth 50 points for an outlet with 110. The redemption screen then shows 60. The SR opens Loyalty > Points for the same outlet and sees 110 Pts, not overdrawn. If the redemption took the outlet to -20, the points page still shows a positive balance with no overdrawn line. Two screens on the same phone disagree about the same outlet. Fix: load the local redemptions and the bundle build time in OutletPointsHost, subtract them, and derive overdrawn from the adjusted balance.

LOWS:

## redemption-screen verdict=pass
SUMMARY: I read slice 4 (redemption model, screen, host, store, record layer) at dfabe13e by reading the code only. Nothing was built or run, so every behaviour below is from the code, not a test. I found no blocking defect. The main weakness is the 'balance minus this phone's redemptions' rule. It depends on a phone-clock string compared with the server's bundle build time. It can subtract a redemption twice when the phone clock runs ahead, or miss one when a redemption was still pending while the bundle was built. This only affects the shown balance, and a redemption is accepted either way. The rest holds up: one redemption per uuid, nothing written on cancel, no accidental cash payout (cash_points is always 0), bounded steppers with integer totals, overdraw shown plainly and allowed, strings in both languages, and only six goldens added. The status file lists the unfinished slices honestly, but its top handover block is stale and it does not say what only a device walk can prove.

LOWS:
- Balance double-subtract risk (clock skew): LocalRedeemed.points compares the redemption's phone-clock confirmed_at with the bundle's server build time as strings. If the phone clock runs ahead, a redemption that was synced and already counted in a newer bundle can still look 'after the bundle' and be subtracted a second time until the next bundle. The reverse race also exists: a redemption still pending when the bundle was built is counted, then after it is acked its confirmed_at is older than the build time, so it stops being counted although the bundle did not include it (balance too high until the next bundle). The string comparison also assumes both timestamps use the same format (Z, millisecond digits); I could not check the server's server_time format. Only a display figure and the server accepts overdraw, so not blocking, but the shown 'overdrawn' warning could be wrong in these cases. If bundle build time is null, every non-rejected redemption is subtracted, including acked ones.
- Replay of the same redemption uuid with a different basket is silently dropped but reported as saved: CaptureRepository.recordProgramme returns false on a replay and ProgrammeStore.saveProgramme turns that into true (it only checks that nothing threw). The uuid is rememberSaveable and renewed only after a successful save. If the app is killed after the database commit but before the new uuid is stored, the restored screen still has the old uuid and (via rememberSaveable) the old basket. Re-confirming the same basket is harmless (one redemption). Changing the basket first and confirming would show 'saved' while the new lines are lost. Narrow; a returned false from recordProgramme should be told apart from a real save.
- In RedemptionHost.onConfirm, the re-read of redemptions after the save has no catch. If that read threw after the commit, the exception escapes the coroutine (the screen only has try/finally) and could crash the screen even though the redemption was saved, and the uuid would not be renewed.
- Confirm dialog text says 'Points will be deducted', while the lead asked for 'saved on this phone' honesty. Only the success dialog says that. The points are not deducted anywhere authoritative until sync. Wording nit.
- The retailer picker lists outlets of every route the bundle holds for the business date (readShopOutlets uses routesOfDay and flat-maps all routes), not only the route the SR is working. The bundle is the SR's own, so no foreign outlets, but on a multi-route day the open-day guard uses the outlet's own route id. I could not verify how RouteDayLock.requireOpen behaves for a route the SR has not opened; a refusal would show the generic 'could not be saved' text. Also the guard is called with record type 'redemption', which the lock comment says is not one of the locked types, so redemptions are still accepted after Final Submit; the status file says the check-in gate is not in this branch.
- Cash-back is safe: plan() always writes cash_points 0 and cash_mtk 0, and gifts with no or zero points_cost are filtered out of the screen and refused by Basket.plus, so a cash payout cannot be created by accident. Steppers are bounded (50 per gift, 20 lines, minus floors at 0), totals are Long sums of qty times points, and the record layer re-checks all of it. Cancel writes nothing; the double-tap guard (busy flag plus fixed uuid) is real. There is no screen test that taps confirm twice, only a single-confirm and a store replay test (I did not open ProgrammeStoreTest in detail).
- Strings: the screen uses stringResource throughout, 59 entries in both values and values-bn. The only literals are the stepper glyphs and a white colour. Not verified: that every Bangla string is correct Bangla (I only counted entries). Offline: states for no programme, no outlets with points and no gifts are present; the screen reads only the stored bundle, so there is no network use in the path. Goldens: the lane adds 6 redemption PNGs (bn, basket, empty, font20, overdrawn, en sunlight) and no existing golden or file is modified (only A entries under ui-screenshots, plus the listed code edits).
- docs/status/android-sr-programmes.md states plainly what is not done (slices 5 to 7, rows 12 to 15 blocked and named N-2, N-3, N-5, N-8) and marks rows 5 to 7 'server path not verified; needs owner's earning rule'. But the HANDOVER block at the top is stale: it says slice 4 is local and not pushed, which contradicts this branch, which contains it. It never states what only a device walk can prove (real balance display after sync, the clock-skew cases, kill-and-relaunch mid-confirm, printing is not involved). It also does not mention the small private store: none exists here, since redemptions live in amo_record and the outbox, so clearing app data loses unsent redemptions along with everything else (same as other records). Not verified: nothing was built or run, and I did not read the other slices.
