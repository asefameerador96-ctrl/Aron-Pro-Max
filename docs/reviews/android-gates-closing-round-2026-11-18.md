## lock-and-data verdict=pass
SUMMARY: Read every non-test change in abfa1ef4..d9997b8ae (one commit, d9997b8ae9) on origin/lane/android-gates. No blocking defect found; twelve lows.

What I checked and found sound:
- closeLock in the Save (SrSaleKit / AmoSaleKit commitUnderCloseLock): both orders are right. Save first: memo stored, the close then reads it and writes sold. Close first: the Save finds the visit_close (same business date key as the close writes: the visit's date) and throws before anything is written. An edit is not refused. Lock order is one-way everywhere I could trace (closeLock -> SaleFlow lock; resumeLock -> closeLock; dropUnsavedDraft holds only the flow lock and its tell() only writes a phone mark; AmoDay.closeVisit / endCallIfClosed are never called from inside the commit; the onRefused callback runs after the lock is released). The Mutex is suspending, so no main-thread block. The commit is still one Room transaction via SaleFlow.commit, still returns the same memo on a repeat while the call is open, no double memo path found. Print runs outside the lock.
- When the route-day refused the phone's close no visit_close exists, but a racing Save is then refused by the route-day check in the capture itself, so no memo lands there either. A call ended that way is not restored at the next start, so the extra CALL_ENDED marker is not written again and again.
- NoSale rows, SR gate Close, AMO gate Close, AMO leave: write errors are caught, cancellation is rethrown, the call is kept.
- Marker before drop: tell() runs inside the draft lock before store.clear, only when something is there; a failing tell does not keep the draft.
- Room: version stays 10, no schema json changed in this round, the 9->10 auto-migration only gained a spec (no identity hash effect). The backfill reads columns that exist in 9.json (outbox.client_uuid, amo_record.client_uuid / record_type / payload_json), writes only outbox.parent_uuid with 'AND parent_uuid IS NULL', uses the same RecordMapping.amoParent as new rows, is deterministic, and cannot fail the upgrade.
- SQL guard: the same-family visit clause is unchanged in meaning; the memo/print/due/supersedes parents are now matched in any family; NULL parents never match. REFUSED_SELECT only adds two columns from joins that already existed.
- Wire: no payload, hash or signature code touched; parent_uuid and phone marks are local; closed_by appears only in a local helper comment, not in any payload. No new sensor, network call or polling in the sale path.

What I could not verify: nothing was built or run here (no Android SDK), so Room code generation with the new spec class, the tests the lane lists, and the mutation proofs are taken from the handover, not seen. The real 04:00 timing on a phone, the dayGate refresh timing behind the SR gate dialog, a real 9->10 upgrade with queued AMO lines, and the server's answer to an edit whose superseded memo was refused are not verifiable by reading.

LOWS:
- Save refused for a closed call shows only the generic 'save failed' step (CallAlreadyClosedException is not a DayRefusal, so SrLockGate/AmoLockGate.saveAndPrint just rethrow it and SaveAndPrint stops at SaveFailed). In the 04:00 race the rep still learns why from the stored CALL_ENDED / DRAFT_DROPPED notice once the screen leaves the call, but the sale screen itself has no own text, and a second tap fails the same way. Files: android/app-sr/src/main/kotlin/com/aktcl/aron/sr/SrSaleKit.kt (commitUnderCloseLock), android/app-amo/src/main/kotlin/com/aktcl/aron/amo/AmoSaleKit.kt.
- The closed-call check runs BEFORE SaleFlow.commit's own 'already committed, return the same memo' answer. If a memo was stored but the read-back for printing failed (SaveFailed after a landed commit) and the call is closed before the retry, the retry is refused although the memo exists (no second memo, no data loss; the memo is in the memo list for reprint). Checking flow.state.value.committed (or committer.existing) first would keep the replay idempotent.
- commitUnderCloseLock reads flow.state.value.draft outside the SaleFlow lock, then commits whatever draft the flow holds. The kit has ONE flow for sale and edit, so in theory the draft could be swapped between the check and the commit (edit draft seen, sale draft committed). Needs two screens driving the flow at once; not a realistic path, but the check and the commit are not strictly the same draft.
- The close lock is now held across the Room commit AND the print model read-back (printSource.load: prepare() plus a memo read). It is a suspending Mutex, so no main-thread block and no deadlock found (order is always closeLock -> flow lock; dropUnsavedDraft takes only the flow lock and its tell() only writes a phone mark; resumeLock -> closeLock is one-way). A close tapped during a slow Save just waits.
- SrCheckInGate: the new 'call ended' dialog lives in the gate's remembered state. If closing the call makes the gate itself leave the screen (dayGate turns null on the same refresh), the dialog and the onCallClosed (Home) step are lost and the rep lands on the gated screen with no text. I believe the gate normally stays (the earlier day is still open, so the reason becomes not-checked-in), but I could not confirm the dayGate refresh timing by reading alone.
- AMO gate Close (MainActivity) ignores the DayRefusal that closeVisit returns: when the route-day refused the close the AMO goes back in silence (the new sr_call_ended text exists only in app-sr). ControlCallHost.leaveCall swallows a failing close with no message at all (call stays, rep must guess and tap again). Both are admitted as untested in the handover.
- AmoStockCorrectHost fallback guard is built with onCheckIn = {}: in that path the 'go to check-in' button of the guard dialog does nothing. Only reached when the app gives the screen no guard.
- Notice dismissal is still not durable (the marker delete runs on a background coroutine; a kill right after the tap shows the notice once more). The lane documented this as accepted in D-AGATE-19 instead of fixing it; safe direction, but item 4 asked for durable dismissal.
- A draft file of a call the phone closed stays on disk if the process dies between the close and the drop (the notice may already say 'dropped'). Documented as accepted. Note the claim 'overwritten by the next draft of that visit' is not quite right: the file is keyed by the visit uuid, and a later EDIT of a memo of that same visit calls flow.start with that visit uuid and would load the stale file. That needs a saved memo plus a second unsaved draft on one call plus the kill window, so it is remote.
- SQL guard, edit case: an exhausted edit memo is now withheld from Send again when the memo it supersedes was refused by the server. That is right only if the server answers such an edit with a retryable parent-missing; if the server would accept the edit on its own, this is a false refusal of a legitimate Send again. Server behaviour not checked here, and this path has no own test (admitted).
- Reader vs SQL guard: RoomDaySource looks for the cross-family refused parent only among the rows of refusedList(limit), the SQL guard looks at the whole outbox. A refused parent beyond the page limit makes the list offer Send again that the SQL then refuses (returns 0, nothing happens). No harm to data.
- Migration9To10 swallows every exception, so a failed backfill is silent (rows keep NULL parent, i.e. the old behaviour). Acceptable for local metadata, but nothing records that it happened.
