## sync-semantics verdict=pass
SUMMARY: Read-only review of the sync and check-out server code in the lane's own diff (git diff 951292a48...origin/lane/sr-server at 1c8c3cb0). No blocking defect found. Nothing was built or run.

What I traced and found sound:
- closed_by absent (old phones): the member is not in the insert column list, the column default 'rep' applies, every reader and rule behaves as before. 'rep' explicit: same. 'phone' on a check-out: stored and acknowledged accepted, skipped by checkout_too_early, by the CHECKOUT_WITHOUT_SUBMIT judgement, by supervisor_day.checked_out_at, by geo_fix, out-of-bounds and GNSS rules, by dw.fact_attendance check_out_*, the attendance report (note column added last) and My Team last fix and mock count. 'phone' on a check-in or any other value is refused by the V0201 CHECK (enforced for new rows although NOT VALID) and becomes a final schema_invalid.
- Idempotency: the attendance insert is a plain INSERT in a savepoint, with no ON CONFLICT clause, so the index swap cannot break an arbiter. A unique violation is mapped by TABLE name (attendance_event gives attendance_duplicate), not by index name, so the new index names attendance_event_once_rep and attendance_event_once_phone work, and an old API against the new database also works. Same client UUID twice is still a duplicate by client_uuid. Rep close and phone close of the same day are both stored in either order; two rep check-outs, two check-ins or two phone closes are attendance_duplicate. No other INSERT ... ON CONFLICT in the backend targets attendance_event; the risk_signal arbiter (code, subject_type, subject_id, business_date) is the same one already used elsewhere. No other code or migration references the dropped index name.
- Migrations V0201..V0203 are new files only (forward-only, no shipped migration edited); both new indexes are created before the old one is dropped in the same transaction; existing rows are all 'rep' so the build cannot fail on data.
- Automatic submit of the day's sales at check-out is done on the phone (D-LEAD-PREREQ-02 rule 3), not by the server: the server writes no memo, stock or total at check-out, so nothing can double. day_submit stays an ordinary idempotent record; a closed route-day still accepts day_submit and attendance (state records are outside the day lock). The lane's diff does not touch this path.
- After-midnight rule: enforced by the phone; the server does not refuse a rep check-out by clock (ruling: the server flags, never refuses). The business date is taken from the envelope, so a phone close dated with the forgotten day and captured the next morning is accepted inside the backdate window. Grace period (received_at older than cfg.day.submit_settle_timeout_min, clamped 5..240), 8-day scan (max_backdate_days + 1, clamped 2..31), route_id on the worker-raised signal and ON CONFLICT DO NOTHING all read correctly; ROUTE_CAPTURE_TYPES equals IngestService.DAY_LOCKED_TYPES; worker_rw has the grants the two rules need (read app, INSERT/UPDATE risk_signal) and the tests run them under that role.
- Scope: the round adds no endpoint. The phone close is the rep's own upload (user id from the token); TeamApi only gained closed_by = 'rep' filters inside the existing zone-scoped team query, so a TSO cannot close or see another territory's rep through it.
- Merge with 951292a48: the merge base of the lane head and the integration branch is 951292a48 itself, so the lane's diff is the complete difference. Every removed line in sync, attendance, memo, analytics, risk and contract files is a line the lane replaced on purpose; nothing from the integration side was dropped or reverted. The lane's own username/memo widening is gone and V0197/V0198 are untouched.

LOWS:
- Stale version wording: code comments and KDoc (IngestService, DayStates, RecordWriter, RiskSignals, Aggregator, WireDtos), docs/24-build-spec.md and the web test title still say 'contract 1.20.0'; the shipped contract is 1.19.0.
- Contract text for AttendanceClosedBy and the V0201 column comment say the phone close has 'no location read'. D-LEAD-PREREQ-04 ruling 2 says the phone makes one location attempt and stores the reading. The server behaviour is consistent (the fix is kept on the attendance row only, never a geo_fix, ignored by My Team and the geo rules); only the wording is stale.
- closed_by is validated only by the database CHECK (bad value or 'phone' on a check-in gives SQLSTATE 23514, an explicit null gives 23502; both become a final schema_invalid with the generic detail 'database refused the record'). Correct outcome, but no named member in the reason.
- Deployment order matters: RecordWriter only writes columns the table has and caches the column list per process. If the new API ever started before V0201 ran, a phone close would be stored without closed_by (so as 'rep', a real check-out time) until that process restarts, and My Team, the attendance report and the aggregator would fail on the missing column. Migrate first, then start the API (the request file says so).
- The worker late raise counts registry rows of any status and any source as 'route captures'. A paper backfill keyed on the web for a rep's day within the 8-day window, where the rep made a real check-out and the day has no day_submit record, would raise CHECKOUT_WITHOUT_SUBMIT (raised_by worker) although D-LEAD-PREREQ-02 says the paper backfill stays exempt. I did not verify whether a paper backfill writes a day_submit or registers under the rep's user id; flag only, no data effect.
- First worker run after deploy scans the last 8 business dates of existing check-outs. Any old rep check-out with captures, no day_submit record at all and no signal row gets a signal then. Expected to be few (the ingest already judged these at check-out time), but dev may show a small one-off burst.
- Asymmetry kept on purpose and documented: the ingest raise counts a data-voided or submit-voided submit as none, the worker late raise treats any day_submit record (even voided) as submitted. A day whose only submit was voided before the check-out is raised by the ingest, one voided after is never raised.
- Withdrawal looks back only max_backdate_days + 1 dates: a signal whose submit is released by a reviewer later than that stays open until a reviewer dismisses it.
- A second phone close of the same user and day under another client UUID is refused attendance_duplicate (final) with the text 'Attendance for today was already recorded'. Harmless, but the phone must treat that refusal as done, not as an error to show the rep (android side, not checked here).
- V0202 holds ACCESS EXCLUSIVE on app.attendance_event while two unique indexes are built (non-concurrent). Fine at pilot size; at fleet size reads and check-ins wait for those seconds.
