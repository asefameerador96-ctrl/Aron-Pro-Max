### BLOCKING upheld=2/3: StarProgress uses BigInteger.TWO, which does not exist on Android below 13 (API 33); the app's minSdk is 26
WHERE: shared/rules/src/commonMain/kotlin/com/aktcl/aron/rules/StarProgress.kt, roundDiv (`val two = BigInteger.TWO`); shared:rules is linked into the apps through android/core-common (`api(project(":shared:rules"))`); gradle/libs.versions.toml android-minSdk = 26
WHY: BigInteger.TWO was added in Java 9 and reached Android only at API level 33. Library desugaring does not supply it, and Android lint does not check the bytecode of a plain JVM dependency, so nothing in the build catches it. The lane's own contract note (docs/requests/contract-sr-targets.md, N-8) tells the phone lane to recompute with StarProgress, and the header of SkuProgress says the phone and server call the same functions. The server (JVM 17+) is fine, so lane CI stays green.
SCENARIO: The Android lane wires screen 62 (Match Box Lifting Star) to StarProgress.compute as the contract invites. On a field phone running Android 8 to 12, opening the screen throws NoSuchFieldError on the first roundDiv call and the app crashes. At 6af9be045 no Android code calls StarProgress yet (I grepped origin/lane/android-sr-programmes: no reference), so today this is latent; it fires on the first phone-side use. Fix is one token: BigInteger.valueOf(2). This is also the only java.* import in shared/rules commonMain.

## scope-bundle-migrations verdict=fail
SUMMARY: Reviewed 6af9be045 against merge-base 29e8d86f3 by reading code only. Scope, admin upload guarantees, migrations and the additive contract are sound. Two blocking defects in the bundle lens: (1) as_of is the worker's wall-clock freshness stamp, rewritten every ~5 s on idle passes, and it sits inside the bundle digest and the route-level delta fingerprint for every SR route (calendar and kpi are always present), so no SR ever gets a 304 again and every delta resends the whole route with its outlets; this hits the pilot immediately and breaks the data-pack rule. (2) The month-to-date reads run on every bundle build against tables whose indexes lead with business_date (aggregates) or have no outlet index at all (dw.fact_memo_line); harmless at pilot size, a database-saturating scan at 8,500 routes; add route-leading / outlet-leading indexes in the renumbered migration. Lows cover: no size test or paging for campaigns, no geographic reach on the admin write (national ADMIN by design, same as route-targets), small data-integrity gaps in the campaign upload, and the full renumbering lists for V0230..V0233, dw view contract 1.10 and contract 1.22.0. Working-day calendar source and its admin GUI exist already.

### BLOCKING upheld=3/3: as_of (projector wall-clock) is inside the bundle digest, so every SR bundle gets a new version every few seconds and 304 / small deltas stop working
WHERE: backend/sync/.../SrTargets.kt asOf() (line ~90) and its use in SrTargets (each achievement_mtd row + calendar.as_of), SrKpi (kpi.as_of), SrStar (star.as_of), SrCampaigns (each campaign row as_of); BundleService.contentDigest / snapshotSeq (digest of the whole Bundle minus meta); BundleFingerprint.routeLevel in BundleDelta.kt (route-level hash covers calendar/kpi/star/campaigns/targets/achievement_mtd); backend/analytics/.../AggregationWorker.kt markFresh() -> DashboardSummaries.touchFreshness()
WHY: as_of is read from dw.summary_freshness.last_updated_at for 'agg_daily_route_sku'. The worker loop runs every 5 seconds (AggregationWorker.start default) and at the end of every idle pass markFresh() writes last_updated_at = now for every freshness table (touchFreshness: 'at = now' unless a dirty key is pending). So the value moves every ~5 s even when no figure changed. calendar and kpi are emitted for EVERY SR route even with no targets uploaded (SrTargets.load returns a Snapshot per route, SrKpi uses ids.associateWith), so every SR bundle carries a moving timestamp. The bundle version is a SHA-256 over the whole bundle content without meta, so the version changes on each request; the delta compares a route-level hash that includes these members, and a changed route is sent whole ('routes_added': the phone replaces the route and its outlets). Each request also inserts a new app.bundle_snapshot row. The lane's tests use a fixed clock and no running worker, so they cannot see this.
SCENARIO: Pilot SR with 120 outlets, no targets uploaded at all. Phone fetches the bundle at 09:00 (version D:1). At 09:10 it asks GET /v1/sync/delta or the bundle with If-None-Match. The worker has run ~120 idle passes since, so calendar.as_of and kpi.as_of differ; the digest differs; the server answers a new version D:2 instead of 304, and the delta carries the whole route with all 120 outlets in routes_added. This repeats on every poll all day for every SR (and one new app.bundle_snapshot row per request). It breaks the delta/304 economy and the 2 GB data-pack rule (CLAUDE.md constraint 3). Fix direction: keep as_of out of the digest and the route-level fingerprint (or put it in meta), or make it change only when the figures of the route change (for example max(updated_at) of the rows read, or a value truncated to the through_date close).

### BLOCKING upheld=3/3: Month-to-date reads on the bundle path have no index that leads with the route or the outlet (fleet size only; pilot unaffected)
WHERE: SrTargets.load, SrKpi.load (two reads), SrStar.sold (two reads per route) on dw.agg_daily_route_sku / dw.agg_daily_route_brand: primary key (business_date, route_id, sku_id|brand_id), only other index (sku_id|brand_id, business_date) (db/migrations/V0011). SrCampaigns.load (two reads) on dw.fact_memo_line filtered by outlet_id + business_date: the table has only PK (line_client_uuid, business_date) and index (memo_client_uuid, business_date) (db/migrations/V0118). None of V0230..V0233 adds an index.
WHY: The queries are 'route_id = ANY(:r) AND business_date BETWEEN first AND through'. With the leading column a date RANGE on PostgreSQL 16 (infra/modules/postgres.bicep version 16, no skip scan) the index scan walks every entry of the date range for all routes and only filters route_id inside the index. For fact_memo_line there is no usable index at all for outlet_id, so the month partition is scanned. These run on every bundle build, and bundles are built on request (and on every delta). The status doc says 'an indexed table' and lists the fleet-size run as not done.
SCENARIO: Final account, 8,500 routes x ~40 SKUs, day 28 of the month: one SR bundle build walks about 28 x 8,500 x 40 = ~9.5 million index entries of agg_daily_route_sku per read, four to five reads per build (targets, KPI categories, star month-to-date, star last month = ~10 million more), plus the same on agg_daily_route_brand. An SR whose outlets are in a campaign also triggers two scans of the month partition of dw.fact_memo_line (tens of millions of lines at fleet). At 8,500 SRs logging in in the morning this saturates the database. At pilot size (5 to 10 users) it is harmless, so this must be fixed before the final-account sizing, most cheaply now: add (route_id, business_date) indexes on the two aggregates and an (outlet_id, business_date) index on dw.fact_memo_line (or read campaign achievement from dw.agg_daily_outlet_sku) in the renumbered migration.

The primary SR can probe a cover SR's memo uuid acting for them and get IN, VOIDED or stored lines. uuids are 122-bit random and the memos are on the primary's own route, so this is not a practical leak. It does widen 'own records only', and it is untested (the foreign-uuid tests use another user with no acting_for). It is worth checking whether open_memos exposes such uuids.
- No test for an AMO, TSO or other non-SR phone token: the 403 test uses only a web admin token. The role check exists in code (`p.role != Role.SR`).
- The foreign-uuid tests assert only `in_figure` and `voided` are empty. They do not assert that `twin_ambiguous` is absent, and they do not probe another SR's manual memo by its memo_no (a twin across users). The code is correct: the twin query is own-only.
- The read-only test counts rows in seven tables. `app.bundle_download` does not exist in any migration, so its count is -1 both times and that part cannot fail. app.domain_event (the outbox) is not counted, and row counts cannot detect an UPDATE. DECISIONS D-TKPI-14 says 'compares row counts of seven tables'; in effect it compares six.
- The empty-plans path of BundleService.figures answers the probe in a REPEATABLE READ transaction without `SET TRANSACTION READ ONLY`. It only reads, but it is inconsistent with the main path.
- There is no rate limit. AdmissionControl puts POST /v1/sync/figures in LoadClass.OTHER, which is never shed, and there is no per-device limiter. The contract still lists a 429 response. The cost is about 141 ms warm per call (measured serially, no concurrency). 'Never on a timer' is client guidance only; nothing says the server does not limit. A looping or abusive phone is bounded only by the request timeout.
- Probe business_date values are not restricted to the bundle month: up to 300 distinct arbitrary dates go into `business_date = ANY(:d)` across partitions. The cost is bounded but needless; probes outside [first of month, for] could be skipped or refused.
- The probe IN state does not check that the memo's route is among the response's `routes`. The contract rule still says 'for each own memo of the month' with no route qualifier, which carries over the earlier low: an SR moved off route A mid-month gets IN for A's memos that no returned figure holds.
- Duplicate uuids in one request keep the first entry, so a duplicate with `removed_locally: true` after a false one gets no stored_lines. Bad `for` errors carry the pointer `query.for` although `for` is in the body.
- Worst-case response size: 300 removed_locally IN answers x 60 stored_lines is several hundred KB raw. The measured typical size is 141,746 B raw / 11,160 B gzip per call, but docs/04 states no per-call or per-day budget for /figures, and the call frequency (after every sync cycle and on every screen open) is not bounded.
- Astha hook: `include_astha` returns the bundle's programmes section (null when there is no programme; the test asserts it equals the bundle's), built in the same snapshot but with no identity answer. The phone must still merge Astha with the old acknowledgement-inference rule that the SR figures dropped. figures-astha-identity.md says so honestly; until the loyalty lane builds the astha probe, a phone mixing the two rules can misstate Astha.
- The concurrency proof ('a commit during the read is answered IN exactly when the figure holds it') runs through BundleService.bundle(probe=...), a path no HTTP endpoint uses. /figures uses figures(), which has the same structure but its own code, and no concurrent-commit test covers it.
- Migrations are still numbered V0230..V0233 at this head; the renumbering to V0210..V0213 is pending. The contract version says 1.22.0 while the descriptions say 'number provisional'.
- (refuted 2/3) A today-dated memo stored with a line refused for good is counted with the refused line all day: the endpoint gives no line state for stored memos dated after through_date: For a memo dated after through_date the phone adds its own local contribution. The only answers are VOIDED or NOT IN, and IN with `lines` exists only for memos dated up to through_date. When the server stored the memo but refused one line for good (D-SALE-ZERO-PRICE-01 price_invalid, a final refusal), the phone keeps adding the refused line for the rest of the day. The rule forbids using the ack, so the phone cannot correct it. The contract calls refused lines server-authoritative and the request doc says the zero-price hole is closed by construction, but that is true only from the next day. Proof case (d) counts the phone's local contribution, not the stored one, so T(S) itself drifts from the stored truth for today. The same applies to any partial server-side change of a stored today memo.
