# CI failure audit (2026-10-07, lead workflow wf_e3eba3cc-190)

Question from the owner: why do most GitHub Actions runs look failed, are we making a mistake, are we wasting tokens by pushing a failing thing again and again? Method: all 392 runs downloaded, four independent read-only analyses (non-success explainer, failure root causes, waste and economics, process audit), one synthesis, three skeptics (data, cause, advice), one final rewrite. Snapshot 05:33 UTC; later figures are live checks. Figures marked as assumptions are not measurements.

## 1. Direct answer

**Nothing in your screenshot is red, going by the icons you described.** The checkers could not see the screenshot itself.
- The grey circle with a slash is a deploy run that was skipped on purpose (all 5 deploy rows, #64 to #68).
- The grey circle with an exclamation mark is a ci run that was cancelled while waiting, because a newer push replaced it. It never started (ci #246, #248, #250). This is inferred from timing and from the runs having zero jobs. No log line says it.
- The orange runs were still going. They ended red a few minutes later (#247, #251, #245, #249) [C5, C7].

**What really failed:** 79 of 392 runs (20%), and every one is a ci run. That is 31% of ci runs [C1, C2].

**The real problem is hidden behind the grey.**
- No ci run created since about 04:51 UTC on 7 October has passed. This holds for all branches up to 05:44 [C9].
- By creation time, every INT run (the shared integration branch) that reached a verdict since then was red. Live checks up to about 06:20 still showed no green INT run [C9, C10].
- Some older INT runs finished green as late as 05:10, because they waited behind the old deploy step.

**Are we making a mistake?** Yes, but not "one failing thing retried blindly". The mistakes are in process:
- Red code got merged into INT. One clear case is `hasLongClickAction`.
- Lanes picked up breaks from INT and from each other (`hasLongClickAction`, duplicate `TeamDeps`). I have no reliable overall count. The share of red runs that are merge commits is no higher than normal, so I do not use it as evidence.
- INT is pushed about once a minute. About 84 to 87% of INT ci runs since 04:55 were replaced before they started [C11, C12, C19, C35].

Token waste from red runs is real but modest. It is an assumption-based estimate of roughly 3 to 10% of lane spend. It is not measured [C30].

## 4. Are we wasting tokens or runner time?

**Runner time: measured.**
- GitHub billed 0 on every run checked, because the repository is public. The original check covered 20 runs. The skeptics re-ran 1 or 2 and also got 0 [C26].
- Cancelled ci runs are cheap. They used about 23 runner-minutes. Their wall time was 294 minutes (65 runs), mostly spent waiting. All 37 cancelled ci runs created since 04:55 had zero jobs. Some older cancelled runs had queued jobs that never reached a runner [C6, C27].
- Skipped deploy runs take about 1 second.
- Failed ci runs used 889 job-minutes (81 failed runs through 05:44). Passing runs used 618 [C27].
- Repeated reds. This is a judgement range, not a measurement:
  - About 29 of 81 red runs (36%) repeated a cause that an earlier finished red had already shown.
  - Another check found 30 full repeats in 79. A stricter signature check on 55 parsable reds found 17.
  - The wider "47 of 81 (58%)" figure counts 13 runs that were in flight at the same moment. They could not have known the earlier red, so that figure overstates avoidable waste. Not verified [C28].
  - A repeated red is also information for a different lane, so it is not always waste.
- Push rate:
  - Across all branches, the median gap between pushes was 21 s from 03:00 to 05:44. 224 of 277 pushes (81%) came in those 2.7 hours.
  - 55% of pushes had a merge commit as head. Most of those merges (125 of 153) were made on INT itself, not INT merged into lanes [C12, C13].
- After the 04:55 change, about 84 to 87% of INT ci runs were replaced before starting. The exact figure depends on the cut-off time [C11].

**Tokens: only partly measured.**
- Reported lane spend is $596 across 21 lane sessions with cost data. Two checks reproduced it. One found no cost data in its files, so treat it as not fully verified. It is probably a lower bound, but that is an inference [C29].
- The lead session's $725 is not verified. It is inferred from the session title [C29].
- Red-CI fix cycles are an estimate, not a measurement:
  - The window method gives $20 to 25 (3.3 to 4.2% of lane spend). It counts red pushes followed by a later push and multiplies by assumed per-cycle prices.
  - The scaled method gives about $59 (9.9%). It spreads core-ui's share over every lane.
  - Core-ui is modelled at about $4.5 of $14.69 (about 31%).
  - Use these as a wide range. Do not use them to rank causes [C30].
- Context size looks like the bigger driver. This is an inference, because the CI share is itself an estimate. 12 of 21 lane sessions are above the 450k recycle limit (maximum 666,619). Cache reads were about 72% of cost in the core-ui transcript. That figure comes from one or two samples and was not re-checked on all lanes [C31].

**Assumptions, not measurements.**
- Opus lanes cost $0.50 to 0.70 per fix cycle.
- About half the fix cycles were avoidable, so the avoidable share is about 1.5 to 5% of lane spend.
- If the repo went private, the 2,000 free minutes would last about 2.7 to 3 hours at the 03:00 to 05:44 pace. That pace is about 680 to 730 job-minutes per hour, with each job rounded up to a whole minute. About 2,100 to 2,200 billable minutes of ci have been used so far, about 85% of them on 7 October. Deploy and codeql minutes are not in that count. The earlier "2,548" figure did not reproduce. GitHub's price and plan limits were not checked. Sponsor rule 13 keeps the repo public until the product is complete, so this is a planning figure only [C32].

## 5. What we change now (ranked)

   - Check that the `hasLongClickAction` fix (716e945) is on INT.
   - Re-merge INT into core-ui, sr-a, sr-b and backend-reports.
   - Pause pushes until INT is green.
   - Owner: lead, then each lane.
   - Must not weaken: no test skipped, disabled or quarantined. The Semgrep gate and the hardcoded-string (Bangla/English) test stay.
2. **Gate what reaches INT.**
   - Promote a lane head only after a green run on that exact commit, checked by a small script.
   - A lane merges INT only when INT's latest verdict is green.
   - Contract, shared types, migrations and ci.yml changes go via a lane branch and wait for green.
   - Owner: lead.
   - Must not weaken: sponsor rule 11. No pull request or merge queue is opened until you approve the flow. The 8 required checks on main stay.
3. **Slow the INT push rate.**
   - Batch lane merges, for example at most one INT push every 5 to 8 minutes.
   - Keep the "newer push replaces the waiting run" rule for now. After the change, queue wait for jobs that got a runner fell (median about 16 to 18 s down to 3 s) and verdicts per hour fell from about 61 to 27. This is a before/after on a short window with 11 runs still open, so the cause is not proven [C33].
   - The analyses disagree here. One suggests one run per commit instead. I would decide that only after INT is green.
   - Owner: lead (lane protocol), infra.

   - Owner: infra lane.
   - Must not weaken: the single deploy lock, the migrate retry, pilot-size dev resources (rule 1), and never deploy a red commit.
6. **Land contract changes together with their consumers.**

   - Owner: contract/shared lane with backend-sync, android-core, android-geo-dpc and db.

## 6. What I am NOT sure about

- **Tokens.** I cannot measure them exactly. The red-CI cost figures are modelled from assumed per-cycle prices and two short transcript samples (the backend-reports sample covers just 05:05 to 05:58 and 3 fix windows). The $725 lead cost and the "lower bound" wording are inferences.
- **Moving numbers.** The snapshot ends at 05:33 UTC. Later figures are live checks from 05:44 to about 06:20, and they change every minute. Counts such as "43 INT runs, 37 cancelled" move with the cut-off time.
- **Screenshot.** Your screenshot says 368 runs. The data shows 381 created by 05:25:38. I could not explain the gap of 13. The icon meanings come from your description. The checkers could not see the screenshot, but the data matched your description one-to-one.
- **"Last green" time.** #163 was created at 04:38:23 and finished at 04:57:03. Older INT runs (#150, #160 and four more) finished green later, up to 05:10, because they waited behind the old deploy step. "Every INT run since then was red" holds by creation time only. All I can say for certain is that no ci run created after 04:51 is green [C10].
- **Runner minutes.** One analysis counted 1,804 job-minutes with 238 in cancelled runs. That count includes queue wait of jobs that never ran a step. The other two counted about 1,531 to 1,593, with 23 in cancelled runs. The 23 is the real runner time. The 1,593 includes in-progress runs.
- **Which Android lanes are CI-only.** The evidence is strong for core-ui only. sr-a ran 164 tests locally. Whether Robolectric bypasses the mirror is an inference.
- **Table rows not covered by the checks.** The Dependabot, one-off and "core-ui #257 green" details were not checked.
- **Open questions.**
  - Whether the deploy lock fix works as hoped, and whether the 4 non-deployed green INT runs were really pushed out by about-to-be-skipped deploys.
  - Whether the daily gate pull request can finish while INT keeps moving, or whether a merge queue is available on a user-owned repo.
  - The cause of cancelled run #194. One check found no annotation. Another found a "higher priority waiting request" note on it.
  - Whether the AuthDto fix (55dd250) and the `hasLongClickAction` fix have reached INT.
- **The concurrency change.** Its effect on the red rate is mixed up with the shared breaks that appeared at the same time. I make no claim about it. The before/after queue-wait numbers do not prove it was the cause.
