### PERF-05 (high, real, effort S) Cold start does Keystore decrypts on the main thread, and the SQLCipher key format will pay a 256k-iteration KDF on every open

**Evidence.** SessionRepository initialises _state = MutableStateFlow(restore()) (core-session SessionRepository.kt:84-91). restore() calls store.active(), store.profileByUserId() and store.tokens(): three file reads, each an AES-GCM decrypt, and KeystoreSecretCipher.key() reloads KeyStore.getInstance("AndroidKeyStore") on every call (SecretCipher.kt:24-33, SessionStore.kt:41). The object is built by the Hilt singleton SessionModule.sessionComponents and injected into MainActivity with @Inject lateinit var (MainActivity.kt) on the main thread before the first frame. Keystore operations cost tens to hundreds of ms on low-end TEE devices against a 2.5 s cold-start gate. Separately, core-database SqlCipher.kt:13-20 passes the 32-byte random key to SupportOpenHelperFactory(passphrase) as a passphrase; SQLCipher 4 then runs PBKDF2-HMAC-SHA512 at its default 256,000 iterations on every open of the per-user database (login, cold start, process restart). DatabaseKeys, named in that file's comment, does not exist yet, and docs/status/android-core.md l.38 lists SQLCipher timing as not done. Once phones are enrolled, changing the key format needs a sqlcipher_export re-key of every device.

**Recommendation.** android-core, at F-SYS-006 wiring and before the first enrolment: pass the random key in raw form (the x'<64 hex>' blob) so SQLCipher skips the KDF, and document the key format in DECISIONS.md. Restore the session off the main thread (a Restoring state behind the splash) and cache the Keystore SecretKey in KeystoreSecretCipher. Add debug-build StrictMode with penaltyDeath for disk and network on the main thread, and time the first SQLCipher open and session restore on the A06 in the device check.

**Skeptic.** Both halves are confirmed. (1) SessionRepository.kt l.84-91: _state = MutableStateFlow(restore()) runs in the constructor, and restore() does store.active(), profileByUserId() and tokens(). Each is a file read plus an AES-GCM Keystore decrypt (SessionStore.read), and KeystoreSecretCipher.key() reloads KeyStore.getInstance("AndroidKeyStore") on every call (SecretCipher.kt l.24-33). SessionComponents.kt l.42 builds it eagerly, and the SR MainActivity gets it by @Inject lateinit var during super.onCreate on the main thread. DeviceIdentity(storageDir) is also built there. No StrictMode exists anywhere in android/ source. The per-call Keystore cost on low-end phones is estimated, not measured. (2) SqlCipher.kt l.13-20 passes the 32-byte random key as a passphrase to SupportOpenHelperFactory, so SQLCipher 4 runs its default PBKDF2-HMAC-SHA512 KDF (about 256k iterations) on every open of the per-user database. That is typically hundreds of ms on a low-end ARM phone for a key that is already 256-bit random. DatabaseKeys is referenced in the comment but does not exist (grep: no code). The scheduled row F-SYS-071 (android-core, Day 6) lands the key handling after F-SYS-006 wiring on Day 2, so the key format could be fixed in practice only after phones have enrolled with unsynced data. A later re-key means an in-place sqlcipher_export on a database holding unsynced rows. docs/status/android-core.md l.38 only plans a manual SQLCipher timing on the A06. Nothing else covers this.

### TP-4 (high, partly, effort M) Kill-and-relaunch is simulated by a clean DB close, there is no crash hook, and the androidTest files never run in CI

**Evidence.** The only kill test, CaptureRepositoryTest.kt:158-185, closes the Room database cleanly under Robolectric (line 169 'fileDb.close() // the process dies here'); a clean close checkpoints the WAL and finishes all work, so it cannot show what a SIGKILL between the domain-row insert and the outbox insert, mid-batch send or mid-ACK leaves behind. docs/17 s12.3 and docs/20 s2.4 specify kill points (T-1-24, T-1-28, T-1-29, T-2-22 to T-2-24) driven by 'am force-stop' and a debug chaos hook; grep for CHAOS_KILL or killAt in code finds none. The two real-device tests, android/core-database/src/androidTest/.../SqlCipherDeviceTest.kt (its header says 'device or CI emulator only') and android/core-session/src/androidTest/.../DeviceCryptoTest.kt, are not executed anywhere: ci.yml runs only testDebugUnitTest and lintDebug, and there is no emulator runner, connectedCheck or managed device. SQLCipher encryption of the per-user DB and the device key are therefore unverified by any automated gate, and the JVM tests run an unencrypted DB. CLAUDE.md's definition of done requires 'survives a kill-and-relaunch mid-operation'.

**Recommendation.** Owner lane infra (not android-core). Add a CI emulator job (reactivecircus/android-emulator-runner pinned by SHA, API 34, KVM) that runs connectedDebugAndroidTest for core-database and core-session on pushes touching android/, before F-SYS-006 wires the SQLCipher passphrase into the apps. Add a one-line request to infra for it, since none exists. Defer the debug-only KillPoint hook to the F-SYS-008 row and run it as the RC device-lab step; do not build it now. Effort S to M.

**Skeptic.** Core claim confirmed: the only two device tests (android/core-database/src/androidTest SqlCipherDeviceTest and android/core-session/src/androidTest DeviceCryptoTest) are never executed, since ci.yml has no emulator, connectedCheck or managed-device step. docs/status/android-core.md ('Awaiting a device or the CI emulator job') acknowledges they are unrun, yet no infra row or request asks for the job (the android-core ask was only assembleRelease, which infra did add). SQLCipher at-rest encryption and the Keystore token cipher therefore have no automated proof, and JVM tests run an unencrypted DB (factory null in Robolectric). This matters because a release build with R8 and native libs is built in CI but its encryption is never exercised. Overstated part: the kill-and-relaunch gates T-1-24, T-1-28 and T-1-29 are specified in docs/20 as release-candidate device-lab tests (phase RC, adb force-stop), not per-push CI. F-SYS-008, the batch sender and ACK applier do not exist yet, so a chaos hook cannot be placed. CaptureRepositoryTest also does test atomicity through rollback on invalid input, and the in-flight batch recovery path.

### PERF-06 (medium, partly, effort M) Phone bundle path holds the whole body as a String twice, has no page or delta client, and rewrites all reference rows on every apply

**Skeptic.** The code facts are true: AronApiClient.kt l.141 does response.body.string(); SyncApi.bundle() decodes BundleHead from that string and returns the string as BundleDownload.body, which is parsed again; ReferenceRepository.apply (l.55-63) clears outlets, routes and SKUs and re-inserts with REPLACE; the client has no page or delta call although the contract has getBundlePage and getBundleDelta (openapi.yaml l.519-551). ### PERF-02 (high, real, effort M) Blocking JDBC runs on the Ktor call threads (guard, outlets, reach); health shares those threads; no request timeout or in-flight limiter

**Evidence.** Only the auth routes wrap DB work in withContext(Dispatchers.IO) (backend/auth AuthModule.kt:49, 54, 67). GET /admin/outlets calls jdbi.withHandle directly in the route (backend/masterdata OutletsApi.kt, listOutlets) and SqlReachResolver does the same on a cache miss (SqlReach.kt:62-70). AuthGuard's onCall (platform AuthGuard.kt, authenticate()) calls scopeVersions.current() and mustChangePassword() on every request, which is JdbiUserStore.gate() with svCacheMs = 10 s (auth JdbiStores.kt:24, 47-58), so a phone that calls less often than every 10 s reads app_user on the call thread each time. Netty runs handlers on a call group sized to availableProcessors, and the API container is cpu 1.0 (infra/apps.bicep:39), so about one call thread. Hikari has connectionTimeout 5 s and initializationFailTimeout -1 (platform Database.kt), so with the database down each request parks the call thread for up to 5 s. The liveness probe GET /v1/health (apps.bicep:215-225, failureThreshold 3) is served by the same threads, which contradicts the comment in Database.kt that health answers while the database is down. No Ktor RequestTimeout is installed (docs/18 s4.3 sets 25 s) and there is no per-replica in-flight limiter L3 (docs/18 s4.4); only the login HashLimiter exists. Verify the thread count with the stall test below.

**Recommendation.** backend-core, before F-API-006 (the server ingest; the finding's F-SYS-008 is the Android uploader) is written. (1) Add one platform helper, for example Database.blocking{}, that runs JDBI on a bounded dispatcher (limitedParallelism of the pool size). Use it in AuthGuard and the stores, the reach resolver and every route, with an arch test that fails on jdbi calls in route lambdas outside it. (2) Install RequestTimeout 25 s (docs/18 s4.3) mapped to 503 with Retry-After. (3) Map SQLTransientException, Hikari pool timeout and SQLSTATE 57014, 55P03, 57P01, 08xxx and 40001/40P01 in StatusPages to ERR_SERVICE_UNAVAILABLE with a jittered Retry-After, never 500. (4) Add the stall test: with the Hikari pool starved, GET /v1/health answers under 200 ms, /health/ready returns 503, and a data route returns 503 within its timeout. The L3 in-flight limiter already belongs to N-056 (backend-reports); link it, do not duplicate it.

**Skeptic.** Confirmed in code and in the Ktor jar. javap on ktor-server-netty 3.6.0 shows callGroupSize = parallelism = availableProcessors. Main.kt l.50 uses embeddedServer(Netty) with defaults, and infra/apps.bicep l.39 gives the API cpu 1.0, so there is one call thread. withContext(Dispatchers.IO) appears only in AuthModule.kt (l.49, 54, 67) and PasswordHasher. Every other route and store calls JDBI directly on the call thread: OutletsApi.kt l.93, SqlReach.kt l.62-70, ConfigService, ConfigResolver, ConfigDelta, and AuthGuard.authenticate() through JdbiUserStore.gate() with its 10 s cache. Hikari connectionTimeout is 5 s with initializationFailTimeout -1 (Database.kt). /v1/health (Main.kt l.77) shares the call thread and the liveness probe (apps.bicep ~l.215) has failureThreshold 3. This is a concrete failure mode: during a database failover each request parks the sole thread for up to 5 s, liveness fails, and replicas restart, which contradicts the apps.bicep comment that a failover never restarts every replica. No RequestTimeout or limiter exists in backend/. Http.kt StatusPages maps any Throwable to ERR_INTERNAL (500), and the file's own comment says phones bisect on 500. So a pool timeout or a query cancel returns 500, not 503 with Retry-After. This is not covered anywhere: backend-core status lists no such row, and N-056 (backend-reports, Day 6) covers admission control only.

### REL-01 (high, real, effort S) A PostgreSQL outage or failover makes every API request, including the liveness and startup probes, block 5 s and restarts the replicas

**Evidence.** backend/platform/.../Http.kt:82 calls ctx.config.configVersion() in the onCall hook of every request, /v1/health included. In production ctx.config is DbServerConfig (backend/app/.../Wiring.kt:43). DbServerConfig.kt:23-26 snapshot(): once the 30 s cache is stale it calls load() on the request path. On failure it returns the stale snapshot WITHOUT refreshing `at`, so every following request retries and blocks again. Database.kt:42 sets Hikari connectionTimeout to 5000 ms. I reproduced this with the same Hikari settings against a closed port: each getConnection() failed after about 5000 ms, 3 times out of 3. infra/apps.bicep:212-236 sets no timeoutSeconds on the probes, and the Container Apps default is 1 s. So /v1/health takes about 5 s during an outage, the Liveness probe fails 3 times (periodSeconds 10) and every replica is restarted. A restarted replica can never pass the Startup probe (30 x 5 s), because the config cache is empty and every probe blocks. This contradicts the stated design in docs/18 s5.1 FM-15 and FM-16 ("liveness checks the process only") and the comment at Database.kt:46 ("the API starts (health answers) even while the database is down"). backend/app/.../HealthTest.kt only proves the in-memory wiring never touches the DB; no test uses the production wiring with an unreachable DB. docs/status/infra.md says a nightly PostgreSQL stop 20:00-08:00 is lead-approved but not built.
