## 1. Principles
1. The migration runs only inside the final Azure account, as a Container Apps job next to the private PostgreSQL, and reports only counts and checksums.
2. Re-runnable by construction: every target row has a deterministic key (UUID v5 of namespace + vendor table + vendor key); every fact chunk is deleted by chunk key and re-inserted in one transaction (masters are matched, never created); running twice changes nothing.
3. Restartable: per-table, per-chunk checkpoints in a control table; a killed run resumes at the first unverified chunk.
4. Reversible: every imported row lives in the archive schema (dropped by schema) or in the id map; the only live-master write (coordinate fill) is logged with before and after; a PITR restore point is taken first.
5. No personal data in logs, reports, tests or this repository. Reports hold numbers only.
6. Money is integer milli-taka computed with exact decimal arithmetic (never float); quantities are base units via the SKU's pack factor.

## 3. (b) Table-by-table mapping (26 tables)
Column names are **assumed canonical names** (listed in `tools/apsis-migration/mapping/columns.json` with a list of candidate vendor names per canonical name; the first candidate present in the dump wins; a canonical column that no candidate matches is reported as "missing" and the dependent step stops, it never invents a value). **Masters are matched, never created or overwritten (D-APSIS-MIG-06):** the October master-data load (docs/reference/master-data-loader.md) creates and owns the live masters; this tool matches the dump's masters to ours by business code, fills `apsis_map` (id map and lookup tables), stubs outlets we do not have (codes only) and reports the gaps as counts. ### Conversions (exact)
- Money: `amount_mtk = floor(amount_decimal * 1000 + 0.5)` on `numeric` (half up for non-negative; `app.div_half_up` semantics for negatives). No `float`/`double` in any conversion; the unit tests compare with `Decimal`.
- Quantity: `qty_base = qty_vendor * pack_factor` when the vendor unit is a packet/box/dozen, else as is; the pack factor comes from `app.sku.base_per_pack` (cigarettes 20s/10s, matches dozens, lighter box 25 as the field rule 5; bidi pending confirmation: flagged).
- Time: staging keeps temporal values as text; transformation does `(ts_text::timestamp AT TIME ZONE <source_tz>)` to `timestamptz` (source tz from Q4, default UTC) and `business_date = (captured_at AT TIME ZONE 'Asia/Dhaka')::date` (our `app.dhaka_date`). MySQL zero dates (`0000-00-00`) become NULL and are counted.

## 4. (c) Load order, performance, restartability
**Order.** 1 dry run (`profile`, no database); 2 review of the column list and the settings; 3 masters (small tables): staged, matched to our masters by normalised code, id map and lookups; 4 then **one fact table at a time**: stage, transform month by month, verify each month, drop that table's staging (the sales and outlet-route staging stay for the reconciliation): small facts (attendance, section summary, the four programme archives), geo, then sales; 5 `reconcile`, owner sign-off, `cleanup` (drops the staging), `finalize` (read indexes, autovacuum back on, ANALYZE).

**Staging.** `apsis_stage.<table>` tables are **logged** (they survive a restart and a failover), typed, no constraints, no indexes, only the reviewed columns plus `_row_uuid`, `_chunk`, `_stmt`. COPY per INSERT statement (50,000-row batches inside one statement). Staging is **one process**; tables are independent, so the operator may run several `--only` jobs in parallel (control rows are per table); that was not tested.

**Truncation and failover.** The control table records, per table, the rows read from the dump (`rows_parsed`) and the distinct rows staged (`rows_in`), per month and in total. A resume checks that the staged table still holds exactly those rows; if not (restore, failover, manual drop) it re-stages from the dump. A month is never verified against an empty staging copy: the transform refuses and sets the table back to "pending". The reconciliation compares rows read from the dump with the vendor's own counts (`mapping/expected_counts.json`, the inventory) and fails on any gap.

**Sizing (estimates, never promises).** Dump 52.5 GB. In PostgreSQL: `sales_line` about 122 M rows x about 100 bytes = 12-15 GB + chunk index; `visit_geo` 89 M x about 130 bytes = 11-14 GB; the rest under 5 GB; read indexes after load 8-12 GB. Staging peak = the masters (about 1-2 GB) + the table in flight (geo about 15 GB as typed text) + the sales staging kept at the end (about 15 GB) + WAL for logged staging. Plan **250 GB free storage** and autogrow on (final account only). Duration: a pure-Python tokenizer reads roughly 8-15 MB/s in one process: 52.5 GB is **4-7 hours of parsing in one process** (the earlier "3-5 h with four processes" was not what the code does), plus transform and index time: plan a 12-hour window on a database no user is live on (see the runbook), measure the first month of sales before continuing, and parallelise with `--only` if the measured rate demands it.

**Load-window settings.** Server parameters set by the runbook and reverted after: `max_wal_size = 64GB`, `checkpoint_timeout = 30min`, `wal_compression = on`, `maintenance_work_mem = 2GB`. The job's session sets `synchronous_commit = off` itself (`PGOPTIONS`, in the code). Archive partitions are created with autovacuum off; `finalize` turns it on and builds the read indexes. No foreign keys on archive tables.

**Restartable.** `apsis_ctl.chunk` per table: a `_stage` row (resume point = last complete INSERT statement, rows parsed) and one row per month: `pending -> staged -> transformed -> verified | failed`. The same command resumes: verified months are skipped, an unverified month is deleted by chunk key and re-inserted (an index on `chunk_key` makes that cheap). Settings that change the result (source time zone, quantity unit) are stored per run; a run with other settings while verified months exist is refused until `reset-transform`. No step needs a hand edit of `apsis_ctl`.

## 5. (e) Where the history lands and how it is read
**Archive schema `apsis_hist`, not the live `app.memo` / `app.visit` (D-APSIS-MIG-02, unchanged and still right):** the live tables need memo numbers, signatures, verdicts and parents the history cannot supply, carry write-once, stamping and projection triggers, and the vendor sales table is by outlet, SKU and day, not by memo. Masters stay in the existing `app` tables, owned by the October master-data load; this tool matches them (section 3, D-APSIS-MIG-06/-07).

**Layout.** Monthly range partitions on `business_date` for sales, geo, attendance and the programme archive; `ensure_partition` creates a month only inside 2025-10..2026-12 (a garbage date lands in the default partition, which the reconciliation requires to be empty; it is a SECURITY DEFINER function so the job role creates no table). `chunk_key` indexed; read indexes after load.

**Reading history (V0262).** Views in schema `dw`: `v_hist_sales_line`, `v_hist_sales_day`, `v_hist_visit_geo`, `v_hist_attendance` and **`v_sales_with_history`** (live `dw.v_outlet_sku_daily` after `apsis_ctl.setting.history_until`, archive up to it; one row per date, outlet, SKU, with `source`). Every view carries the scope columns `zone_id, territory_id, division_id, wing_id` (attendance gets them from the user's home zone), ends with `data_origin, is_effective` as the dw contract requires, and has column comments. **Scope**: the views filter nothing themselves (like every dw view); the server-side scope rule filters on those columns exactly as it does for the live views; rows whose geography could not be resolved have NULL scope ids and are visible to national roles only; history is attributed to the geography as of the load (past moves, request R1, are not kept: report users must be told).
**Who may read.** The project's grant map (`app.db_role_grant`, applied by `app.apply_db_role_grants()`) is the single source: V0262 adds the five history relations to the `except_tables` of the `dw` rows of `api_rw` and `worker_rw` (and with them `jobs_rw`, which inherits `worker_rw`), and `v_hist_visit_geo` / `v_hist_attendance` (exact coordinates, per-person attendance) to those of `web_ro` and `bi_reader`, then runs the refresh. A test runs the refresh after the migrations and checks `SELECT/INSERT/UPDATE/DELETE` per role on every history relation and `USAGE` on every migration schema. **Which reports include history:** those that compare across the cutover (monthly trend, same month last year, outlet sales history, route productivity Dec-Sep) read `v_sales_with_history`; day/live reports, dues, targets and loyalty do not. Phones never download history; the bundle rules are untouched.

## 6. (d) Reconciliation: gates, not a printout
`reconcile` (and `reconcile.sql` + `gates.py`) writes one numbers-only JSON and a one-line verdict; the exit code is non-zero on any failed gate. Every problem is a sentence with numbers. Gates:
- **Tables:** per table, rows read from the dump = the vendor's count (`mapping/expected_counts.json` from the inventory; a missing expected count fails); staged distinct rows = the sum of the monthly rows; rows loaded + rows skipped = staged rows; **skipped share** (zero dates, bad numbers) <= threshold; collapsed duplicate rows reported; a fact table without a primary key fails until the owner accepts it.
- **Money:** per business day, staging sum (milli-taka) = archive sum, difference exactly 0, totals equal; **per-SKU quantity** differences 0.
- **Time zone:** the vendor's own route-day "visited" figures (`trans_section_summary`) against our recomputation from the loaded geo rows under the chosen zone: agreement >= 0.80, else fail with "the source time zone or the date column may be wrong" (a wrong zone shifts evening sales to the next Dhaka day and this is the check that sees it). The dry run adds the hour-of-day histogram of each date column with a hint (utc / dhaka_local / unclear) to choose `--source-tz` before loading; there is no fallback to `created_at`.
- **Masters and scope:** distinct normalised vendor outlet/route/SKU codes matched >= 0.50 (a table that matches nothing stops the run before facts); sales rows without an outlet match <= 0.10; without an SKU match <= 0.10; matched outlet but no zone/wing chain <= 0.02. All thresholds are in `mapping/columns.json` and are the owner's to confirm (the first real run shows the real shares; 980k vendor outlets against 737k of ours means a legitimate unmatched share).
- **Memo numbers** (when the sales table has them): none on more than one outlet. **Control:** default partitions empty, every month verified.
- Informational: outlets per route (vendor vs ours), counts of vendor-deleted rows.

## 7. (f) Privacy and the column review
- **Reviewed column list.** `mapping/column_review.json` lists, per table, every column as `keep` or `drop`. The loader refuses a table with an unclassified column, with a column in both lists, with a column the dump does not have, and with a credential-looking column in `keep` without an explicit `ack_keep_credential_like`. The name patterns (credential, device, personal, `owner|phone|mobile|contact|email|address|name|...`) only **suggest** the first draft (`profile --suggest-review`); a person reviews it. Anything that is neither personal nor a credential stays: the programme archives hold the whole reviewed row as `jsonb`, so promotion, gift and scheme names survive the deletion of the dump. Dropped column **names** (never values) are stored in `apsis_ctl.report` and printed.
- **Not "no personal data at all".** The tool loads only what the review keeps; a column with personal content under an unexpected name is the reviewer's to catch, which is why the dry run lists every column name and why the list is reviewed before the first real run.
- Outlets we do not have: archived by code only (`outlet_stub`). The loader never prints a row. **Errors** are reduced to the SQLSTATE (`psql VERBOSITY=sqlstate`): server messages quote offending values and never reach a log or `apsis_ctl.chunk.error`.
- Names from the dump are data: table, file and column names pass a strict identifier pattern and an allow-list (the 26 tables) and are double-quoted; values travel through COPY or psql variables; a test feeds hostile table, file and column names.
- Credentials: dropped by the review; no vendor hash is ever reused. Test fixtures are invented. The job's identity reads the dump from a private container (`docs/requests/apsis-dump-landing.md`).
