**Phase 1 (now): preserve and profile only.**
- `apsis-migration.py profile` reads the dump files and writes four files **outside the repository** (it refuses an output directory inside it): `apsis-profile.json` + `.md` (full) and `apsis-profile.sanitised.json` + `.md`. Per table: name, engine, declared charset, row count, column names and declared types, primary key and indexes (incl. foreign keys). Per column: null share, distinct count (capped, memory-bound), min/max length, min/max **value** for numeric and date columns (full file only; withheld for phone/NID/counter-like long digit strings), a **shape histogram** (empty, datetime-like, date-like, time-like, uuid-like, hash-like, e-mail-like, url-like, phone-like, digits-only, decimal, bengali, bengali-latin-mixed, latin-text, alnum-code, other), hour-of-day histograms for datetime columns, and a **value list only** for a column with fewer than 30 distinct values that are all short codes (letters, digits, underscore) whose column name is not personal- or credential-looking (Capitalised words only when the column name says status/type/tier/...). Reference checks from a small mapping (`mapping/profile_refs.json`): the share of fact keys found in a master key column, exact and after the normalisation rule. **No row is ever printed or written.** The sanitised rendering has no value ranges and is the one that may be committed after the lead reviews it.

Memory: statements are parsed lazily; distinct sets are capped; a line over 256 MB is refused.
- **No transform, no reconciliation, no cleanup, no deletion** in phase 1: every command except `profile` refuses unless `APSIS_PHASE=2` is set, which only the lead enables.
- Runbook for phase 1: copy the dump as-is to private storage (lane infra-final's landing wrapper), run `profile` in the final account, hand the two full files to the owner and the sanitised pair to the lead (`docs/runbooks/apsis-history-migration.md`, "Phase 1").

## 1. Principles (parked phase-2 design)
1. The migration runs only inside the final Azure account, as a Container Apps job next to the private PostgreSQL, and reports only counts and checksums.
2. Re-runnable by construction: every target row has a deterministic key (UUID v5 of namespace + vendor table + vendor key); every fact chunk is deleted by chunk key and re-inserted in one transaction (masters are matched, never created); running twice changes nothing.
3. Restartable: per-table, per-chunk checkpoints in a control table; a killed run resumes at the first unverified chunk.
4. Reversible: every imported row lives in the archive schema (dropped by schema) or in the id map; the only live-master write (coordinate fill) is logged with before and after; a PITR restore point is taken first.
5. No personal data in logs, reports, tests or this repository. Reports hold numbers only.
6. Money is integer milli-taka computed with exact decimal arithmetic (never float); quantities are base units via the SKU's pack factor.

### Conversions (exact)
- Money: `amount_mtk = floor(amount_decimal * 1000 + 0.5)` on `numeric` (half up for non-negative; `app.div_half_up` semantics for negatives). No `float`/`double` in any conversion; the unit tests compare with `Decimal`.
- Quantity: `qty_base = qty_vendor * pack_factor` when the vendor unit is a packet/box/dozen, else as is; the pack factor comes from `app.sku.base_per_pack` (cigarettes 20s/10s, matches dozens, lighter box 25 as the field rule 5; bidi pending confirmation: flagged).
- Time: staging keeps temporal values as text; transformation does `(ts_text::timestamp AT TIME ZONE <source_tz>)` to `timestamptz` (source tz from Q4, default UTC) and `business_date = (captured_at AT TIME ZONE 'Asia/Dhaka')::date` (our `app.dhaka_date`). MySQL zero dates (`0000-00-00`) become NULL and are counted.

## 4. (c) Load order, performance, restartability
**Order.** 1 dry run (`profile`, no database); 2 review of the column list and the settings; 3 masters (small tables): staged, matched to our masters by normalised code, id map and lookups; 4 then **one fact table at a time**: stage, transform month by month, verify each month, drop that table's staging (the sales and outlet-route staging stay for the reconciliation): small facts (attendance, section summary, the four programme archives), geo, then sales; 5 `reconcile`, owner sign-off, `cleanup` (drops the staging), `finalize` (read indexes, autovacuum back on, ANALYZE).

**Staging.** `apsis_stage.<table>` tables are **logged** (they survive a restart and a failover), typed, no constraints, no indexes, only the reviewed columns plus `_row_uuid`, `_chunk`, `_stmt`. COPY per INSERT statement (50,000-row batches inside one statement). Staging is **one process**; tables are independent, so the operator may run several `--only` jobs in parallel (control rows are per table); that was not tested.

**Truncation and failover.** The control table records, per table, the rows read from the dump (`rows_parsed`) and the distinct rows staged (`rows_in`), per month and in total. A resume checks that the staged table still holds exactly those rows; if not (restore, failover, manual drop) it re-stages from the dump. A month is never verified against an empty staging copy: the transform refuses and sets the table back to "pending". The reconciliation compares rows read from the dump with the vendor's own counts (`mapping/expected_counts.json`, the inventory) and fails on any gap.

**Sizing (estimates, never promises).** Dump 52.5 GB. In PostgreSQL: `sales_line` about 122 M rows x about 100 bytes = 12-15 GB + chunk index; `visit_geo` 89 M x about 130 bytes = 11-14 GB; the rest under 5 GB; read indexes after load 8-12 GB. Staging peak = the masters (about 1-2 GB) + the table in flight (geo about 15 GB as typed text) + the sales staging kept at the end (about 15 GB) + WAL for logged staging. Plan **250 GB free storage** and autogrow on (final account only). Duration: a pure-Python tokenizer reads roughly 8-15 MB/s in one process: 52.5 GB is **4-7 hours of parsing in one process** (the earlier "3-5 h with four processes" was not what the code does), plus transform and index time: plan a 12-hour window on a database no user is live on (see the runbook), measure the first month of sales before continuing, and parallelise with `--only` if the measured rate demands it.

**Load-window settings.** Server parameters set by the runbook and reverted after: `max_wal_size = 64GB`, `checkpoint_timeout = 30min`, `wal_compression = on`, `maintenance_work_mem = 2GB`. The job's session sets `synchronous_commit = off` itself (`PGOPTIONS`, in the code). Archive partitions are created with autovacuum off; `finalize` turns it on and builds the read indexes. No foreign keys on archive tables.

**Restartable.** `apsis_ctl.chunk` per table: a `_stage` row (resume point = last complete INSERT statement, rows parsed) and one row per month: `pending -> staged -> transformed -> verified | failed`. The same command resumes: verified months are skipped, an unverified month is deleted by chunk key and re-inserted (an index on `chunk_key` makes that cheap). Settings that change the result (source time zone, quantity unit) are stored per run; a run with other settings while verified months exist is refused until `reset-transform`. No step needs a hand edit of `apsis_ctl`.

## 5. (e) Where the history lands and how it is read
**Archive schema `apsis_hist`, not the live `app.memo` / `app.visit` (D-APSIS-MIG-02, unchanged and still right):** the live tables need memo numbers, signatures, verdicts and parents the history cannot supply, carry write-once, stamping and projection triggers, and the vendor sales table is by outlet, SKU and day, not by memo. Masters stay in the existing `app` tables, owned by the October master-data load; this tool matches them (section 3, D-APSIS-MIG-06/-07).

**Layout.** Monthly range partitions on `business_date` for sales, geo, attendance and the raw archive; `ensure_partition` (SECURITY DEFINER, so the job role creates no table) creates a month only inside the plausible window (`apsis_ctl.setting` `window_from` / `window_to`, default 2025-10-01..2026-12-31, set by the migrate role). A row with a usable date **outside** the window (1970 epoch, before the vendor's first year, future) goes to `apsis_hist.reject` with a count, gets no partition, and fails the reconciliation above `max_reject_share`. `chunk_key` is indexed; read indexes are built by `finalize`.

**What is archived.** Typed: sales (`sales_line`, with `extra jsonb` = every other reviewed column of the vendor row: paid, due, credit, memo number, ...), geo, attendance, the vendor's section summary. **Every other table** of the 26 (masters, mappings, prices, programme and target tables) is archived raw: the reviewed columns of each row, whole, as jsonb (`raw_archive`). So nothing a later step may need for dues, balances, points, targets, stock or memo numbers is destroyed, **except the columns the reviewed list dropped as personal or credential** (if a balance column was dropped by mistake it is lost when the dump is deleted: the review must check that, runbook step 0.6).

**Reading history (V0262).** Views in schema `dw`: `v_hist_sales_line`, `v_hist_sales_day`, `v_hist_visit_geo`, `v_hist_attendance` and **`v_sales_with_history`** (live `dw.v_outlet_sku_daily` after `apsis_ctl.setting.history_until`, archive up to it; quantity only: the live aggregate has no money column). Every view carries the scope columns (`zone_id, territory_id, division_id, wing_id`; attendance from the user's home zone as of the load), ends with `data_origin, is_effective`, and has column comments. The views filter nothing themselves; rows with unresolved geography have NULL scope ids.
**Who reads (lead ruling, fix round 2).** The API's per-user scope filter is the only place scope is enforced, and `api_rw` is also the sync role, so history is **not** granted to `api_rw`, `worker_rw`, `jobs_rw` (grant-map entries in V0262 and a test that runs `apply_db_role_grants()`); `web_ro` and `bi_reader` get the aggregate views but not the coordinate and attendance views. The scoped reader is a separate read-only role **`hist_ro`** (SELECT on exactly these five views, nothing else; outside the five-role map so the refresh never touches it) with its own login, used by a second small read pool in the API's analytics path; the same server scope filter applies on the scope columns; the sync code never holds that pool. The request to the server lane is `docs/requests/apsis-history-reader.md`. **Report wiring is not built**: no API or web code reads these views today; what exists and is tested is the role, its exact privileges, and the SQL a scoped reader runs (a scope array, NULL-scope rows only for national readers).
**Which reports include history:** those that compare across the cutover (monthly trend, same month last year, outlet sales history, route productivity Dec-Sep) read `v_sales_with_history`; day/live reports, dues, targets and loyalty do not. History is attributed to the geography as of the load (past moves, request R1, are not kept; a rep who moved takes their old attendance to the new territory): report users must be told. Phones never download history; the bundle rules are untouched.

## 6. (d) Reconciliation: gates, not a printout
`reconcile` writes one numbers-only JSON and a one-line verdict; the exit code is non-zero on any failed gate; every problem is a sentence with numbers.
- **Coverage of the expected list:** the loop runs over the vendor's 26 tables (`mapping/expected_counts.json`), not over what was staged: a table that was never staged, a refused or ignored file name, an `--only` run, a timeout, all fail ("expected but never loaded"). A sign-off is impossible after a partial run.
- **Tables:** rows read from the dump = the vendor's count (the file must hold exact `count(*)` figures, not `information_schema` estimates: confirm with the owner, Q18); staged distinct rows = the sum of the monthly rows; loaded + skipped + rejected = staged rows; skipped share and reject share within thresholds; collapsed duplicate rows reported; a fact table without a primary key fails until the owner accepts it.
- **Money and quantity:** per business day staging sum = archive sum (exact milli-taka, difference 0, totals equal); per-SKU quantity differences 0; **zero-money, zero-quantity and NULL/blank-amount lines** above 2 percent of non-zero-sale lines fail (a wrong column or unit shows here); negative-money lines are counted and reported, never hidden.
- **Mapping coverage:** every target column with its source column (names only) is in the report; a target column that resolves to no vendor column stops the table's transform and fails the report unless the reviewed mapping lists it as `absent_ok` (intentionally absent). Nothing loads as 0, NULL or false by silence.
- **Time zone: evidence, not a gate.** The decision is made before the run from the dry run's evidence (hour-of-day histogram against working hours; the vendor's own date column against the timestamp's date in each candidate zone) and signed by the owner; the report prints the chosen zone and, only when the geo table has a route column, how many of the vendor's own route-day "visited" figures equal our recomputation (routes matched by normalised code). It is informational; the tool never switches the zone and re-runs by itself.
- **Masters and scope:** distinct normalised vendor outlet/route/SKU codes matched >= 0.50 (a master matching nothing stops the run); unmatched outlet rows <= 0.10, unmatched SKU rows <= 0.10, matched outlet with no zone/wing chain <= 0.02. Thresholds sit in `mapping/columns.json`; the first real run shows the real shares (980k vendor outlets against 737k of ours means a legitimate unmatched share); who may change a threshold after a failed run is the lead, with the owner's written yes.
- **Memo numbers** (when present): none on more than one outlet. **Control:** default partitions empty, every month verified. Informational: outlets per route.

## 7. (f) Privacy, the column review, names, characters
- **Reviewed column list.** `mapping/column_review.json` classifies every column of every table as `keep` or `drop`; the loader refuses a table with an unclassified column, a column in both lists, a column the dump does not have, or a credential-looking column in `keep` without an explicit ack. The name patterns only **suggest** the first draft (`profile --suggest-review`); they miss names such as `national_id`, `android_id`, `app_version`, photo URLs: the reviewer reads the full column list. Dropped column **names** (never values) are reported. Whether the vendor's column names may sit in this public repository until it goes private is the owner's call (names are structure, not data); until then the reviewed file may be kept in the private deploy repository and passed by path.
- **Not "no personal data at all".** The tool loads what the review keeps; a personal column under an unexpected name is the reviewer's to catch.
- **Characters.** The dump is read strictly as UTF-8 (`--charset` states another). A decode failure stops the run naming the line number only; the dry run counts undecodable rows and **mojibake hints** (UTF-8 Bangla read as latin1) and reports them; the tool never guesses a character set (Q2).
- **Logs.** Errors are reduced to the SQLSTATE; parser errors name a statement number and file line only (no table or value). Names from the dump (table, file, column) pass a strict identifier pattern and an allow-list and are double-quoted; values travel through COPY or psql variables. An INSERT statement larger than 256 MB is refused with the remedy (re-dump with a smaller `--net-buffer-length`); a statement is parsed lazily, not held as a list of rows.
- Outlets we do not have: archived by code only (`outlet_stub`). Credentials: dropped by the review; no vendor hash is ever reused. Test fixtures are invented.
