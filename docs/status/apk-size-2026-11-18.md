## 5. Why AMO grew as much as SR without programmes screens

1. AMO has its own large feature module (`feature.amo` +210 KB dex, the largest single package) and the heaviest of the new art: 43 new resources, 75 KB of traced vector XML plus 23 KB of webp, against 8.7 KB for SR.
2. It shares every touched core and feature module (core +125 KB, sale, memo, map, database) and the Compose and WorkManager code they pull in.
3. It gained maps-compose (+54 KB) and the AMO map screen; AMO also loses less from the scanner change in relative terms because its base was smaller.
4. AMO's smaller baseline (5.0 MB) makes the same bytes a larger percentage.

## 8. Recommendation

The growth is explained and legitimate; the absolute size (5.5 to 5.8 MB) is far inside the 30 MB budget. Cheapest first steps: items 2, 3 and 5 (no visual change), then item 1 with design sign-off. Font subsetting (7) gives the largest single win but needs a Bangla device walk. Re-baselining is the lead's call and is not done here.

## 9. Follow-up: reductions applied (lead's go, 2026-11-18)

Built from INT + this branch, same flags as above.

| App | 6 Nov baseline | INT before | After | vs baseline |
|---|---:|---:|---:|---:|
| sr | 5,348,832 | 5,782,830 | 5,740,128 | +7.3% |
| amo | 5,004,623 | 5,485,347 | 5,436,817 | +8.6% |
| tso | 5,073,976 | | 5,005,836 | -1.3% |

Applied:
- **Item 1 (vector art), lossless only.** Rewrote `android:pathData` in 78 vector XML files with implicit command repetition and minimal separators (an expansion check confirmed the parsed commands and numbers are identical for every path; 0 mismatches). Honest correction to my earlier 40-70 KB estimate: without changing geometry this saves only about 6 KB compressed; real savings need re-tracing with fewer points, which changes pixels and is not done. Goldens: `:android:ui-screenshots:test` (verify mode) passes with no golden changed, so rendering is pixel-equal; no golden file is touched.
- **Item 2 (PublicSuffixDatabase).** Dropped `assets/PublicSuffixDatabase.list` via `androidResources.ignoreAssetsPatterns` in the three apps (about 42 KB download each; confirmed absent from the APK). Checked: OkHttp 5.5.0 reads the list in `HttpUrl.topPrivateDomain()` and in `Cookie.parse` (when a Set-Cookie carries a Domain attribute; `Cookie.parse` runs only when a `CookieJar` other than `NO_COOKIES` is installed; corrected 2026-11-25 after the lead's review); grep over all Kotlin finds no `topPrivateDomain`, `CookieJar`, `CookieManager` or `HttpCookie` use; every phone `OkHttpClient` is built without a cookie jar (default `NO_COOKIES`, so `Cookie` parsing never runs); the phone talks to one API host. Other libraries do not use OkHttp's list.
- **Item 4 (lossy webp):** nothing to do. All 16 illustration webps are already lossy (VP8 + alpha); the only png is the brand mark. Packshots untouched.
- **Item 5 (arsc):** `localeFilters` en and bn is already in place in all three apps, so there is no locale to drop. The arsc growth is real strings (about 1,346 entries in amo, Bangla and English); no unused-resource pruning was found to be safe without a per-string review.
- **Item 3 (R8 repackage + Intrinsics removal): not done.** The release variant's unit tests run on unobfuscated classes, so they cannot prove that no class protected by a keep rule is renamed, and I have no release-APK smoke run here. Left out per the lead's rule.
- Items 6-7: not done, as instructed.

Result: the sr and amo warnings stay (+7.3%, +8.6%), about 45 KB lower each. Reaching the warn line needs geometry or font/library work (items 6-7 or re-traced art), which is outside this change.
