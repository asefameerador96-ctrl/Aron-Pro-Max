**Stock Save attempt UUIDs after a process kill (real behaviour, corrected 2026-11-17 by A-GATE3; the older text here said "memory only" and was false).** The attempt keys
(`StockLoad.attemptUuids`: one client UUID per "SKU=quantity in the entry unit") are written to a small file (`StockAttemptStore`, `FileStockAttemptStore`: the date,
then `sku=qty<TAB>uuid` lines, per numeric user id) BEFORE the commit and removed when the commit is confirmed. What happens after a kill:
- killed BEFORE the commit: nothing landed; the file holds the keys; the typed quantities are gone (screen state is not persisted); a re-entry of the same figure posts
  the SAME UUID, which `recordStock` stores once: the issue is stored exactly once.
- killed AFTER the commit and before the screen noticed: the movements are in Room, the file still holds their keys; reopening Stock shows them in the loaded figure;
  entering the SAME figure again posts the same UUID, `recordStock` finds it stored, and the screen says "already saved" and adds nothing: an issue cannot be doubled
  by re-entry. **Acknowledged cost:** a rep who really wants a second issue of exactly the same figure in that window (after a kill, before any other Save) gets
  "already saved" and must enter a different figure (or the difference); the file is cleared by the next confirmed Save of anything.
- a figure that differs from the attempt gets a new UUID (the key includes the quantity), so a real new issue is never swallowed.
- the file is scoped to the date the movements carry (round 3 of A-GATE3: it is now labelled with the MOVEMENT's date, so a Save across Dhaka midnight and a kill still
  matches the relaunched day's load), is validated line by line as a UUID v4 (a damaged line is ignored), and the screen's loaded figure grows only by movements the
  repository really stored (a UUID the purge already forgot adds nothing and says "already saved").
It is not part of the support file and is harmless to keep after logout (UUIDs, SKU ids and figures only).

## checkout-hold-refused verdict=fail
SUMMARY: FAIL on the B5 lens. Under the new nextSendable rule the check-out is held until a day_submit of its date is acked. Two cases work: Send again of an exhausted submit, and the release of an integrity-quarantined submit, because both keep their low seq. A day with no submit row releases the check-out at once. ## resume-day-path verdict=fail
SUMMARY: The restore and 04:00 lens (rulings 1 to 5, SR and AMO) fails with three blocking findings. Nothing was run; this is a code reading of 2ca39b11..12a178bc, first-parent, and the merge 52cd8afe was not reviewed beyond the resolution files touched here.

Trace (a), kill at 23:50 and relaunch at 00:30: resumeDay brings the call back through callToRestoreAcross (today, then the open check-in dates). closeForgottenDays waits because a call is open, and the gate becomes EARLIER_CALL_OPEN. SR keeps VISIT/FORCE/NO_SALE open and the Sale tile leads only to that call (PICKER is gated). AMO keeps CONTROL_CALL/JOINT_CALL/SALE open. Every other gated screen names the earlier call and its outlet and offers Close.

Trace (b), relaunch at 08:00: three writes in order, each in its own transaction. First the visit_close dated D (abandoned, flagged by an end stamped on D+1). Then recordCheckOut writes D's day_submit(s) and the phone's check-out together. A kill between them is resumed cleanly with nothing written twice, as long as there is a single caller. The unsaved-draft drop really keeps saved memos. A half-entered QC or an unsaved edit of the call's memo is dropped with the notice.

Trace (f), ruling 5: sale, QC, close, collection, survey, content view and the AMO assessment, price and distribution records take the visit's date. A collection outside a call is today's and never attaches to an earlier visit.

Trace (g): check-in for D+1 works at any hour, including 00:10 after a midnight close, and stock for D+1 can then be entered.

Blocking:
1. A memo edit left open across midnight now traps the SR. The EDIT screen is gated by the new EARLIER_CALL_OPEN with no button that ends the edit. The 04:00 limit only ends calls, the day never closes, and check-in for D+1 is ignored.
2. The automatic 04:00 end records a call that has a saved sale or audit records as 'abandoned' with is_zero_sale=true. On AMO this goes round closeVisit's sold/audited classification, which the lane itself fixed. The server keeps the first close, so the wrong value cannot be corrected later.
3. The SR start and ON_RESUME paths run resumeDay at the same time with no mutex. The abandon can then write two visit_close rows for one visit; the server refuses the second as a content duplicate. The same race takes two location attempts for one closed day.

Other remaining ways to operate on D+1 without a D+1 check-in (lows):
- the open call itself before 04:00, which the ruling allows;
- that call kept in the foreground past 04:00, since no 04:00 timer exists;
- the clock set back after a reboot while offline (pre-existing).

What I could not check:

- what the fix manager actually does in the background;
- whether drafts survive a process kill;
