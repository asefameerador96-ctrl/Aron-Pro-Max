### 4.2 Offline-safe and idempotent: where the manual's flow would risk loss or double counting

- **Redemption (53-54)**: confirm is an online-looking step. Build it as an offline record `redemption` / `redemption_line` (client UUID, already a signed sync type) that debits a *local* optimistic balance; the server posts the ledger by source UUID (unique source, append-only). Two phones over the balance: keep the redemption, flag for review (`negative_balance_policy = flag`), never drop. No cash cashback on the memo discount line (SRM-B-76).
- **Astha gift choice (52)**: today an online-only `putGiftChoices`. New sync record `gift_choice` with per-row client UUID; last write wins by `captured_at` until the hand-over photo locks it.
- **Gift photo / campaign gift photo (57-58)**: photo is compressed and queued like outlet photos; record `gift_photo` keyed by client UUID; "Photo already captured" is answered from the local store and the server, so a retry never double-counts.
- **Points shown on Sales (55)**: read from the bundle with `as_of`; show the age. Never block a sale on a stale balance.
- **KPI / brand KPI / Match (60-62)**: read models from the bundle (`kpi`, `match_programme`) with `as_of`; computed on the server from memos, never on the phone; an offline phone shows the last copy, marked with its age.
- **Journey (59)**: computed on the device from today's visit records (offline), and on the server for the AMO view; same distance rule.
- **Sync of everything**: each new record type goes through the existing signed, idempotent upsert with property tests for duplicate and out-of-order upload.
