## 0. Cross-cutting findings

1. **Units conflict (CONFLICT-WITH-RULE).** The manual (s1) says cigarette and bidi in sticks, lighter in pieces, match in dozens, and prices per 1,000 sticks, and QC in sticks. Standing rule 5 / docs/34 s4.2 (owner 2026-10-22) says packets, box of 25, dozens on screens. The app already follows s4.2 (`shared/rules/.../Memo.kt:181-219`). **Rule wins** on Sale, Stock, Review, Memo and print. Screenshots 14, 22, 26 show small badges and "sticks" in QC: see SRM-A-34.
2. **Quantity popup and dashboard cards are the biggest UI gaps** (rows 14, 29). The manual's flow is a popup with quick buttons and history stats; the app is inline with +/-1.
3. **Call-start order differs.** Manual: select outlet, Sale History / Today's target buttons, "start the call?" Yes/No, camera for outlet photo, then Sales screen. App: select outlet (takes a GPS fix at once), full start-call screen with map and distance, no outlet photo, AV/KV then POSM before sale (`SRK/SrSaleHosts.kt:52-130`, `SRK/CallContentHost.kt:49-74`). The photo-at-call-start step is MISSING (rows 26, 27).
4. **Programme screens are now in scope** (D-OWNER-SR-PROGRAMMES-01): target and achievement by SKU, dashboard STD figures, outlet target. Rows 14, 15, 28 carry full end-to-end needs. Today the SR app has only comments saying "deferred" (`FH/HomeScreen.kt:249`).
5. **Enterprise-bar risks found in the manual's flow** (section 4 below lists the offline-safe design): OTP binding needs the network once (already so, acceptable, one-time); in-app update is online by nature; "Sale saved" must never depend on print; QC and zero-sale reason are new records that must be idempotent by client UUID; target/achievement popups must read from the local bundle (never live), and the outlet photo at call start is a media record needing UUID-keyed idempotent upload and the quota rules for photos.

## 4. Flows that risk data loss, double counting or an online-only step (and the safe design)

1. **OTP bind** is online once. Acceptable (security); the app must keep a valid session offline afterwards. Already so.
2. **In-app data update (row 11):** must not wipe unsynced records. Design: apply new reference data in a staging table, swap atomically, never touch outbox/memos; resume after kill; show progress; if offline, keep yesterday's bundle (stale banner exists).
3. **Call photo (row 27):** the call start must not need the network. Queue the photo; upload is idempotent by media UUID; failure of upload never blocks selling; a reasoned skip is recorded.
4. **Zero sale (row 40):** the zero-sale memo consumes a memo number and writes one visit_close; double tap must not create two (memo uuid is unique in the draft; keep the commit mutex).
5. **QC (row 34):** `qc_line` records are keyed by client UUID, belong to the memo transaction; edit memo supersedes (no double deduction).
6. **Target/achievement (rows 14, 15, 28):** computed from local memos, shown with "last sync" time; the server figure replaces it on sync; never read live in a sale.
7. **Check-out (row 19):** must use trusted time (server-synced offset), not the phone clock (screenshot 12 right shows an active button at a 3:00 clock).
8. **Print (row 24, 36):** commit before print; print failure never rolls back a sale.
